## HV-01 — Parsed Email to Trip Record Linking

**Proposed pattern:** GRASP Information Expert

**Stable instance name:** Parsed Email to Trip Record Linking

### Responsibility to verify

`InboxItem` is assigned responsibility for interpreting its stored parsed email information and creating or linking corresponding itinerary and expense records.

### Minimum source inspection

- `app/models/inbox_item.rb:19–25` — stored parsed-data interface.
- `app/models/inbox_item.rb:34–58` — confirmation and shortlist creation.
- `app/models/inbox_item.rb:67–187` — matching and record linking.
- `app/models/inbox_item.rb:191–207` — expense construction.
- `app/controllers/inbox_items_controller.rb:16–35` — actual callers.
- `app/models/trip_item.rb:1–28` and `app/models/expense.rb:1–28` — related records.

### Participants and claimed roles

| Participant            | Claimed role                                                       |
| ---------------------- | ------------------------------------------------------------------ |
| `InboxItem`            | Information Expert responsible for interpreting stored parsed data |
| `InboxItemsController` | Client requesting confirmation or relinking                        |
| `Trip`                 | Parent trip and association context                                |
| `TripItem`             | Itinerary record created or linked                                 |
| `Expense`              | Expense record conditionally created                               |
| `Traveler`             | Source of payer identity through trip membership                   |

### What I should find

- `InboxItem` stores and retrieves the data being interpreted.
- The controller delegates confirmation and relinking to `InboxItem`.
- `fill_missing_links!` matches existing items or creates missing records.
- The model conditionally creates expenses and processes shortlist ideas.
- These are substantive application rules, not just Active Record associations.

### Strongest objection

`InboxItem` uses data from many models and contains considerable procedural orchestration. Its responsibilities may be too broad to justify describing it as a clear Information Expert.

**Framework boundary:** Active Record supplies relationships and persistence. It does not implement the application-specific email-to-trip mapping rules. Anthropic performs earlier extraction, not this record-linking operation.

**My decision:** ☐ CONFIRMED  ☐ REJECTED  ☐ UNCERTAIN

**Proposed pattern:** GRASP Controller

**Stable instance name:** Inbound Travel Email Intake Coordination

### Responsibility to verify

`TripMailbox#process` handles the incoming-email system event by identifying the trip, evaluating sender approval, creating an inbox record and choosing the next processing action.

### Minimum source inspection

- `app/mailboxes/application_mailbox.rb:1–3`
- `app/mailboxes/trip_mailbox.rb:2–31`
- `app/mailboxes/trip_mailbox.rb:55–60`
- `app/models/trip.rb:4–19`
- `app/models/inbox_item.rb:1–16`
- `app/jobs/parse_inbox_item_job.rb:99–112`
- `app/mailers/trip_mailer.rb:2–10`

### Participants and claimed roles

| Participant           | Claimed role                                  |
| --------------------- | --------------------------------------------- |
| `TripMailbox#process` | System-event controller                       |
| `ApplicationMailbox`  | Inbound mailbox routing                       |
| `Trip`                | Destination identified from recipient address |
| `InboxItem`           | Persisted incoming email                      |
| `ParseInboxItemJob`   | Delegated AI parsing                          |
| `TripMailer`          | Delegated pending-sender notification         |

### What I should find

**Framework boundary:** Action Mailbox supplies reception and routing infrastructure. DaPlanStan supplies trip matching, approval decisions, inbox persistence and conditional delegation. Active Job and Action Mailer supply execution and delivery infrastructure.

## HV-03 — Trip Creation Coordination

**Proposed pattern:** GRASP Controller

**Stable instance name:** Trip Creation Coordination

### Responsibility to verify

`TripsController#create` coordinates the creation of a new trip, its first owner membership and follow-up cover-image retrieval.

### Minimum source inspection

- `app/controllers/trips_controller.rb:35–48`
- `app/models/trip.rb:4–19, 31–37`
- `app/models/account.rb:1–11`
- `app/models/trip_member.rb:1–6`
- `app/jobs/fetch_trip_cover_image_job.rb:4–32`
- `config/routes.rb:21–29`

### Participants and claimed roles

| Participant              | Claimed role                                            |
| ------------------------ | ------------------------------------------------------- |
| `TripsController#create` | System-event controller                                 |
| `Trip`                   | New trip with validation and inbound-address generation |
| `Account#owner_traveler` | Finds the account owner's traveler                      |
| `TripMember`             | Stores initial owner membership                         |
| `FetchTripCoverImageJob` | Performs delegated image retrieval                      |

### What I should find

- The controller creates a `Trip` using submitted trip details.
- It assigns the current user and account.
- It saves the trip before creating its initial owner membership.

**Framework boundary:** Active Record supplies validation, callbacks, associations and persistence. Active Job supplies job execution. DaPlanStan chooses the sequence and owner-membership rule; Pexels supplies external image search.

## HV-04 — Trip Membership Management Coordination

**Proposed pattern:** GRASP Controller

**Stable instance name:** Trip Membership Management Coordination

### Responsibility to verify

`TripMembersController` coordinates adding and removing participants from an existing trip, including authorization, traveler resolution, role assignment and invitations.

### Minimum source inspection

- `app/controllers/trip_members_controller.rb:1–65`
- `app/controllers/application_controller.rb:22–25`
- `app/models/trip_member.rb:1–6`
- `app/models/traveler.rb:1–8`
- `app/models/account.rb:1–11`
- `app/mailers/invitation_mailer.rb:8–13`
- `config/routes.rb:40`

### Participants and claimed roles

| Participant                                      | Claimed role                                       |
| ------------------------------------------------ | -------------------------------------------------- |
| `TripMembersController#create`, `#destroy`       | Receive membership-management events               |
| `TripMembersController#resolve_and_add_by_email` | Resolve identity and possible invitation           |
| `TripMembersController#add_traveler`             | Check duplicates and create membership             |
| `ApplicationController#current_member_for`       | Support permission checks                          |
| `Account`, `Traveler`, `User`                    | Account and participant identity records           |
| `TripMember`                                     | Connect traveler to trip and store membership role |
| `InvitationMailer`                               | Construct invitation email                         |

### What I should find

- An owner or planner membership is checked before managing travelers.
- The controller can find existing account travelers or resolve by email.
- It creates a `Traveler` when needed.

### Strongest objection

Most membership rules are implemented directly in the controller. This might be controller-heavy CRUD rather than a meaningful GRASP responsibility assignment.

**Framework boundary:** Rails handles associations, enums, persistence and callbacks. DaPlanStan implements permission checks, identity-resolution decisions and membership rules. The `TripMember` enum is not Strategy or State.

### Minimum source inspection

- `config/routes.rb:12–14`
- `app/controllers/sessions_controller.rb:4–40, 54–81`

### Participants and claimed roles

| Participant                  | Claimed role                                |
| ---------------------------- | ------------------------------------------- |
| `SessionsController#create`  | Post-authentication system-event controller |
| `#provision_account_or_gate` | Coordinates account eligibility             |
| `#create_account_for`        | Creates account and initial traveler        |
| `UserIdentity`               | Persisted external provider identity        |
| `User`                       | Local authenticated identity                |
| `Traveler#accept!`           | Links invited traveler profile to user      |
| `Account`                    | User-owned account                          |
| `Invite`                     | Provides invitation eligibility predicates  |

### What I should find

- The callback reads `request.env["omniauth.auth"]`.
- It first searches `UserIdentity` by provider and UID.

### Strongest objection

OmniAuth has already performed authentication. The remaining method may be interpreted as conventional procedural post-authentication bookkeeping rather than a distinct GRASP Controller responsibility.

**Framework boundary:** OmniAuth and provider integrations perform OAuth protocol work. Rails supplies sessions and persistence. DaPlanStan implements the local identity and account-access decisions. Google and Apple are not separate application-written strategies.

## HV-08 — Outbound Mail Delivery Logging

**Proposed pattern:** GoF Observer — framework-mediated

**Stable instance name:** Outbound Mail Delivery Logging

### Mechanism to verify

An application-defined observer registers with the mail-delivery notification system. The framework invokes its `delivered_email` callback after a qualifying delivery operation.

### Minimum source inspection

- `config/initializers/mail_logger.rb:1–7`
- `app/mailers/application_mailer.rb:1–5`
- `app/mailers/invitation_mailer.rb:1–13`
- `app/mailers/trip_mailer.rb:1–10`
- `Gemfile.lock:19, 185`

Also consult the Action Mailer 8.1.3 and Mail 2.9.0 observer contracts to verify `register_observer` and `delivered_email`.

### Participants and claimed roles

| Participant                                        | Claimed role                               |
| -------------------------------------------------- | ------------------------------------------ |
| `MailLogger`                                       | Application-defined concrete observer      |
| `MailLogger.delivered_email(message)`              | Notification callback                      |
| `ActionMailer::Base.register_observer(MailLogger)` | Observer registration                      |
| Mail gem notification system                       | Publisher, registry and dispatch mechanism |
| `InvitationMailer`, `TripMailer`                   | Mail-producing collaborators               |

### What I should find

- The application defines `MailLogger.delivered_email`.
- The initializer explicitly registers `MailLogger`.
- The documented mail framework contract calls `delivered_email` on registered observers.
- Individual mailer actions do not directly invoke the logger.
- The event relationship is independent of the specific invitation or notification email.

### Strongest objection

The actual Observer infrastructure is implemented by Rails and the Mail gem. DaPlanStan has supplied only the concrete callback and its registration.

**Framework boundary:** Do not claim DaPlanStan wrote the publisher, observer registry or notification-dispatch mechanism. Verify that application-supplied concrete observer registration is acceptable under the assignment's framework-idiom counting rule.

## HV-09 — Trip-Scoped Turbo Refresh Notifications

**Proposed pattern:** GoF Observer — framework-mediated

**Stable instance name:** Trip-Scoped Turbo Refresh Notifications

### Mechanism to verify

Application-defined publication sources request trip-scoped notifications. Browser pages subscribe to the corresponding trip stream. Turbo and Action Cable deliver refresh actions to subscribed clients.

### Minimum source inspection

- `app/models/inbox_item.rb:1–5`
- `app/jobs/geocode_trip_items_job.rb:4–21`
- `app/views/trips/show.html.erb:2–9`
- `app/views/inbox_items/index.html.erb:1`
- `Gemfile.lock:424`

Also inspect Turbo Rails 2.0.23 implementation or documentation for `broadcasts_refreshes_to`, `turbo_stream_from`, `Turbo::StreamsChannel#subscribed` and `broadcast_refresh_to`.

### Participants and claimed roles

| Participant               | Claimed role                                       |
| ------------------------- | -------------------------------------------------- |
| `InboxItem`               | Model publication source                           |
| `GeocodeTripItemsJob`     | Explicit broadcast source                          |
| `turbo_stream_from @trip` | Application subscription declarations              |
| `Turbo::StreamsChannel`   | Framework stream publisher/channel                 |
| Action Cable              | Subscription and delivery infrastructure           |
| Turbo browser runtime     | Framework-provided subscriber and refresh reaction |

### What I should find

- `InboxItem` declares `broadcasts_refreshes_to :trip`.
- `GeocodeTripItemsJob` calls `broadcast_refresh_to(trip)`.
- Both the trip show and inbox index pages subscribe through `turbo_stream_from @trip`.
- The Turbo Rails contract creates matching stream subscriptions and refresh broadcasts.
- The browser receives a framework-defined refresh action rather than a direct call from the model or job.
- These are usages of one trip-scoped notification mechanism.

### Strongest objection

Unlike `MailLogger`, DaPlanStan does not implement a concrete observer callback. Most of the subscription and reaction mechanism is supplied by Turbo.

**Critical comparison:** Does the application's explicit choice of publication sources, trip-scoped stream and subscribed views establish sufficient participation for a framework-mediated Observer instance under the same rule used for HV-08?

**Framework boundary:** Do not attribute Action Cable subscription management, Turbo Stream processing or browser refresh implementation to DaPlanStan.

**My decision:** ☐ CONFIRMED  ☐ REJECTED  ☐ UNCERTAIN

# Part C — Baseline Counting Verification

Complete these checks only after reviewing all nine instances.

- **Use-case responsibility rule:** GRASP Controller instances have been counted by cohesive system events or use cases, not by controller classes, individual methods or HTTP actions.
