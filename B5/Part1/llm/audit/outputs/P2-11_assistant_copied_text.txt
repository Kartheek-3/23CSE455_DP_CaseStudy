## 2. Candidate A — GRASP Controller: OAuth Sign-in and Identity Linking Coordination

### Essential responsibility and system event

GRASP Controller assigns responsibility for receiving and coordinating a system event to an object representing the system, a subsystem or a use case.

System event: An external OAuth authentication callback has returned to DaPlanStan, and the application must establish the corresponding local user identity and access.

Receiving object: `SessionsController#create`.

Source: `app/controllers/sessions_controller.rb:4–41`, reached through `config/routes.rb:12`.

The event is not the user's entire OAuth exchange. That exchange takes place through OmniAuth and the provider before the application processes the normalized result.

### What OmniAuth has already done

By the time the successful callback reaches `SessionsController#create`, OmniAuth is expected to have supplied `request.env["omniauth.auth"]`.

The application consumes the provider identifier, UID, email, name, image and optional access token. It does not implement the provider's authorization-code exchange or Google/Apple-specific token processing here.

Provider configuration appears in `config/initializers/omniauth.rb:1–16`, where Google and Apple are registered.

The controller delegates persistence to Active Record, user-to-account relationships to model associations, traveler acceptance to `Traveler#accept!`, and invitation-validity decisions to `Invite`.

However, it retains most of the sequencing itself.

### Why this is more than a conventional OAuth callback

The callback does not merely retrieve a user and establish a session.

It coordinates a cohesive application use case involving several domain responsibilities:

- Existing-provider identity recognition.
- Linking a new provider identity to an existing or new user.
- Connecting previously invited travelers.
- Determining whether a user already has account or membership access.
- Provisioning an independent account when permitted.
- Applying a beta-invitation gate otherwise.

This is an application-defined system-event workflow with meaningful domain outcomes. The presence of OmniAuth does not explain those decisions.

### Strongest objection

The code is controller-heavy.

`SessionsController#create` and `#provision_account_or_gate` contain authentication-adjacent business rules, identity resolution, account provisioning and access decisions.

There is no dedicated application service coordinating those operations, and the controller directly executes many database writes.

This is a valid design concern. However, GRASP Controller identifies responsibility for handling the system event; it does not require that every domain operation be perfectly separated.

In this case, the controller coordinates a complete sign-in and onboarding use case and delegates some substantive responsibilities.

Origin: Mixed, with application-owned post-authentication coordination.

### Comparison with previously confirmed GRASP Controller instances

| Instance                                        | Event                            | Distinguishing outcome                                          |
| ----------------------------------------------- | -------------------------------- | --------------------------------------------------------------- |
| Inbound Travel Email Intake Coordination        | An email arrives                 | Route it to the correct trip and initiate review/processing     |
| Trip Creation Coordination                      | A user creates a trip            | Establish trip and initial owner membership                     |
| Trip Membership Management Coordination         | A user adds/removes participants | Change membership in an existing trip                           |
| Bulk Itinerary Import Coordination              | User confirms itinerary JSON     | Import ideas and schedule geocoding                             |
| OAuth Sign-in and Identity Linking Coordination | OAuth callback completes         | Resolve local identity, session, invitations and account access |

OAuth sign-in is independent of all four previously confirmed system-event collaborations. It can occur without creating a trip, adding a trip member, importing an itinerary or processing an inbound email.

Therefore, it should not be merged into a general `Rails Controller` instance.

### Final decision

CONFIRMED

Stable instance name: `OAuth Sign-in and Identity Linking Coordination`

Counting: One new GRASP Controller collaboration. Google and Apple do not create separate instances because they use the same application callback and identity-linking responsibility.

## 3. Candidate B — Observer: Outbound Mail Delivery Logging

### Essential Observer mechanism

A defensible Observer collaboration requires:

1. A subject or publisher capable of notifying interested observers.
2. An observer implementing an expected notification operation.
3. A registration relationship connecting the observer to the publisher.
4. A defined event that causes notification without the event-producing client directly calling the observer.

The application does not have to implement its own subscription registry if a framework supplies that machinery and the application explicitly defines and registers a concrete observer.

### Actual DaPlanStan implementation

The complete application-specific implementation appears in `config/initializers/mail_logger.rb:1–7`.

```
module MailLogger
  def self.delivered_email(message)
    Rails.logger.info "[Mailer] Sent '#{message.subject}' to #{Array(message.to).join(', ')}"
  end
end

ActionMailer::Base.register_observer(MailLogger)
```

This is more than a method coincidentally named `delivered_email`.

The application:

- Defines `MailLogger` as a Ruby module.
- Provides the callback `MailLogger.delivered_email(message)`.
- Explicitly registers the module as an observer.
- Leaves the responsibility for invoking the callback to the mail-delivery infrastructure.

### Verification against the actual framework contract

The repository's `Gemfile.lock` specifies Action Mailer 8.1.3 and the Mail gem 2.9.0.&#x20;

### Participant-role mapping

| Observer role                             | Actual participant                                                                               | Source                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Subject/publisher infrastructure          | Mail gem delivery notification mechanism, including `Mail::Message` and `Mail` observer registry | Mail 2.9.0 framework contract                                              |
| Application-facing registration interface | `ActionMailer::Base.register_observer`                                                           | Action Mailer 8.1.3                                                        |
| ConcreteObserver                          | `MailLogger`                                                                                     | `config/initializers/mail_logger.rb:1–5`                                   |
| Observer notification operation           | `MailLogger.delivered_email(message)`                                                            | Same file, `2–4`                                                           |
| Registration operation                    | `ActionMailer::Base.register_observer(MailLogger)`                                               | Same file, `7`                                                             |
| Event-producing mailers                   | `InvitationMailer`, `TripMailer`                                                                 | `app/mailers/invitation_mailer.rb:1–13`; `app/mailers/trip_mailer.rb:1–10` |

There is no separately declared application-owned `Subject` interface.

The subject-side responsibilities are provided by the Mail framework, while `ActionMailer::Base` exposes the registration interface.

This distinction should be preserved in the participant-role mapping rather than incorrectly labeling `TripMailer` itself as a custom ConcreteSubject.

### Why it is a genuine Observer instance

The important evidence is the complete notification relationship:

- DaPlanStan explicitly registers a concrete observer.
- The observer satisfies the documented callback contract.
- The mail delivery machinery maintains the registry and invokes notifications.
- Individual mailers do not directly call `MailLogger`.

This matches the essential Observer mechanism.

A framework-mediated Observer implementation is defensible because the faculty permits framework idioms, provided the application/framework boundary is identified accurately.

### Strongest objection

DaPlanStan did not implement the observer registry, notification-dispatching algorithm or delivery lifecycle.

It supplies only a concrete observer and explicitly registers that observer through Action Mailer's existing API.

That means the implementation should not be presented as a fully application-written GoF Observer framework.

It is a mixed-origin Observer collaboration, with its infrastructure supplied by Rails and the Mail gem.

However, this does not negate the pattern: the application has deliberately participated in an actual observer contract, unlike a generic callback or an ordinary mailer method.

## 7. Remaining runtime and design uncertainties

The structural classifications can be settled without executing the application. The following questions concern runtime correctness and design quality instead.

OAuth:

- Whether Google and Apple callbacks succeed with the actual configuration.
- Whether provider emails are sufficiently verified before being matched to an existing `User`.
- Whether concurrent callbacks can create conflicting identity records.
- Whether a new user and identity remain persisted when beta account provisioning is denied.
- Whether account and owner-traveler creation always complete consistently.

Mail Observer:

- Whether the initializer loads successfully in the intended environment.
- Whether successful email delivery produces the expected log entry.
- Whether delivery failures bypass the success notification as expected.
- Whether the mail delivery error handler in `mail_logger.rb:11–14` affects failure reporting.

A successful delivery callback indicates that the framework's delivery operation completed; it does not prove that a recipient actually received or opened the email.

This establishes a genuine Observer collaboration, even though DaPlanStan does not implement the framework's observer registry.
