## 4. Final counting and deduplication rules

The following rules are now fixed for this baseline and should also govern eventual CSV generation and any participant counts.

1. GRASP Controller: One instance represents one cohesive system-event or use-case responsibility, not an individual controller class, HTTP action or method.
2. Repeated collaboration: The same responsibility appearing across different files or workflows is counted once.
3. Multiple runtime occurrences: Multiple OAuth providers, mailers, emails, job executions, broadcasts or subscribed pages do not automatically create independent instances.
4. Framework mediation: An Observer may use framework-supplied machinery, but the role mapping must explicitly distinguish application-owned participants from Rails, Mail, Turbo and Action Cable participants.
5. Bulk import: Preview and confirmed import remain one `Bulk Itinerary Import Coordination` instance.
6. Trip membership: Addition and removal remain one `Trip Membership Management Coordination` instance.
7. OAuth: Google and Apple remain one `OAuth Sign-in and Identity Linking Coordination` instance.
8. Turbo: Inbox-derived and geocoding-derived refreshes remain one `Trip-Scoped Turbo Refresh Notifications` instance.
9. Mail: All delivery notifications through the registered `MailLogger` remain one `Outbound Mail Delivery Logging` instance.

Participant counting, when later required, should use actual source-defined participant identities and the agreed counting convention. Repeated references to one class within the same instance do not create additional class identities. Framework and application classes must not be conflated.
