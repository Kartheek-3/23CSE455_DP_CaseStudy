# DaPlanStan — Repository-Wide Pattern Coverage Sweep

Baseline pre-freeze review · Original uploaded ZIP · Static source inspection

## 1. Scope and counting standard

I am treating the eight previously source-confirmed collaborations as the working baseline, without treating their confirmation as completed independent human verification.

The final sweep examines the remaining source for independent collaborations, rather than collecting additional instances of Rails inheritance, controller actions or model methods.

The distinction used throughout this review is:

- Pattern evidence: An identifiable responsibility assignment or interaction mechanism involving actual source participants.
- Ordinary application behavior: Framework conventions, CRUD operations, helper methods, conditionals and direct API calls that do not demonstrate a distinctive pattern collaboration.
- Duplicate evidence: Another appearance of a collaboration already identified and counted.

The repository archive contains additional application code outside the six focused investigations, notably the administrator controllers, invitation management, notification aggregation, account settings, general helpers and shared persistence configuration. These are important to inspect even if they yield no new pattern.

### Candidate B — Beta Invite Eligibility Evaluation

GRASP Information Expert · Responsibility assignment

UNCONFIRMED

Provisional instance name: `Beta Invite Eligibility Evaluation`

This is a narrower and weaker candidate.

Unlike a generic model-method claim, it does have specific cross-object responsibility evidence: the invitation record owns the information necessary to determine whether its token can be used and whether it applies to a particular email address.

#### Actual responsibility allocation

`Invite` defines:

```
def used?    = used_at.present?
def expired? = expires_at.present? && expires_at < Time.current
def usable?  = !used? && !expired?

def email_matches?(address)
  email.blank? || email.casecmp?(address.to_s)
end
```

These methods appear at `app/models/invite.rb:12–18`.

Two application callers use that information:

- `InvitesController#accept`, `app/controllers/invites_controller.rb:5–15`, checks `usable?` before saving the invitation token in the session.
- `SessionsController#provision_account_or_gate`, `app/controllers/sessions_controller.rb:63–75`, checks both `usable?` and `email_matches?` before creating an account and marking the invite used.





#### Why Information Expert might fit

The `Invite` record owns `used_at`, `expires_at` and `email`, the precise values needed for these decisions.

DaPlanStan has placed the elementary eligibility rules on the object possessing that information. Two separate controller entry points reuse these predicates rather than reimplementing their conditions.

This is a plausible GRASP Information Expert responsibility assignment.

#### Strongest false-positive explanation

The entire implementation consists of a few simple domain predicates.

There is no substantial collaboration comparable to `InboxItem#fill_missing_links!`, which interprets structured information and coordinates the creation and linking of multiple related records.

The more accurate explanation may be ordinary domain-model encapsulation: keeping simple validation predicates close to their data.

Furthermore, the full signup eligibility decision remains in `SessionsController`. `Invite` does not independently decide whether a user should receive an account.

Origin: Application-owned predicates with Active Record persistence.

Closest established comparison: `Parsed Email to Trip Record Linking` — GRASP Information Expert. The proposed invite instance is materially simpler and needs a stricter significance check.

Decision: UNCONFIRMED, low priority.

I would not include this in the baseline merely because it is technically compatible with the Information Expert principle. It needs a positive argument that the responsibility is substantial enough to count consistently with the other instances.

These are exclusion decisions for the inventory. They do not imply that the code is incorrect or lacks architectural structure.

The correspondence between the archive and the stated Git commit also remains unverified.

Static asset bundles, framework internals unrelated to the previously identified contracts, and deployed external-service behavior have not been exhaustively audited. They are not obvious gaps in the application-owned pattern sweep, but they should remain explicit scope boundaries.
