GRASP Controller — source-level classification

Decision: `Bulk Itinerary Import Coordination` qualifies as a GRASP Controller responsibility assignment. The evidence is not simply that `TripItemsController` is a Rails controller. It handles a distinct system-level import operation involving preview, validation, duplicate resolution, persistence and deferred geocoding.

The implementation is also controller-heavy: most of the import algorithm resides inside `bulk_create_items`. That is a design limitation, but it does not eliminate the system-event coordination responsibility.

The confirmation is based on static source evidence. Independent human review and runtime testing remain pending.

### Are preview and confirmation one cohesive use case?

Yes.

The preview stage parses the supplied JSON, checks that it contains an array, and prepares the items for review without creating records.

The confirmation form in `app/views/trip_items/import.html.erb:101–106` submits the reviewed JSON back to the same endpoint using `confirm: "1"`.

That submission triggers the persistence stage.

These are consecutive phases of one user goal: importing itinerary ideas. They do not warrant two separate GRASP Controller instances.

## 2. Application decisions and delegation

### Decisions made by `TripItemsController#import`

| Source lines | Application decision                                         |
| ------------ | ------------------------------------------------------------ |
| `31–38`      | Distinguish confirmed submission and invoke batch creation   |
| `39–44`      | Choose pasted JSON or uploaded file and handle missing input |
| `45–49`      | Parse input and reject a non-array result during preview     |
| `49–54`      | Count missing-name entries and prepare error information     |
| `34–38`      | Construct an import-result message and redirect              |

The controller determines which use-case stage is active. Rails supplies request parameters and rendering/redirecting infrastructure, but these branching rules are written by DaPlanStan.

### Decisions made by `bulk_create_items`

| Source lines | Application decision                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| `129–133`    | Initialize counts and collect existing names                                   |
| `134`        | Temporarily disable the model's geocoding callback                             |
| `135–147`    | Skip unnamed entries, detect duplicate names and fill selected existing fields |
| `148–162`    | Create new items, normalize kinds and assign `idea` status                     |
| `163–165`    | Update the name lookup and collect IDs lacking coordinates                     |
| `166–168`    | Log individual item failures and continue                                      |
| `170–171`    | Schedule geocoding when needed and return the result summary                   |
| `172–174`    | Attempt callback restoration in `ensure`                                       |

The application therefore makes real import-policy decisions; the method is not merely a forwarding wrapper around `TripItem.create!`.&#x20;



### Responsibilities delegated elsewhere

`TripItem` supplies the domain model, its validations, kind/status enums and `geocoded?` behavior through the included concern.

Active Record handles association-scoped queries, record insertion, column updates and callback registration.

`GeocodeTripItemsJob` receives the IDs of newly created items requiring geocoding. Its `perform` method loads each item, invokes `geocode_from_address` and requests a Turbo refresh after processing.&#x20;



The external geocoding calls remain in the existing `Geocodable` collaboration. They are not new behavior implemented by the import controller.

## 3. Why this qualifies as GRASP Controller

GRASP Controller assigns responsibility for receiving and coordinating a system event to an object representing the relevant system or use case.

The important distinction is between receiving a request and coordinating the application's response to a meaningful business event.

The importer demonstrates the second responsibility.

`TripItemsController#import` establishes the two-stage workflow, while `bulk_create_items` performs the batch-operation decisions and invokes the necessary collaborators.

The implementation is therefore not just:

`HTTP request → Active Record create → redirect`

It includes input inspection, confirmation, matching, selective updating, creation of missing itinerary ideas, deferred geocoding and result reporting.

These collectively support a meaningful use-case responsibility.

### Strongest argument against confirmation

Most of the business operation is concentrated in `bulk_create_items`.

The method directly handles data normalization, deduplication, creation, error handling and callback control. It delegates database operations and geocoding execution, but does not delegate much of the actual import policy to separate application objects.

Consequently, this is certainly controller-heavy procedural orchestration.

However, these two conclusions are not mutually exclusive. GRASP Controller describes responsibility assignment; it does not guarantee low coupling, small methods or ideal separation of concerns.

The controller is doing more work than an ideally thin coordinator, but it still owns a coherent system event with an identifiable outcome.

That is why I retain the CONFIRMED classification while documenting the concentration of business logic as a design limitation.

The previous three implementations also use Rails infrastructure, but their system events and domain outcomes are different. &#x20;



### Why bulk import is independent

Bulk import neither creates a trip nor manages its membership. It operates on an existing trip, processes user-supplied structured data and creates or updates itinerary records.

It also differs from inbound-email intake. The JSON import is explicitly initiated and confirmed by a user; it does not use `TripMailbox`, `InboxItem` or `ParseInboxItemJob`.

Although both paths may eventually create `TripItem` records, sharing a destination model is not sufficient to merge their system-event collaborations.

Similarly, reusing `GeocodeTripItemsJob` does not make bulk import another geocoding-pattern instance.

Under the established use-case counting rule, bulk import should be counted separately.

| Observation                                                                          | Source location                                              | Verification status                                                |
