# Geocoding Collaboration — Source Investigation 01

Candidates only

DaPlanStan original source ZIP · Static source analysis

## 1. Main finding

The geocoding implementation has three distinct triggering paths, rather than a single controller-to-job workflow.

1. Manual request: A user selects Fix missing pins on the trip page. `TripsController` identifies records without coordinates and schedules `GeocodeTripItemsJob`.
2. Bulk import: `TripItemsController` imports itinerary items, temporarily disables the model's geocoding callback, then schedules the same background job for newly created records needing coordinates.
3. Ordinary record saving: The `Geocodable` concern registers an Active Record `after_save` callback. This can invoke geocoding during a normal `TripItem` save without passing through `GeocodeTripItemsJob`.

These paths ultimately reach the same application-level operation: `TripItem#geocode_from_address`, which delegates to the implementation supplied by the `Geocodable` module.&#x20;



This distinction matters because not every geocoding operation is asynchronous. The manual and bulk-import paths enqueue a job, whereas the model callback is part of the normal record-save lifecycle.

The strongest initial explanation is shared model behavior combined with Rails callbacks, background-job orchestration and a Geocoder library integration. A recognized GoF pattern has not yet been demonstrated.

The two job-driven entry points converge at the same model method used by the normal save callback. The diagram shows logical calls, not a verified runtime execution.

### Path A — Manual geocoding

The route is defined inside the `resources :trips` member block, under the application's `whats.` host constraint.

The user-facing button in `app/views/trips/show.html.erb:53–68` submits a POST request when missing-coordinate items exist. The controller's `show` method calculates that count using `!i.geocoded?` at lines 11–28.

The request then proceeds as follows:

1. Rails routes the request to `TripsController#geocode_missing`.
2. Controller authentication and `set_editable_trip` run first. The lookup restricts the trip to a user with an owner or planner membership.
3. The action selects IDs of trip items that fail `geocoded?`.
4. If any exist, the controller calls `GeocodeTripItemsJob.perform_later(missing_ids, @trip.id)`.
5. Rails Active Job supplies the queueing mechanism.
6. When the job executes, its `perform` method loads the trip and individually finds each item.
7. The job invokes `item.geocode_from_address`.

The application does not call the external geocoding service directly from the controller.&#x20;



### Path B — Bulk import

`TripItemsController#import` calls `bulk_create_items` after confirming the imported JSON.

The import method temporarily disables the `TripItem` save callback, creates the records, collects IDs without complete coordinates, and enqueues those IDs for the same background job. Its `ensure` block calls `TripItem.set_callback` afterward.

This is an important second entry path. It also introduces a question for later verification: the callback is restored without explicitly repeating its original conditional predicate. The actual post-import callback configuration should be inspected before making a behavioral claim about it.&#x20;



### Path C — Automatic geocoding during saving

The `Geocodable` module registers:

```

after_save :geocode_from_address,
  if: -> {
    (saved_change_to_address? || saved_change_to_name?) &&
      !geocoded?
  }

```

This condition is true when the saved address or name changed and both latitude and longitude are not already present.

The callback can be reached through ordinary `TripItemsController#create` and `#update` operations. The source also contains `InboxItem` methods that create trip items, so those records can pass through the same model lifecycle. However, `InboxItem#fill_missing_links!` updates existing records using `update_columns`, which bypasses the normal callback.&#x20;



Rails provides callback execution. The application supplies the callback condition and method.

## 3. How the model and concern collaborate

`TripItem` includes the `Geocodable` concern and defines its own method:

```

def geocode_from_address
  return if TRANSPORT_KINDS.include?(kind.to_s) && address.blank?
  super
end

```

Here, `TRANSPORT_KINDS` contains `flight`, `car`, `train` and `ferry`.

The model applies a domain-specific guard to avoid geocoding transport-company or transport-item names when no real address is supplied. Otherwise, `super` invokes the implementation found in the included concern.

This is ordinary, valid Ruby method lookup and module reuse. It is not, by itself, proof of any GoF pattern.&#x20;



The concern then performs the actual lookup algorithm.

1

Try the address-based lookup

`Geocodable#geocode_with_bias`, lines 27–45, extracts a location hint from the address, looks it up, then requests a full-address result with latitude/longitude parameters when a reference was found.

If a reference and result are available, the method uses `Geocoder::Calculations.distance_between` and accepts the result only if the distance is under 50 km. When the hint lookup fails, it tries the full address without that distance check.

The code attempts geographic biasing. Whether the configured Nominatim service meaningfully applies the supplied `lat`/`lon` parameters has not been verified.

2

Try fallback queries

`Geocodable#geocode_fallback`, lines 46–67, builds alternative search strings from address components, the item's name combined with its trip title, and the item's name alone.

For each query, it takes the first result. If another geocoded stop establishes a trip center, a fallback result more than 2,000 km from that center is rejected.

`trip_geocoded_center`, lines 69–75, calculates an arithmetic mean of other trip items' saved latitude and longitude values.

3

Persist coordinates or log failure

`Geocodable#geocode_from_address`, lines 13–24, runs the first method and, if it returns no result, the fallback method.

If a result is available, it stores latitude and longitude using `update_columns`. Otherwise it logs a warning. Exceptions are rescued and logged as warnings.

Rails documents that `update_columns` bypasses validations and callbacks. This prevents the coordinate write from starting another normal save-callback cycle.&#x20;

### The external service boundary

The application calls `Geocoder.search` and `Geocoder::Calculations.distance_between`. The installed Geocoder dependency supplies those APIs; DaPlanStan does not implement the underlying geocoding HTTP client in these files. The dependency documentation describes search queries, results and the pass-through `params` option.&#x20;

## 6. The design problem being solved

DaPlanStan stores itinerary stops that may have full addresses, partial addresses, place names or no usable coordinates.

The collaboration is designed to convert that incomplete location information into coordinates that can be persisted and displayed on the trip map.

It attempts to solve several practical problems: avoiding obviously unsuitable transport-name lookups, using context to improve ambiguous searches, trying alternative search strings, avoiding excessive distance from known trip stops, and processing batches away from the initiating controller request.

After a job completes its loop, it requests a Turbo refresh. The trip page provides the coordinate data to its map controller, which creates Leaflet markers only for items with latitude and longitude values.&#x20;



The source establishes these design intentions. It does not establish the accuracy or operational reliability of the resulting coordinates.

## 7. Possible design-pattern classifications

Only now, after tracing the collaboration, are pattern names considered.

Candidate A — Template Method

Unconfirmed

Why it might fit: `TripItem#geocode_from_address` performs a preliminary check and invokes `super`, allowing the included concern's method to perform the main operation. That resembles behavior specialization around a shared implementation.

Why it might be a false positive: There is no clearly established invariant template algorithm with designated subclass-overridden primitive steps or hooks. The model simply guards an inherited module method.

Assessment: Weak resemblance; more naturally explained as method overriding and module reuse.

Candidate B — Strategy

Unconfirmed

Why it might fit: The implementation uses two lookup approaches, `geocode_with_bias` and `geocode_fallback`, depending on whether the earlier approach succeeds.

Why it might be a false positive: There are no interchangeable strategy objects, shared behavioral interfaces or runtime selection of independently encapsulated algorithms. Both methods are hardcoded into a single concern.

Assessment: Weak resemblance; fixed sequential fallback is a stronger description.

Candidate C — Adapter

Unconfirmed

Why it might fit: The application uses a domain-oriented method, `geocode_from_address`, while the concern handles calls to the third-party `Geocoder.search` API and translates returned coordinates into model updates.

Why it might be a false positive: The concern does more than interface conversion, and there is no explicit incompatible target interface or separate adapter/adaptee object collaboration. It is simply an integration boundary offering convenient methods.

Assessment: Plausible superficial resemblance; insufficient evidence for a GoF Adapter.

Candidate D — Observer

Unconfirmed

Why it might fit: The application reacts to model saves using callbacks and requests a Turbo refresh after background processing.

Why it might be a false positive: Rails already supplies callback dispatch, and Turbo supplies refresh broadcasting. The inspected application code does not show a separate application-defined subject/observer registration and notification collaboration.

Assessment: Framework event mechanisms are visible, but an application-implemented Observer has not been established.

No candidate is approved for the baseline pattern inventory. These are hypotheses to evaluate or reject, not four identified pattern instances.

## 8. Strongest alternative explanation

The geocoding collaboration is a shared model concern combined with procedural fallback logic, Rails lifecycle callbacks and optional background-job execution.

This explanation accounts for the observed code without inventing additional abstractions.

Specifically, `Geocodable` centralizes the reusable lookup and persistence behavior; `TripItem` provides a domain-specific guard; `TripsController` and `TripItemsController` initiate batch work; and the Geocoder gem provides the external lookup implementation.

A concern and a reusable method do not automatically constitute a recognized GoF design pattern.

## 9. Important unresolved behavior and verification work

There are several source-supported questions worth investigating before confirming any classification or claiming runtime correctness.

| Issue                        | Why it matters                                                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Callback restoration         | The importer re-registers the callback without its original condition; inspect the resulting callback chain                      |
| Global callback modification | `skip_callback` changes class-level behavior; investigate possible interference between concurrent requests                      |
| Rate limiting                | The job sleeps 1.1 seconds per item, but an item may cause several `Geocoder.search` calls, so per-request spacing is not proven |
| Job success logging          | The job logs after invoking geocoding, even when the concern returns without coordinates or rescues an exception                 |
| External query parameters    | Verify how Nominatim handles the `lat` and `lon` values sent through Geocoder's `params` option                                  |
| Actual results               | No geocoding responses or successful execution logs were examined                                                                |
| Pattern mechanism            | No independently established interchangeable strategy, adapter contract, observer registration or template-hook protocol         |
| Reviewer decision            | No human review outcome has been recorded for any of these candidates                                                            |

The callback-restoration and rate-limit issues are especially useful verification observations. They should be recorded as possible behavioral risks, not asserted as observed defects without tests.

### Suggested verification cases

For subsequent human verification, the most informative cases would be a normal item with an address, a transport item with no address, an ambiguous address requiring fallback, an item with manual coordinates, a failed external lookup, and a bulk import followed by a normal save.

These would help confirm the flow's behavior, although passing functional tests alone would still not prove a particular design-pattern classification.
