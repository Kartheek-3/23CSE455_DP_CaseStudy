## P01 — Parsed Email to Trip Record Linking

**Pattern name:** Information Expert (GRASP)\
**Stable instance name:** Parsed Email to Trip Record Linking\
**Verification status:** SOURCE-CONFIRMED

**Source locations**

- `app/models/inbox_item.rb:19–25, 34–58, 67–187, 191–207`
- `app/controllers/inbox_items_controller.rb:16–35`
- `app/models/trip.rb:4–12`
- `app/models/trip_item.rb:1–28`
- `app/models/expense.rb:1–28`
- `app/models/trip_member.rb:1–6`
- `app/models/traveler.rb:1–8`

**Participant-role mapping**

`InboxItem` — Information Expert responsible for interpreting its stored parsed email data.\
`InboxItemsController` — requesting client for confirmation and relinking.\
`Trip` — parent domain context.\
`TripItem` — itinerary record created or linked.\
`Expense` — conditionally created linked expense.\
`TripMember` and `Traveler` — membership and payer-identification collaborators.

**Strongest supporting evidence**

`InboxItem` stores the extracted information through `parsed_data`. Its `confirm_and_create_items!` and `fill_missing_links!` methods interpret the data, match existing itinerary items, create missing records and conditionally create expenses.

**Strongest false-positive explanation tested**

The behavior could be interpreted as an oversized Active Record model performing procedural orchestration across several domain objects rather than a clear Information Expert responsibility.

**Reason retained**

The central information being interpreted belongs to `InboxItem`, and the application explicitly assigns substantive record-linking rules to this model rather than merely storing the extraction result.

**Application/framework boundary**

DaPlanStan implements the mapping, matching and creation decisions. Rails Active Record supplies associations, queries and persistence. Anthropic performs the earlier extraction, not this linking operation.

**Runtime verification:** NOT COMPLETED\
**Independent human sign-off:** NOT ESTABLISHED

# B. Rejected-Candidate Evidence Records

## R01 — Geocoding Template Method

**Proposed pattern:** Template Method (GoF Behavioral)\
**Source area:** Shared geocoding concern and TripItem model

**Why it initially appeared plausible:** `TripItem` overrides `geocode_from_address`, checks transport-item conditions and calls `super` to reuse the concern implementation.

**Decisive rejection reason:** There is no application-defined template algorithm invoking overridable primitive steps. `TripItem` guards the complete operation instead of supplying a primitive operation within an algorithm skeleton.

**Better source explanation:** Ordinary Ruby module method reuse with a model-specific guard.

**Source locations:** `app/models/concerns/geocodable.rb:4–16, 27–65`; `app/models/trip_item.rb:32–37`

**Final status:** REJECTED

## R02 — Geocoding Strategy

**Proposed pattern:** Strategy (GoF Behavioral)\
**Source area:** Primary and fallback geocoding

**Why it initially appeared plausible:** The concern contains two different lookup methods, `geocode_with_bias` and `geocode_fallback`.

**Decisive rejection reason:** Both are fixed methods within the same concern. The code executes them in a predetermined fallback sequence and does not select interchangeable implementations through a common Strategy role.

**Better source explanation:** Sequential conditional fallback within one algorithm.

**Source locations:** `app/models/concerns/geocodable.rb:13–14, 27–65`

**Final status:** REJECTED

## R03 — Geocoding Adapter

**Proposed pattern:** Adapter (GoF Structural)\
**Source area:** Geocoder API integration

**Why it initially appeared plausible:** The `Geocodable` concern invokes the external Geocoder library and converts lookup results into coordinates stored on application records.

**Decisive rejection reason:** No incompatible application target interface and adaptee interface are established. The concern directly invokes `Geocoder.search` and performs domain-specific persistence.

**Better source explanation:** Direct third-party API integration with application-specific query and coordinate-handling logic.

**Source locations:** `app/models/concerns/geocodable.rb:13–22, 27–65`; `config/initializers/geocoder.rb:1–7`

**Final status:** REJECTED

## R04 — Itinerary Timeline–Map Event Coordination

**Proposed pattern:** Observer (GoF Behavioral)\
**Source area:** Frontend Stimulus controllers and browser events

## R05 — Beta Invite Eligibility Evaluation
