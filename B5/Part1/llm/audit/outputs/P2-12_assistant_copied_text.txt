# DaPlanStan — Frontend Interaction Investigation

Source Investigation 06 · Original uploaded source ZIP · Static source analysis

New patterns unconfirmed

## 1. Initial source findings

I inspected the JavaScript files under `app/javascript/controllers/` and searched their corresponding views for controller attachments, event dispatches and listeners.

The directory contains 16 application-defined Stimulus controllers, plus two Stimulus initialization/registration files.

The strongest cross-controller interaction is between three controllers:

- `TimelineController` publishes `map:locate` and `map:reset` when a user selects or deselects an itinerary row.
- `TripNavController` publishes `map:resize` when the itinerary panel becomes visible.
- `MapController` listens for all three events and performs the corresponding Leaflet operations.

This is a real, application-defined communication relationship. However, the event names are explicitly known to the producers and consumer, and the events are dispatched directly onto the map's DOM element. It should not automatically be classified as a fully decoupled Observer implementation.

Two other mechanisms are present but should be kept separate: normal DOM/Stimulus interactions within individual controllers, and server-driven Turbo Stream refreshes that may update the page and cause Stimulus controllers to reconnect.

## 2. Main Stimulus controllers and their responsibilities

The application's Stimulus setup is defined in `app/javascript/controllers/application.js:1–9` and `index.js:1–4`. Controllers are loaded through the import map and attached to HTML elements using `data-controller` attributes. Stimulus supplies controller lifecycle handling, targets and declarative actions.&#x20;

### Flow A — Select an itinerary row

UI initiation

`app/views/trips/_timeline.html.erb:23` attaches `TimelineController`.

The view renders itinerary rows through `app/views/trip_items/_item_row.html.erb:7–17`.

For rows with coordinates, the application includes:

```
data-action="click->timeline#select"
data-lat="<%= item.latitude %>"
data-lng="<%= item.longitude %>"
data-item-id="<%= item.id %>"
```

Rows without coordinates are not assigned this click action.

Publisher

`TimelineController#select`, `app/javascript/controllers/timeline_controller.js:11–33`, looks up:

```
const map = document.getElementById("trip-map")
```

For a newly selected row, it sends:

```
map.dispatchEvent(new CustomEvent("map:locate", {
  detail: {
    lat: parseFloat(row.dataset.lat),
    lng: parseFloat(row.dataset.lng),
    id: row.dataset.itemId
  },
  bubbles: true
}))
```

The event carries the coordinates and itinerary-item ID.

Consumer

`MapController#connect`, `app/javascript/controllers/map_controller.js:51–57`, registers an event listener on the map element.

`MapController#onLocate`, lines 92–109:

- Reads `lat`, `lng` and `id` from `event.detail`.
- Calls Leaflet's `flyTo`.
- Iterates through known markers.
- Highlights the selected marker.
- Dims other markers.

End result: The selected itinerary row controls the map's focus and marker highlighting without invoking a `MapController` method directly.&#x20;



### Flow B — Deselect an itinerary row

The same `TimelineController#select` method checks whether the clicked row was already selected.

If true, it dispatches:

```
map.dispatchEvent(
  new CustomEvent("map:reset", { bubbles: true })
)
```

`MapController#onReset`, lines 77–89, restores marker appearance and calls `flyToBounds` when saved coordinates are available.

The result is that clicking the selected row again restores the map's broader trip view.

This is the same timeline-to-map communication relationship, not a separate pattern instance.

### Flow C — Make the itinerary panel visible

The trip view attaches:

```
<div data-controller="trip-nav pull-to-refresh">
```

`app/views/trips/show.html.erb:16`

Desktop and mobile navigation buttons use `click->trip-nav#switch`, as shown in:

- `app/views/trips/_tab_bar.html.erb:4–24`
- `app/views/trips/_bottom_nav.html.erb:4–24`

`TripNavController#switch`, `trip_nav_controller.js:22–29`, selects the new tab and updates the URL.

`TripNavController#show`, lines 31–56, shows the selected panel and hides the others.

Only when the itinerary panel transitions from hidden to visible does it execute:

```
const mapEl = p.querySelector("[data-controller='map']")
if (mapEl) mapEl.dispatchEvent(new CustomEvent("map:resize"))
```

The receiving `MapController#onResize`, lines 68–74, invokes Leaflet's `invalidateSize`, then fits the known map coordinates where possible.

This solves a concrete UI problem: the map needs to recalculate its layout when a previously hidden panel becomes visible.

Unlike the other two events, `map:resize` is dispatched without `bubbles: true`. That is sufficient for this observed flow because it is dispatched directly on the element carrying the listener.

## 4. Custom-event producer and consumer table

A search across the application JavaScript identified exactly these three `CustomEvent` construction sites in the inspected source.&#x20;



| Event        | Application producer        | Dispatch location              | Application consumer     | Behavior                            |
| ------------ | --------------------------- | ------------------------------ | ------------------------ | ----------------------------------- |
| `map:locate` | `TimelineController#select` | `timeline_controller.js:26–31` | `MapController#onLocate` | Move map and highlight marker       |
| `map:reset`  | `TimelineController#select` | `timeline_controller.js:21–22` | `MapController#onReset`  | Reset marker styling and map bounds |
| `map:resize` | `TripNavController#show`    | `trip_nav_controller.js:40–43` | `MapController#onResize` | Recalculate map size and bounds     |

All three listeners are registered at `map_controller.js:51–56` and removed during `disconnect` at lines 60–64.

### Does one controller know about another?

There is no direct controller-instance lookup or controller-method invocation in these interactions.

Neither `TimelineController` nor `TripNavController` imports `MapController` or retrieves it through Stimulus's application API.&#x20;



However, they are not completely independent of the map's implementation:

- `TimelineController` explicitly looks for the DOM ID `trip-map`.
- `TripNavController` explicitly searches for an element with `data-controller='map'`.
- Both producers know the event names that `MapController` handles.
- Only the map element registers listeners for these application-defined events.

The result is indirect method communication through directly targeted DOM events, not a general event bus or a completely anonymous publisher/subscriber relationship.

## 5. Other frontend event and lifecycle behavior

Several other interactions initially resemble notification mechanisms, but their origins are different.

| Interaction                | Actual code                                              | Classification of behavior                                      |
| -------------------------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| Kind or category selection | `kind_picker_controller.js:19–57`; related form partials | Ordinary Stimulus action and local DOM updates                  |
| Receipt selection          | `receipt_controller.js:6–31`                             | Native file-input event and FileReader API                      |
| Location marker dragging   | `location_picker_controller.js:18–58`                    | Leaflet event callbacks and local form updates                  |
| Pull-to-refresh            | `pull_to_refresh_controller.js:13–26, 59–70, 124–130`    | Browser touch listeners and explicit `window.location.reload()` |
| Navigation render event    | `trip_nav_controller.js:11–19`                           | Subscription to Turbo's `turbo:render` lifecycle event          |
| Dropdown closing           | `details_close_controller.js:5–19`                       | Browser click and Turbo navigation listeners                    |
| Page transition effects    | `app/javascript/application.js:11–32`                    | Turbo lifecycle events and browser View Transitions API         |
| Flash dismissal            | `flash_controller.js:4–16`                               | Local timers and DOM removal                                    |

The Stimulus `data-action` mechanism binds DOM events to controller methods. That is supplied by Stimulus; the application supplies the methods that react to those events.&#x20;

Similarly, listening to `turbo:render` does not mean DaPlanStan independently implements an Observer framework. Turbo publishes the lifecycle event, while the application uses it to restore tab appearance after rendering.

### No additional app-defined event family found

The inspected JavaScript does not demonstrate another custom publisher/consumer relationship comparable to the three `map:*` events.

In particular, `pull-to-refresh` does not publish a custom refresh event for other controllers. It calls `window.location.reload()` directly.

## 6. Revisit: Trip-Scoped Turbo Refresh Notifications

The application contains two trip-stream subscriptions:

- `app/views/trips/show.html.erb:2`
- `app/views/inbox_items/index.html.erb:1`

Both use:

```
<%= turbo_stream_from @trip %>
```

Two application paths can cause refresh broadcasting to the corresponding trip stream:

- `InboxItem` declares `broadcasts_refreshes_to :trip` in `app/models/inbox_item.rb:5`.
- `GeocodeTripItemsJob` explicitly calls `Turbo::StreamsChannel.broadcast_refresh_to(trip)` in `app/jobs/geocode_trip_items_job.rb:21`.

## 7. New pattern candidate

After reviewing the source, only one new classification is worth retaining.

Observer-like DOM Event Coordination

UNCONFIRMED

Provisional instance name: Itinerary Timeline–Map Event Coordination

Category: GoF Behavioral candidate · Mixed application/browser implementation

Actual participants

- Event producers: `TimelineController#select` and `TripNavController#show`.
- Notification target: DOM element `#trip-map`.
- Event subscriber: `MapController`, through its `addEventListener` calls.
- Notification handlers: `MapController#onLocate`, `#onReset` and `#onResize`.
- Event infrastructure: Browser `EventTarget`, `CustomEvent` and event dispatch machinery.

Why it might fit

The producers publish named events without directly calling receiver-controller methods. The consumer explicitly registers notification handlers, responds to those notifications and unregisters handlers when disconnected.

Those are concrete elements of an Observer-like event relationship.

Strongest false-positive explanation

The implementation may be nothing more than ordinary browser event handling.

The producer identifies the map's DOM element directly and dispatches an event specifically to it. There is no application-defined subject abstraction, independently maintained observer list or evidence of multiple interchangeable listeners.

Most of the event mechanism comes from browser APIs, while Stimulus supplies the controller lifecycle.

Origin: Mixed — application-defined events, dispatch decisions and reactions; browser-provided event infrastructure.

Decision: UNCONFIRMED.

Formal verification must decide whether this browser-mediated targeted event relationship is sufficiently substantive to count as an Observer instance, rather than merely an ordinary DOM event contract.

I do not recommend separate pattern candidates for `map:locate`, `map:reset` and `map:resize`. They are operations within the same map-interaction collaboration.

No new candidate is justified merely by `connect`, `disconnect`, Stimulus targets, Leaflet marker callbacks or ordinary UI form interactions.

## 11. Strongest non-pattern explanation

The frontend architecture is best explained as server-rendered Rails views enhanced by small Stimulus controllers, direct DOM custom events, Leaflet map operations and Turbo lifecycle integration.

The application uses declarative Stimulus actions for ordinary component behavior. For the timeline and map, it introduces explicit DOM events so that map interactions can be requested without calling another Stimulus controller's methods.

This is a meaningful frontend collaboration, but it is still compatible with the simpler explanation of ordinary browser event-driven programming.

The source does not demonstrate a general-purpose application event bus, custom notification registry or elaborate frontend coordination abstraction.
