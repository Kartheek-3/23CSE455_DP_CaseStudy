## 1. GRASP Information Expert — CONFIRMED

### Essential responsibility rule

GRASP Information Expert recommends assigning a responsibility to the class that possesses, or has direct access to, the information necessary to perform it.

It does not require a special interface, inheritance hierarchy or named pattern class.

For this investigation, the specific responsibility is interpreting stored email-extraction data and converting it into linked itinerary and expense records.

### Actual participants and roles

Information Expert: `InboxItem`

Relevant methods:

- `InboxItem#parsed_data` — `app/models/inbox_item.rb:19–21`
- `InboxItem#parsed_data=` — lines 23–25
- `InboxItem#confirm_and_create_items!` — lines 34–58
- `InboxItem#fill_missing_links!` — lines 67–187
- `InboxItem#build_expense` — lines 191–207

Requesting client: `InboxItemsController#update`, `app/controllers/inbox_items_controller.rb:16–35`.

Collaborating domain objects: `Trip`, `TripItem`, `Expense` and `Traveler`.

### Supporting evidence

`InboxItem` stores the structured AI result in `parsed_data_json` and exposes it through `parsed_data`.

The controller delegates record creation to the model:

```
when "confirm"
  @item.confirm_and_create_items!(current_user)
```

The model then accesses the information it owns:

```
def fill_missing_links!(added_by)
  data = parsed_data
  return unless data.is_a?(Hash)
```

Using that information, it identifies existing itinerary items, creates missing ones and conditionally creates expenses.

The most important supporting locations are `app/controllers/inbox_items_controller.rb:16–26`, `app/models/inbox_item.rb:67–99` and `app/models/inbox_item.rb:101–207`.&#x20;



This is more than merely using Active Record. DaPlanStan has explicitly assigned the application-specific interpretation and linking responsibility to the object holding the extracted email data.

### Strongest objection

`InboxItem` does not possess all the required information independently.

It must query the associated trip, existing itinerary items, members and expenses. Its implementation also mixes extraction interpretation, deduplication, record creation and expense-related rules.

This raises a legitimate responsibility-design concern: the model may be coordinating more behavior than is ideal.

However, GRASP Information Expert allows collaboration with other objects. It does not require that all necessary data physically reside inside one class.

The essential observation remains that `InboxItem` owns the extracted data and has been given the responsibility for interpreting it.

### Application versus framework

Mainly application-owned.

Rails supplies model associations, database querying and persistence methods. It does not supply the application's mapping of travel legs, accommodations, bookings and shortlist entries into DaPlanStan records.

### Final decision

CONFIRMED

The source establishes a defensible application-specific GRASP Information Expert responsibility.

Stable instance name: `Parsed Email to Trip Record Linking`

Scope of confirmation: The assignment of extracted-email interpretation and linking responsibility to `InboxItem`, not a claim that every responsibility in this model is ideally allocated.

## 2. GRASP Controller — CONFIRMED

### Essential responsibility rule

GRASP Controller recommends assigning the handling of a system event to an object representing the system, a subsystem or the relevant use case.

Such an object receives the event, coordinates the required actions and delegates responsibilities to appropriate collaborators.

It does not need to inherit from `ActionController`.

For this investigation, the system event is the arrival of an inbound travel email.

### Actual participants and roles

System-event controller: `TripMailbox#process`, `app/mailboxes/trip_mailbox.rb:2–31`.

Event routing entry point: `ApplicationMailbox`, `app/mailboxes/application_mailbox.rb:1–3`.

Delegated collaborators: `Trip`, `InboxItem`, `ParseInboxItemJob` and `TripMailer`.

### Supporting evidence

`ApplicationMailbox` specifies:

```
class ApplicationMailbox < ActionMailbox::Base
  routing(all: :trip)
end
```

This routes email events into `TripMailbox`.

Inside `TripMailbox#process`, the application implements the event coordination.

It identifies the destination trip at lines 3–9, evaluates sender eligibility at lines 11–14 and creates an `InboxItem` at lines 16–24.

It then determines what happens next:

```
if approved
  ParseInboxItemJob.perform_later(inbox_item.id)
else
  notify_owners_of_pending_sender(trip, inbox_item)
end
```

The mailbox does not attempt to implement AI extraction itself. It delegates that responsibility to a separate job. It also delegates notification construction and delivery to a mailer.

This creates a clear application-defined separation between the event handler and subsequent work.&#x20;

### Strongest objection

`TripMailbox` inherits from `ActionMailbox::Base`. Receiving inbound email through its `process` method is a normal Rails convention.

Consequently, simply discovering a `TripMailbox` class or a `process` method would not be enough to establish GRASP Controller.

The decisive evidence is the application-written coordination inside that method: trip identification, sender checks, inbox persistence and conditional delegation.

The framework determines how the event reaches the handler. DaPlanStan determines what that handler does with the event.

### Application versus framework

Mixed, with the relevant responsibility application-owned.

Action Mailbox supplies inbound-event dispatch and mailbox lifecycle behavior.

DaPlanStan supplies the event-handling decisions and orchestration.

### Final decision

CONFIRMED

The source establishes an application-defined system-event controller for incoming travel email.

Stable instance name: `Inbound Travel Email Intake Coordination`

Scope of confirmation: The `TripMailbox#process` event-handling responsibility. This does not automatically classify every Rails controller or mailbox in the repository as a separate GRASP Controller instance.

## 3. Turbo-mediated Observer — UNCERTAIN

### Essential mechanism

Observer requires a notification relationship between a subject or event source and one or more interested observers.

For a framework-mediated implementation, the source should establish a subscription, a notification publisher and a delivery mechanism connecting them.

Unlike the GRASP candidates, this is a collaboration whose defining behavior largely depends on external framework machinery.

### Actual participants

Application-defined refresh source:

```
broadcasts_refreshes_to :trip
```

Trip-stream subscriber declarations:

```
<%= turbo_stream_from @trip %>
```

`app/views/trips/show.html.erb:2`

```
<%= turbo_stream_from @trip %>
```

Additional application-defined publisher from geocoding:

`GeocodeTripItemsJob#perform`, `app/jobs/geocode_trip_items_job.rb:20–21`

```
Turbo::StreamsChannel.broadcast_refresh_to(trip)
```

### Supporting evidence

The `InboxItem` model declares automatic refresh broadcasting to its associated trip.

Both the inbox index and the trip show page subscribe using the trip object.

The geocoding job also explicitly requests a broadcast for a trip.

A repository-wide search identified these application declarations and found no additional custom observer-registration implementation in the inspected application source.&#x20;



Together, these statements establish an intended trip-scoped notification mechanism.
