## 1. Final decisions

Itinerary Timeline–Map Event Coordination

Proposed GoF Observer

REJECTED

Trip-Scoped Turbo Refresh Notifications

Framework-mediated Observer

CONFIRMED

The distinction is based on what the collaborations actually do, not simply whether they use events.

The timeline–map implementation sends commands to a specifically identified map element through browser events. The Turbo implementation establishes a genuine trip-scoped publication/subscription relationship through the framework's documented contract.

The Turbo confirmation is for a framework-mediated Observer instance, not an independently implemented application-owned GoF Observer framework. Runtime operation and independent human sign-off remain separate verification matters.

## 2. Candidate A — Itinerary Timeline–Map Event Coordination

### Minimum Observer mechanism

A defensible Observer implementation should have an identifiable subject or event publisher, an observer that registers interest, a notification mechanism and a response triggered by that notification.

For this investigation, merely using `CustomEvent` is insufficient. The key question is whether the application implements a meaningful subscription relationship or simply uses events as an indirect way to direct operations at a known component.

### Actual publishers

Publisher 1: `TimelineController#select`

`app/javascript/controllers/timeline_controller.js:11–33`

The method receives a Stimulus click action from an itinerary row. It locates the map using:

```
const map = document.getElementById("trip-map")
```

When a selected row is clicked again, it dispatches `map:reset` at lines 21–22.

When a new geocoded row is selected, it dispatches `map:locate` with latitude, longitude and the itinerary-item ID at lines 26–34.

The row click binding is defined in `app/views/trip_items/_item_row.html.erb:7–17`.

Publisher 2: `TripNavController#show`

`app/javascript/controllers/trip_nav_controller.js:31–56`

When the itinerary panel becomes visible after being hidden, it executes:

```
const mapEl = p.querySelector("[data-controller='map']")
if (mapEl) mapEl.dispatchEvent(new CustomEvent("map:resize"))
```

The dispatch occurs at lines 40–43. Its purpose is specifically to tell the map to recalculate its dimensions.

### Actual subscriber

`MapController` registers all three event handlers in `app/javascript/controllers/map_controller.js:51–56`:

```
this.handleLocate = this.onLocate.bind(this)
this.handleReset  = this.onReset.bind(this)
this.handleResize = this.onResize.bind(this)

this.element.addEventListener("map:locate", this.handleLocate)
this.element.addEventListener("map:reset", this.handleReset)
this.element.addEventListener("map:resize", this.handleResize)
```

It removes these listeners during `disconnect`, lines 60–64.

The registered methods perform real application behavior:

| Event        | Handler                  | Source lines | Effect                                       |
| ------------ | ------------------------ | ------------ | -------------------------------------------- |
| `map:locate` | `MapController#onLocate` | `92–109`     | Moves map and highlights an itinerary marker |
| `map:reset`  | `MapController#onReset`  | `77–89`      | Restores markers and overall map bounds      |
| `map:resize` | `MapController#onResize` | `68–74`      | Recalculates Leaflet map size and bounds     |

These are actual dispatch/listener relationships. They are not merely similarly named methods.&#x20;



### Does either publisher directly call `MapController`?

No.

Neither publisher retrieves a `MapController` instance and invokes its methods. Instead, each dispatches a browser event onto the map's DOM element.

That creates a degree of implementation separation: the publishers do not need to know how Leaflet markers are created or moved.

However, the separation is limited.

### Strongest evidence against Observer

The producers explicitly identify the destination map element:

- `TimelineController` uses `document.getElementById("trip-map")`.
- `TripNavController` searches for `[data-controller='map']`.

They also know the map-specific event names.

The collaboration has one intended receiver, `MapController`, and the three events encode requests for particular map operations.

There is no demonstrated application-defined subject whose changing state is published to independently interested observers. Nor does the source show a broader registration contract that allows different application components to subscribe to itinerary-selection changes.

Although the browser's `EventTarget` mechanism technically supports multiple listeners, the application uses it here primarily to deliver targeted commands.

This is the decisive distinction: the code implements a genuine DOM event relationship, but the more precise architectural description is targeted inter-controller communication through browser events.

A one-receiver implementation can qualify as Observer in principle. The rejection is not based on receiver count alone. It is based on the combination of explicit destination targeting, event semantics and the absence of a substantive subject/observer responsibility beyond ordinary DOM event dispatch.

### Origin and decision

Origin: Mixed. DaPlanStan defines event names, dispatch conditions and reactions. The browser supplies `CustomEvent`, `EventTarget`, listener registration and dispatch. Stimulus supplies controller lifecycle integration.

Final decision: REJECTED as a distinct GoF Observer instance.

This is not a rejection of the implementation's functionality. It is a decision not to inflate the design-pattern inventory by relabeling ordinary targeted DOM event communication.

All three events remain documented together as one rejected candidate, rather than three pattern instances.

## 3. Candidate B — Trip-Scoped Turbo Refresh Notifications

CONFIRMED — Framework-mediated Observer

### Essential mechanism

For Observer to be defensible, this collaboration must provide an identifiable notification source, a subscribed receiver and a mechanism that delivers updates to that receiver without the publisher directly invoking its UI-update methods.

The application supplies all the necessary configuration and invocation points. The checked Turbo Rails 2.0.23 source supplies the missing subscription and dispatch infrastructure.

### A. Application publishers

Publisher path 1: `InboxItem` changes

`app/models/inbox_item.rb:1–5`

```
class InboxItem < ApplicationRecord
  belongs_to :trip
  belongs_to :reviewed_by, class_name: "User", optional: true

  broadcasts_refreshes_to :trip
end
```

The meaningful line is:

```
broadcasts_refreshes_to :trip
```

In Turbo Rails 2.0.23, this declaration registers an `after_commit` callback that schedules a refresh broadcast to the specified streamable, which here resolves to the `InboxItem`'s associated trip.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



Thus, the model does not directly find a browser and refresh it. It requests a notification through Turbo's infrastructure.

Publisher path 2: Geocoding completion

`app/jobs/geocode_trip_items_job.rb:4–21`

After processing the requested itinerary items, the job invokes:

```
Turbo::StreamsChannel.broadcast_refresh_to(trip)
```

The framework constructs a Turbo Stream refresh action and publishes it to the stream identified by the supplied trip.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



These are two triggers for the same kind of trip-scoped notification.

### B. Application subscribers

The trip page declares:

`app/views/trips/show.html.erb:2`

```
<%= turbo_stream_from @trip %>
```

The inbox index declares the same subscription:

`app/views/inbox_items/index.html.erb:1`

```
<%= turbo_stream_from @trip %>
```

The views do not call the publishing model or geocoding job.

Instead, each rendered page independently subscribes to its trip's stream.

### Why Turbo has slightly weaker application ownership

The mail logging instance includes a concrete observer method written by DaPlanStan:

`MailLogger.delivered_email(message)`, `config/initializers/mail_logger.rb:2–4`.

The Turbo collaboration does not implement a custom browser observer class or notification callback. Instead, its concrete subscriber is provided by Turbo, and DaPlanStan activates it through the view helper.

Nevertheless, the application explicitly defines both sides of the communication:

- It chooses the trip as the notification subject.
- It declares model-driven and job-driven broadcasts.
- It renders pages subscribing to that trip's stream.
- The versioned framework implementation connects those publishers and subscribers.

Under the same acceptance rule used for the mail Observer—framework-mediated collaborations are eligible when the application explicitly participates in a documented Observer mechanism—this is sufficient.

Final decision: CONFIRMED as a framework-mediated Observer instance.

It should not be described as a custom GoF Observer implementation written entirely by DaPlanStan.

## 9. Runtime questions — separate from pattern identification

The confirmed static mechanism does not prove every notification produces the desired UI outcome.

The following remain appropriate for runtime testing:

- Whether an active trip page and inbox page both receive refresh actions after an `InboxItem` commit.
- Whether a geocoding job's explicit broadcast refreshes the subscribed trip page.
- Whether `data-turbo-permanent` preserves an outdated Leaflet map or marker collection despite a successful page refresh.
- Whether repeated or closely spaced broadcasts are debounced as expected.
- Whether timeline-to-map events behave correctly when desktop and mobile timelines are both present.
- Whether listeners reconnect correctly after navigation and Turbo morphing.

These do not need to block the static identification of the Turbo Observer collaboration. They should be recorded as functional and integration-verification questions.

**Candidate 1: Itinerary Timeline–Map Event Coordination**

- Proposed pattern: Observer
- Final decision: REJECTED
