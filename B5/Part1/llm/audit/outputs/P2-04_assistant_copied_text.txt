## 1. Main finding: Parsing and creating trip records are separate operations

The source establishes three important boundaries:

1. Email intake: `TripMailbox` identifies the trip, checks the sender and creates an `InboxItem`.
2. AI extraction: `ParseInboxItemJob` sends email information to Anthropic and saves the resulting structured data in the existing `InboxItem`.
3. Record creation: `InboxItemsController#update` separately invokes application methods that create or link `TripItem` and `Expense` records when the user selects confirmation or relinking.

Parsing an email does not itself create itinerary items or expenses. This distinction is directly supported by `ParseInboxItemJob#perform` at lines 99–112 and `InboxItemsController#update` at lines 16–35.&#x20;



An approved sender allows an email to proceed to parsing, but approval is not the same as confirmation of its extracted travel information.

## 2. How incoming email enters and is assigned to a trip

The application's mailbox entry point is:

`app/mailboxes/application_mailbox.rb:1–3`

```
class ApplicationMailbox < ActionMailbox::Base
  routing(all: :trip)
end
```

The `routing(all: :trip)` declaration tells Rails Action Mailbox to route incoming messages to `TripMailbox`. It does not itself identify a particular trip.

At `app/mailboxes/trip_mailbox.rb:2–9`, `TripMailbox#process` extracts the first recipient address, normalizes it to lowercase and removes surrounding whitespace:

```
to_address = mail.to&.first.to_s.downcase.strip
trip = Trip.find_by(inbound_email: to_address)
```

When no matching trip exists, the method logs a warning and returns. It does not create an `InboxItem` or enqueue parsing in that branch.

### Where the recipient address comes from

`app/models/trip.rb:14–19` validates the inbound address and registers a callback to generate one when creating a trip.

`Trip#build_inbound_email`, lines 35–37, constructs an address from the parameterized trip title, a random hexadecimal suffix and the configured email domain.

The mailbox uses the address stored on `Trip`, not the trip title or message subject, to identify the destination.

Important limitation: The code checks the first address in `mail.to`. It does not iterate over every recipient to locate a matching trip.

These relationships are application-written behavior operating on Rails and Action Mailbox objects.&#x20;



## 3. What `TripMailbox` decides and stores

After locating the trip, `TripMailbox#process` checks whether the sender is recognized.

At `app/mailboxes/trip_mailbox.rb:11–14`, the sender is approved if any one of these conditions is true:

- Their normalized email is recorded in the trip's `approved_senders` association.
- Their email matches a `Traveler` associated with the trip through `TripMember`.
- Their email matches the `User` account associated with a trip member's traveler record.

These are three application-defined database checks, not an Anthropic decision.

At lines 16–24, the mailbox creates an `InboxItem` using `trip.inbox_items.create!`.

| Stored field    | Source of value                       |
| --------------- | ------------------------------------- |
| `trip_id`       | The matched `Trip` association        |
| `from_email`    | First sender address, normalized      |
| `from_name`     | Sender's display name, when available |
| `subject`       | Email subject, or `"(no subject)"`    |
| `raw_body`      | Decoded text extracted from the email |
| `raw_html`      | Decoded HTML content, when available  |
| `received_at`   | Email date, otherwise `Time.current`  |
| `sender_status` | `approved` or `pending_approval`      |

For multipart email, `extract_text_body` prefers the decoded text part, then falls back to `mail.decoded`. `extract_html_body` attempts to extract the decoded HTML part. Both methods have exception fallbacks.

The source references are `app/mailboxes/trip_mailbox.rb:16–59`.&#x20;

### What happens after the inbox record is created?

Recognized sender

`ParseInboxItemJob.perform_later(inbox_item.id)` is called at `app/mailboxes/trip_mailbox.rb:26–27`.

Unrecognized sender

No initial parsing job is enqueued. `notify_owners_of_pending_sender` sends a notification to each owner through `TripMailer.pending_sender_notification(...).deliver_later`, at `app/mailboxes/trip_mailbox.rb:55–59`.

The mailbox therefore coordinates intake, trip lookup, approval checking, inbox persistence and the initial next action. It does not itself extract structured travel details or create destination trip records.

## 4. Exactly what `ParseInboxItemJob` does

Primary source: `app/jobs/parse_inbox_item_job.rb:1–140`

The job inherits from `ApplicationJob` and declares `queue_as :default`. It also declares a Rails `retry_on StandardError` policy, although its own broad rescue handler is relevant to whether that policy would actually run.

Its implemented sequence is:

1. Find the inbox record

   `InboxItem.find_by(id: inbox_item_id)` returns the stored email. If no record exists, `perform` returns.
2. Construct the prompt

   `build_prompt` uses the trip title, sender name/email, subject and `raw_body` truncated to 4,000 characters. It does not use `raw_html` or attachments.
3. Call Anthropic

   `parse_with_anthropic` creates an `Anthropic::Client` and requests a message from `claude-haiku-4-5-20251001`, with a system prompt, a tool schema and the constructed email prompt.
4. Extract the structured response

   The application searches the response content for the first block whose type is `:tool_use`. It returns the block's input as a string-keyed hash, or `{}` when no such block exists.
5. Save extraction results

   `inbox_item.update!(parsed_data: data, parse_status: :parsed)` saves the extracted structure through `InboxItem#parsed_data=`.
6. Handle errors

   On a rescued exception, it logs the failure and attempts to set `parse_status: :failed`.

The system prompt instructs the model to extract clearly stated information. The application-supplied tool schema defines four main output categories:

| Structured key    | Expected content                               |
| ----------------- | ---------------------------------------------- |
| `travel_legs`     | Flights, trains, ferries, buses and cars       |
| `accommodations`  | Stays, check-in/out dates and amounts          |
| `bookings`        | Tours, restaurants, tickets and other bookings |
| `shortlist_items` | Suggested places and activities                |

These are data returned to the application. The `record_travel_data` tool declaration does not itself call `TripItem.create!` or `Expense.create!`.

One important distinction: the code sets `parse_status: :parsed` even if `parse_with_anthropic` returns an empty hash. It has no visible semantic validation requiring the result to contain a usable travel record.

### Anthropic versus DaPlanStan responsibility

| Anthropic/provider                                                | DaPlanStan application                                                  |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Processes the submitted prompt and model instructions             | Selects the model and constructs the prompt                             |
| Produces a structured tool-use response when successful           | Defines the expected tool input schema                                  |
| Supplies generated travel-information values                      | Extracts the tool input and saves it to `InboxItem`                     |
| Does not directly operate on the Rails database through this call | Later interprets the saved values and creates or updates domain records |

Rails Active Job handles background execution, while DaPlanStan supplies the `perform` implementation and record updates.

The precise job logic is at `app/jobs/parse_inbox_item_job.rb:99–139`; the tool schema is at lines 20–97.&#x20;

### A. What happens when the user selects Add to trip?

The action is initiated from `app/views/inbox_items/show.html.erb:53–62` and handled by `InboxItemsController#update`.

Under the `confirm` branch, the controller first calls `confirm_and_create_items!` and then records `review_status: :confirmed`, `reviewed_by` and `reviewed_at`.

Within `InboxItem#confirm_and_create_items!`, lines 34–58:

1. It invokes `fill_missing_links!`.
2. It reads the saved `parsed_data`.
3. If that data is not a Hash, it returns.
4. It processes `shortlist_items` using a category mapping.
5. It skips entries with blank names or names already found among the trip's itinerary items.
6. It creates new `TripItem` records with `status: :idea` for accepted shortlist entries.

There are separate rescue handlers for individual shortlist creation errors.

### C. How different extracted categories are handled

| Category        | Processing                                                                                                                             | Expense creation conditions                                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Travel legs     | Converts transport modes to itinerary kinds; constructs names and destination addresses; detects a particular two-leg return-trip case | If a payer exists, selects the first leg with a price and creates an expense only when that selected item has no expense |
| Accommodations  | Creates or links stays with dates, address, amount and confirmation number                                                             | Payer exists, price is present and the item has no expense                                                               |
| Other bookings  | Maps booking type to an itinerary kind and creates or links the booking                                                                | Payer exists, price is present and the item has no expense                                                               |
| Shortlist ideas | Handled separately by `confirm_and_create_items!`                                                                                      | No corresponding expense creation in that method                                                                         |

The code for travel legs is at `app/models/inbox_item.rb:101–138`, accommodations at lines 140–158 and bookings at lines 160–187.&#x20;

The shared `build_expense` method at lines 191–207 uses `trip.expenses.create!`, linking the `Expense` to the `TripItem`, `InboxItem`, reviewer and identified payer. It stores an amount, currency, description, category, date, booking source and confirmation timestamp.

Important condition: An extracted amount alone is insufficient to create an expense. The application must identify a `paid_by_traveler`, and the relevant expense must not already exist according to its lookup.

The source comments describe the linking routine as idempotent. Its name matching and expense-existence checks support that intention, but concurrency and duplicate behavior have not been independently tested.

## 6. How approved-sender management affects processing

`ApprovedSendersController` provides separate actions for adding and removing sender approvals.

Approval: `app/controllers/approved_senders_controller.rb:5–20`

The controller optionally looks up an existing `InboxItem` using `params[:inbox_item_id]`, then creates an `ApprovedSender` for the trip containing the submitted email, approving user and approval timestamp.

When the request identifies an inbox item, the controller also changes that particular item's `sender_status` to `approved` and enqueues `ParseInboxItemJob`.

If no inbox item ID is supplied, it adds the sender to the approved list but does not automatically enqueue jobs for every previously received email from that address.

Removal: `app/controllers/approved_senders_controller.rb:22–26`

The controller destroys the selected approved-sender entry. It does not retrospectively change the status of existing inbox records.

Validation: `app/models/approved_sender.rb:1–6`

The model requires an email, requires `approved_at` and enforces trip-scoped email uniqueness.

The route for these controller actions is declared at `config/routes.rb:45`. The controller uses `current_user.trips.find(params[:trip_id])` at lines 30–32; there is no separate owner-role check in the inspected action.

### A source-level inconsistency worth flagging

In `app/views/inbox_items/show.html.erb:53–75`, the conditional order is:

```
<% if @item.pending_review? %>
  ...
<% elsif @item.pending_approval? %>
  ...
```

New inbox records have `review_status: pending_review` by default, including those from unrecognized senders. Therefore, the first branch appears to take precedence over the approval branch for those new records.

Meanwhile, `InboxItemsController#update` does not check `sender_status` or `parse_status` before executing the `confirm` or `relink` actions.

This creates a possible approval/review gating inconsistency: the mailbox delays automatic parsing for unknown senders, but the review controller does not independently enforce that gate. A real user-interaction test is required before recording the full impact as a verified defect.&#x20;



It is relevant to explaining control flow, but it is not by itself evidence of a design pattern.

## 10. Pattern candidates worth investigating

No GoF classification is established by this source trace. There are three narrower hypotheses worth retaining for skeptical review.

Candidate A — GRASP Information Expert

UNCONFIRMED

Why it might fit: `InboxItem` owns the parsed-data interface, belongs to the relevant trip, and contains methods that use this information to create and link related records (`app/models/inbox_item.rb:19–25, 34–207`).

False-positive risk: These are responsibilities placed on an Active Record model. That could simply represent model-centric application code, not a deliberate responsibility allocation justified by GRASP Information Expert. The method also reaches across `Trip`, `TripItem`, `Expense`, `Traveler` and `User` data.

Origin: Mainly application-owned business logic, supported by Active Record.

Verification focus: Determine whether `InboxItem` genuinely holds the information needed to justify ownership of these operations, or whether it is only coordinating responsibilities belonging to several other entities.

Candidate B — GRASP Controller

UNCONFIRMED

Why it might fit: `TripMailbox#process` acts as a handler for an inbound system event. It coordinates lookup, authorization-related checks, inbox-record creation and delegation to background processing or notification.

False-positive risk: Receiving an event in a Rails mailbox is a framework convention. A method that coordinates several calls is not automatically a meaningful GRASP Controller assignment.

Origin: Application-owned event handling within Rails-provided mailbox infrastructure.

Verification focus: Evaluate the division of responsibility between `ApplicationMailbox`, `TripMailbox`, `InboxItem` and the parsing job against the GRASP Controller definition, not merely their names or inheritance.

Candidate C — Observer-like Turbo refresh

UNCONFIRMED

Why it might fit: `InboxItem` declares `broadcasts_refreshes_to :trip` at `app/models/inbox_item.rb:5`, and `app/views/inbox_items/index.html.erb:1` declares `turbo_stream_from @trip`.

Together, these are evidence of a framework-configured model-change notification and stream subscription relationship.

False-positive risk: The actual observer/subscription machinery is implemented by Turbo and Rails. The application does not visibly define its own observer interface, registry or notification implementation.

Origin: Predominantly framework-provided, with application-defined declarations.

Verification focus: Trace actual subscription and broadcast behavior, then determine whether it qualifies under the faculty's framework-idiom category. This may overlap with the same trip-stream infrastructure observed during the geocoding investigation; it must not automatically become a separate counted pattern instance.

The use of `ParseInboxItemJob`, Anthropic tool input, lookup methods and `find_or_upsert` does not currently justify proposing Command, Chain of Responsibility, Strategy, Adapter or Factory as additional candidates. Those labels would require defining mechanisms that this inspection has not demonstrated.

## 11. Strongest non-pattern explanation

The complete workflow is best described as:

A Rails Action Mailbox intake pipeline with a sender-approval gate, asynchronous AI-based data extraction, persisted intermediate results and user-triggered domain-record linking.

The application uses straightforward procedural decisions, Active Record associations, background jobs and methods on its `InboxItem` model. Much of the framework behavior is declarative.

This explanation accounts for the collaboration without inventing interfaces, interchangeable implementations or design-pattern participants.

## 12. Remaining verification questions

The static trace is complete enough to support candidate review, but the following points remain unresolved:

1. Inbound transport: Has Postmark successfully delivered a real email through the configured Action Mailbox ingress into `TripMailbox`?
2. Approval enforcement: Does the inbox view's conditional order cause an unknown sender's email to display confirmation controls before approval, and are there any runtime protections not visible in the inspected application methods?
3. Parsing execution: Does the job return a usable Anthropic tool result for representative emails? Its rescue handler also needs checking against Rails' configured retry behavior.
4. Record linking: Do repeated or concurrent confirmation requests remain duplicate-safe? The source's name matching and expense-existence checks demonstrate an intention, not a tested guarantee.
5. Partial failures: What happens when individual item or expense creation fails but the controller subsequently marks the inbox record confirmed? No transaction covering the entire operation is visible.
6. Attachments: Are inbound attachments preserved through another framework mechanism? The inspected mailbox method does not copy them to `InboxItem`.
7. Turbo updates: Are subscribed browser clients actually refreshed following `InboxItem` changes, and should that framework behavior qualify for the inventory?
8. Human verification: A reviewer still needs to assess the GRASP responsibility assignments and decide whether they are meaningful enough to be counted.
