# DaPlanStan — External Integrations and Account Identity

Source Investigation 05 · Original uploaded ZIP · Static source analysis

Pattern classifications unconfirmed

## 1. Overview of the source findings

The three integration areas have different responsibilities.

- Cover images: DaPlanStan constructs its own HTTP request to Pexels, interprets the JSON response and stores the selected image URL on `Trip`.
- OAuth authentication: OmniAuth handles provider-specific authentication. DaPlanStan receives normalized authentication information and implements user lookup, identity linking, account provisioning, invitation acceptance and session creation.
- Outbound email: DaPlanStan selects recipients and constructs invitation or notification messages. Rails Action Mailer and the configured delivery service handle message processing and transport.

The source also contains an important supporting component that was not in the initial file list: `config/initializers/mail_logger.rb`. It registers an application-defined delivery observer with Action Mailer. That behavior is relevant to candidate discovery, but it must be evaluated separately from ordinary outbound mail delivery.

The investigation below distinguishes application-written coordination from Rails conventions and third-party APIs before considering pattern classifications.

## 2. Cover-image retrieval

### 2.1 Entry points

The same `FetchTripCoverImageJob` is invoked from three actions in `TripsController`.

| Trigger                                                  | Source                                      | Invocation                |
| -------------------------------------------------------- | ------------------------------------------- | ------------------------- |
| Successful trip creation                                 | `app/controllers/trips_controller.rb:35–48` | `perform_later(@trip.id)` |
| Successful trip update when a title parameter is present | `app/controllers/trips_controller.rb:68–75` | `perform_later(@trip.id)` |
| Explicit Fetch from Pexels action                        | `app/controllers/trips_controller.rb:87–92` | `perform_now(@trip.id)`   |

The manual refresh is initiated by a POST form in `app/views/trips/cover.html.erb:65–76`, corresponding to `config/routes.rb:27–28`.

Important distinction: Manual refresh invokes `perform_now` synchronously, whereas creation and update call `perform_later`.

Additionally, the update condition tests whether `trip_params[:title]` is present, not whether the title actually changed. Therefore, a successful request containing an unchanged but nonblank title can still enqueue a new image lookup.&#x20;

### 2.3 What the job actually does

`FetchTripCoverImageJob#perform`, `app/jobs/fetch_trip_cover_image_job.rb:4–32`, implements the following steps.

Locate the trip. It retrieves `Trip.find_by(id: trip_id)` and returns if no matching record exists.

Check configuration. It reads `ENV["PEXELS_API_KEY"]`. If missing or blank, it logs that information and returns.

Construct a search. It removes four-digit years from the trip title, compresses whitespace and appends `travel landscape`.

For example, a trip titled `Japan 2026` would produce a query based on `Japan travel landscape`.

Construct the request. The application creates a GET request to:

`https://api.pexels.com/v1/search`

It supplies the URL parameters `query`, `per_page=1` and `orientation=landscape`, with the API key placed in the `Authorization` header.

Process the response. On an HTTP success response, it parses the JSON and retrieves:

```
data.dig("photos", 0, "src", "large2x")
```

Persist the result. If an image URL exists, the job calls:

```
trip.update_columns(cover_image_url: image_url)
```

The job rescues errors and logs warnings. It does not propagate its rescued failures to the controller through a custom result object.&#x20;



### 2.4 Image storage versus image display

The job stores the returned URL, not downloaded image bytes.

`Trip` also declares an Active Storage cover attachment at `app/models/trip.rb:2`.

The application's `trip_cover_src` helper prefers an uploaded Active Storage image over the Pexels URL:

```
def trip_cover_src(trip)
  return url_for(trip.cover_image) if trip.cover_image.attached?
  trip.cover_image_url.presence
end
```

Source: `app/helpers/application_helper.rb:44–47`.

A user can separately upload a custom cover through `TripsController#update_cover`, which attaches the upload and clears the Pexels URL.

The manual refresh operation does the reverse: it purges the uploaded image, clears the URL and invokes the Pexels job synchronously.

### 2.5 Responsibility allocation

| Participant              | Responsibility                                                 |
| ------------------------ | -------------------------------------------------------------- |
| `TripsController`        | Decide when cover retrieval is needed                          |
| `FetchTripCoverImageJob` | Prepare request, invoke Pexels and interpret result            |
| `Trip`                   | Hold the image URL and optional attachment                     |
| Active Record            | Perform persistence                                            |
| Active Job               | Provide asynchronous/synchronous job invocation infrastructure |
| Ruby `Net::HTTP`         | Perform HTTP transport                                         |
| Pexels                   | Search its image catalogue and return image metadata           |
| Active Storage           | Store manually uploaded cover attachments                      |

The application does not use a Pexels-specific SDK in this method. It constructs the HTTP request directly using Ruby libraries.

### 2.6 Collaboration boundary

This image-retrieval operation was already encountered as a supporting participant in the previously reviewed `Trip Creation Coordination` instance.

The additional edit and manual-refresh callers do not, by themselves, create new pattern instances.

The actual Pexels integration is a direct HTTP lookup with response processing and persistence. No interchangeable provider implementation or incompatible-interface translation has been established.

Preliminary conclusion: The cover-image retrieval flow is independently understandable as external API integration. No genuinely new pattern candidate is warranted from this job alone.

## 3. OAuth sign-in and identity linking

### 3.1 Provider configuration and entry

`config/initializers/omniauth.rb:1–16` registers two OmniAuth providers:

| Provider | Configuration                                        |
| -------- | ---------------------------------------------------- |
| Google   | `:google_oauth2`, client ID and client secret        |
| Apple    | `:apple`, client ID, team ID, key ID and private key |

The initializer also specifies that OAuth requests begin using POST.

The application routes:

- `GET /auth/:provider/callback` to `SessionsController#create`.
- `GET /auth/failure` to `SessionsController#failure`.
- `DELETE /auth/sign_out` to `SessionsController#destroy`.

These routes are at `config/routes.rb:12–15`, within the `whats.` hostname constraint.

The actual provider authentication protocol is implemented by OmniAuth and its provider integrations, not by `SessionsController`.&#x20;



### Important provider distinction

Although both Google and Apple are configured, the inspected sign-in interfaces contain Google-specific forms:

- `app/views/home/app.html.erb:50–68`
- `app/views/invites/accept.html.erb:19–31`
- `app/views/layouts/_navbar.html.erb:68–71`

No corresponding Apple sign-in button was found in the inspected application views.

Therefore, the source establishes Apple provider configuration but does not establish a working Apple sign-in user journey.

### 3.2 How authenticated provider data reaches the application

`SessionsController#create`, `app/controllers/sessions_controller.rb:4–40`, begins with:

```
auth = request.env["omniauth.auth"]
```

The controller expects the normalized OmniAuth authentication result to expose fields such as:

- `auth.provider`
- `auth.uid`
- `auth.info.email`
- `auth.info.name`
- `auth.info.image`
- `auth.credentials.token`

DaPlanStan reads these fields. It does not itself implement Google's or Apple's token exchange or provider-specific response parsing in this controller.

### 3.4 Existing identity lookup

At `app/controllers/sessions_controller.rb:7–11`:

```
identity = UserIdentity.find_by(
  provider: auth.provider,
  provider_uid: auth.uid
)
```

When an identity exists, the controller uses `identity.user` and updates the avatar URL if the provider supplies an image.

It does not repeat the user-by-email lookup for this branch.

`UserIdentity`, at `app/models/user_identity.rb:1–8`, belongs to `User`, validates the provider and UID and declares encryption for `access_token`.

The database defines a unique index on `(provider, provider_uid)` at `db/structure.sql:25`.

### 3.5 New provider identity linking

If the exact provider identity does not exist, the controller calls:

```
user = User.find_or_initialize_by(email: auth.info.email)
```

This has two possible outcomes.

Existing user email: The controller reuses the matching `User`, fills a missing name if necessary, updates the avatar and saves.

New user email: It initializes and saves a new `User` with the available provider profile information.

In both cases, the controller then creates a new associated `UserIdentity`, recording the provider, UID, provider email and access token.

That is the key identity-linking rule: provider-and-UID lookup takes precedence, and email is used when introducing a provider identity not already linked.

There is no separate application-level Google-specific or Apple-specific account-linking algorithm in this method.&#x20;



### 3.6 Session establishment and pending invitations

Once a user has been resolved, the controller writes:

```
session[:user_id] = user.id
```

`ApplicationController#current_user`, at `app/controllers/application_controller.rb:14–16`, subsequently resolves the session ID to a `User` record.

Next, `SessionsController#create:28–31` retrieves all `Traveler` records with the signed-in user's email and no associated user:

```
pending_travelers =
  Traveler.where(user_id: nil, email: user.email).to_a

pending_travelers.each { |t| t.accept!(user) }
```

`Traveler#accept!`, `app/models/traveler.rb:26–28`, associates the traveler with the user and records `invite_accepted_at`.

This links previously created email-only traveler records to the newly authenticated identity.

It is not equivalent to assigning a new trip membership. Those memberships were already established by the membership-management workflow.

### 3.7 Account provisioning and invite gate

After processing pending travelers, the controller checks:

| Condition                                       | Application decision                   |
| ----------------------------------------------- | -------------------------------------- |
| User already owns an account                    | Redirect to trips                      |
| User has traveler profiles but no owned account | Redirect to trips as an invited member |
| Neither condition holds                         | Invoke `provision_account_or_gate`     |

`SessionsController#provision_account_or_gate`, lines 54–76, handles first-time independent account access.

When `OPEN_SIGNUP=true`, it creates an account without requiring a beta-invite token.

Otherwise it consumes `session[:invite_token]` and searches for the corresponding `Invite`.

A valid invite must be usable and match the signed-in user's email, unless the invite is unrestricted.

If valid, the controller creates an account, marks the invite used and redirects to trips. Otherwise, it clears `session[:user_id]` and redirects to the waitlist.

`create_account_for`, lines 78–81, performs:

```
account = Account.create!(owner: user, name: user.name)

account.travelers.create!(
  user: user,
  name: user.name,
  email: user.email,
  avatar_url: user.avatar_url
)
```

The invite's predicates are implemented by `Invite#usable?` and `#email_matches?`, at `app/models/invite.rb:12–17`.

Important: An invitation to join a trip and an invite to create a new account are not identical records or workflows. A user already linked to a traveler profile can access trips without receiving a separate owned account.

The key source locations are `app/controllers/sessions_controller.rb:26–81` and `app/models/traveler.rb:18–28`. &#x20;



### 3.8 Application decisions versus provider behavior

| Concern                | DaPlanStan application                                            | OmniAuth / Rails                                        |
| ---------------------- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| Provider configuration | Register Google and Apple with credentials                        | Provide provider strategies and OAuth protocol handling |
| Provider response      | Read `omniauth.auth`                                              | Produce the normalized authentication result            |
| Identity lookup        | Match provider/UID first, then email when necessary               | Execute Active Record queries                           |
| Identity linking       | Associate a new `UserIdentity` with the selected user             | Persist associations and encrypt configured attributes  |
| Signed-in session      | Assign user ID and choose redirect                                | Manage HTTP session infrastructure                      |
| Invitation acceptance  | Find pending travelers by email and call `accept!`                | Persist traveler associations                           |
| Account eligibility    | Check owned account, memberships, open signup and invite validity | Supply persistence and controller mechanisms            |

The application uses a common callback for both configured providers. No application-defined interchangeable provider-specific algorithms are visible.

Preliminary conclusion: This is primarily OmniAuth-backed authentication with application-owned identity resolution and account-provisioning rules. The account-linking behavior is meaningful, but merely configuring Google and Apple does not establish an application-implemented Strategy, Adapter or Factory.

## 4. Outbound mail

### 4.1 Types of outgoing email

The inspected application contains three relevant mailer actions.

| Email                               | Originating call site                                         | Mailer                                   |
| ----------------------------------- | ------------------------------------------------------------- | ---------------------------------------- |
| Account traveler invitation         | `TravelersController#create`, lines 18–26                     | `InvitationMailer#invite`                |
| Trip membership invitation          | `TripMembersController#resolve_and_add_by_email`, lines 46–65 | `InvitationMailer#invite_to_trip`        |
| Unknown inbound sender notification | `TripMailbox#notify_owners_of_pending_sender`, lines 55–60    | `TripMailer#pending_sender_notification` |

They share Action Mailer infrastructure but have different application-defined recipient decisions and message content.&#x20;



### 4.2 Account traveler invitation

`TravelersController#create` handles addition of a traveler to the current account.

When an email is provided, it checks whether the address belongs to the acting user or an existing account traveler, then looks up a registered `User`.

For an existing user, it creates a linked `Traveler`. Otherwise, it creates an email-only traveler.

The controller then invokes:

```
InvitationMailer.invite(current_user, email).deliver_later
```

`InvitationMailer#invite`, `app/mailers/invitation_mailer.rb:2–6`, stores the inviter and sign-in URL for the template, then sets the recipient and subject.

The template at `app/views/invitation_mailer/invite.text.erb:1–12` instructs the recipient to sign in to DaPlanStan.

This path was encountered during earlier membership analysis, but the account-level invitation caller is distinct from the trip-specific invitation caller.

### 4.3 Trip membership invitation

`TripMembersController#resolve_and_add_by_email` looks up or creates the relevant `Traveler`.

If the supplied email does not correspond to an existing account traveler or registered user, the controller creates an email-only traveler and calls:

```
InvitationMailer.invite_to_trip(
  account.owner, email, @trip
).deliver_later
```

`InvitationMailer#invite_to_trip`, lines 8–13, constructs a trip-specific invitation.

The template at `app/views/invitation_mailer/invite_to_trip.text.erb:1–9` includes the inviter's name, trip title and application sign-in URL.

The source uses `account.owner` as the displayed inviter even when a planner performs the membership-management action. It does not pass the acting planner as the inviter.

This is an application decision, not Action Mailer behavior.

### 4.4 Unknown-sender notification

The inbound-email workflow previously established that `TripMailbox#process` creates an `InboxItem` even when its sender is not approved.

The unapproved branch calls `notify_owners_of_pending_sender`.

That method:

1. Finds members of the relevant trip with `role: :owner`.
2. Loads the associated traveler information.
3. Calls `TripMailer.pending_sender_notification(member, inbox_item).deliver_later` for each owner.

`TripMailer#pending_sender_notification`, `app/mailers/trip_mailer.rb:2–10`, uses the trip member's `traveler.display_email` as recipient and constructs a subject identifying an unknown sender.

Its template, `app/views/trip_mailer/pending_sender_notification.text.erb:1–13`, includes the trip title, sender name/email, subject, receipt date and an approval-related URL.

This is the same pending-sender notification collaboration already traced during inbound-email intake. It must not be counted again as a new GRASP Controller instance.&#x20;



### 4.5 Mail delivery configuration

`ApplicationMailer`, `app/mailers/application_mailer.rb:1–5`, specifies default sender and reply-to addresses from environment variables and uses the `mailer` layout.

Delivery is environment-dependent:

| Environment                        | Configured behavior                          |
| ---------------------------------- | -------------------------------------------- |
| Production                         | Postmark delivery using `POSTMARK_API_TOKEN` |
| Development with Postmark token    | Postmark delivery                            |
| Development without Postmark token | Write email output to `tmp/mails`            |

The relevant configuration is `config/environments/production.rb:63–69` and `config/environments/development.rb:40–50`.

`deliver_later` is supplied by Rails Action Mailer/Active Job, while Postmark supplies external delivery when configured. DaPlanStan's mailers do not implement the SMTP or Postmark transport protocol.&#x20;



### 4.6 Additional delivery logging

`config/initializers/mail_logger.rb:1–14` contains an explicit registration:

```

module MailLogger
  def self.delivered_email(message)
    Rails.logger.info(
      "[Mailer] Sent '#{message.subject}' to #{Array(message.to).join(', ')}"
    )
  end
end

ActionMailer::Base.register_observer(MailLogger)

```

This is different from the standard mailer methods above.

DaPlanStan defines the `MailLogger` module and registers it with Rails' Action Mailer notification machinery. The logger receives a mail message and records its subject and recipients.

The framework supplies the delivery notification and observer registration mechanism. DaPlanStan supplies the registered callback implementation.

This is a concrete source-defined collaboration worth considering during the candidate stage, although actual invocation has not been runtime-verified.&#x20;

## 8. Strongest non-pattern explanation

The overall source area is best explained as:

Conventional Rails integration with external services, together with application-owned identity and notification rules.

- Google and Apple sign-in are configured through OmniAuth, followed by application-defined identity and account operations.

This explanation covers the observed behavior without inventing provider strategies, adapter hierarchies or factory objects.

Only the sign-in responsibility assignment and explicit delivery observer registration merit further pattern verification.
