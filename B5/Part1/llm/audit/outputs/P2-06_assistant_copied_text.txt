# DaPlanStan — Trip Creation, Membership and Permission Investigation

Patterns unconfirmed

Source Investigation 03 · Original uploaded ZIP

## 1. Initial source findings

The implementation separates responsibilities across Rails controllers and Active Record models. Three important facts emerge from the code:

1. Trip creation and owner-membership creation are coordinated by `TripsController#create`, not by a single `Trip` model method. The controller saves the trip, creates its first `TripMember`, and enqueues cover-image retrieval.
2. Membership roles are stored as values on `TripMember`. No application-defined interchangeable role objects or role-specific classes were identified in this source area.
3. Permissions are enforced differently across controllers. Some actions require owner or planner membership, others require only that the user belongs to the trip.

The last distinction matters: DaPlanStan does not implement one uniform, centralized authorization policy.

### Step A — The request enters the controller

`config/routes.rb:21` declares `resources :trips` within the application's host constraint at lines 6–7. This provides the normal RESTful POST route to `TripsController#create`.

The controller registers `authenticate_user!` at line 2. The request must be associated with a signed-in user before trip creation proceeds.

At `app/controllers/trips_controller.rb:35–39`, the application constructs the trip and assigns its creator and account:

```

@trip = Trip.new(trip_params)
@trip.created_by = current_user
@trip.account = current_account

```

The strong parameters at lines 129–131 permit only `title`, `description`, `start_date` and `end_date` from the submitted trip form.

`created_by` and `account` are assigned by the application rather than taken from those form parameters.&#x20;



### Step B — The trip is saved

`TripsController#create` calls `@trip.save` at line 40.

`Trip`, defined in `app/models/trip.rb:1–19`, has relationships to its account, creator, members, travelers, itinerary items, expenses and other trip resources.

The model validates the title, start date, end date and inbound email address. It also declares:

```
before_validation :generate_inbound_email,
  on: :create,
  if: -> { inbound_email.blank? }
```

`Trip#generate_inbound_email` and `#build_inbound_email`, lines 31–37, generate a trip-specific address using the title, a random hexadecimal suffix and the configured email domain.

The application defines the address-generation logic. Rails provides validation, callback invocation and persistence infrastructure.&#x20;



If saving fails, the controller renders the new-trip form with an unprocessable-entity response.

### Step C — The initial owner membership is created

Once the trip is saved, the controller executes:

```

owner_traveler = current_account.owner_traveler
@trip.trip_members.create!(
  traveler: owner_traveler,
  role: :owner,
  joined_at: Time.current
)

```

`Account#owner_traveler`, `app/models/account.rb:9–11`, searches the account's travelers for the record linked to the account owner.

The source also shows how that record is normally provisioned. `SessionsController#create_account_for`, `app/controllers/sessions_controller.rb:78–81`, creates an `Account` and then its owner-linked `Traveler`.

These are distinct identities:

- `User` is the signed-in person.
- `Account` groups that person's owned travel resources.
- `Traveler` represents a participant, optionally linked to a `User`.
- `TripMember` establishes the traveler's membership and role in a particular trip.

The controller creates the membership through the new trip's Active Record association. It explicitly assigns `owner`, rather than relying on the database's default membership role.&#x20;



### Step D — Cover-image processing is requested

At `app/controllers/trips_controller.rb:43`:

```
FetchTripCoverImageJob.perform_later(@trip.id)
```

The job implementation is application-written. It loads the trip, checks for a configured Pexels API key, constructs a search from the title, requests a landscape image and stores the returned image URL when available.

Important details from `app/jobs/fetch_trip_cover_image_job.rb:4–30`:

- If the trip is missing, the job returns.
- If the API key is absent, it logs a message and returns.
- If the HTTP response is unsuccessful, it logs a warning and returns.
- It uses the first returned photograph's `large2x` URL.
- It catches exceptions and logs warnings.

The controller does not wait for this external lookup before redirecting. Successful image retrieval was not established through runtime testing.&#x20;



### Where creation responsibility is located

| Responsibility                                  | Actual owner                                            |
| ----------------------------------------------- | ------------------------------------------------------- |
| Handle trip-creation request                    | `TripsController#create`                                |
| Construct trip and assign account/creator       | `TripsController#create`                                |
| Validate trip data and generate inbound address | `Trip`                                                  |
| Find the account owner's traveler record        | `Account#owner_traveler`                                |
| Create the first membership                     | `TripsController#create` through `trip_members.create!` |
| Persist records and associations                | Active Record                                           |
| Request cover-image work                        | `TripsController#create`                                |
| Perform cover-image retrieval                   | `FetchTripCoverImageJob`                                |

The business operation is therefore coordinated across multiple objects, with the controller responsible for sequencing them.

Important limitation: The trip save and owner-membership creation are not visibly enclosed in one application-level database transaction. If membership creation raises after a successful trip save, the source does not establish an automatic rollback of the already-saved trip.

### C. How invited travelers gain access

The relevant supporting code is:

- `Traveler#accept!` — `app/models/traveler.rb:26–28`
- `SessionsController#create` — `app/controllers/sessions_controller.rb:26–40`

At sign-in, the application looks for travelers with a matching email and no linked user:

```
pending_travelers = Traveler.where(user_id: nil, email: user.email).to_a
pending_travelers.each { |t| t.accept!(user) }
```

`Traveler#accept!` then assigns the user and records the invitation-acceptance timestamp.

The existing trip membership remains linked to the same traveler. Through `User#traveler_profiles`, the signed-in user can now retrieve that membership and its trip.

This is an account-linking operation, not a membership-role transition.&#x20;



### D. How roles are represented

`app/models/trip_member.rb:1–7` contains:

```
class TripMember < ApplicationRecord
  belongs_to :trip
  belongs_to :traveler

  enum :role, {
    owner: "owner",
    planner: "planner",
    contributor: "contributor",
    viewer: "viewer"
  }
  validates :role, presence: true
end
```

The role is a persisted string-backed Rails enum.

| Role          | Where the code uses it                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| `owner`       | Initial membership, deletion protection, owner-only trip operations                                    |
| `planner`     | Authorization for trip editing and membership management                                               |
| `contributor` | Assigned to travelers added through the membership controller                                          |
| `viewer`      | Declared as a role and database default, but not assigned by the inspected membership creation actions |

A source-wide search did not identify an application route or controller action for changing a `TripMember` role. The examined creation paths explicitly assign `owner` or `contributor`.

There is no application-implemented State or Strategy collaboration in these enum declarations. The role values are queried by authorization code; they do not encapsulate interchangeable behavior.

### E. Updating and removing members

The routes expose `create` and `destroy` only. There is no `TripMembersController#update` action.

`TravelersController#update`, at `app/controllers/travelers_controller.rb:37–44`, updates the traveler's profile information, such as name and avatar URL, rather than the `TripMember#role`.

For removal, `TripMembersController#destroy`, lines 17–22:

1. Locates the membership through `@trip.trip_members`.
2. Rejects removal if `member.owner?` is true.
3. Otherwise destroys the membership.
4. Redirects to the travelers page.

This removes the person from the trip, not from the account.

Account-level traveler deletion is different. `TravelersController#destroy` removes the traveler record, and `Traveler` declares `has_many :trip_members, dependent: :destroy`. Thus, deleting an account traveler can also remove that person's trip memberships. Unlike the membership controller, the account-level deletion action contains no explicit trip-owner protection. That interaction should be tested before claiming owner memberships are always protected.

## 4. Permission handling — actual authorization paths

### A. Current user and membership lookup

`ApplicationController`, at `app/controllers/application_controller.rb:14–24`, defines:

```
def current_user
  @current_user ||= User.find_by(id: session[:user_id]) if session[:user_id]
end

def current_account
  @current_account ||= current_user&.account
end

def current_member_for(trip)
  return nil unless current_user
  trip.trip_members.joins(:traveler)
      .find_by(travelers: { user_id: current_user.id })
end
```

`authenticate_user!`, lines 47–49, handles the basic sign-in requirement.

The application then uses membership-based queries for trip authorization. It does not rely solely on whether the user created the trip or owns the account.

### B. Viewing a trip

`TripsController#show` uses the `set_trip` callback:

```
def set_trip
  @trip = current_user.trips.find(params[:id])
end
```

This scopes the lookup to trips reachable through the signed-in user's traveler memberships.

No role check is performed here. Consequently, a user with a linked membership in any of the four roles can satisfy the trip-visibility query.

The index action uses the same `current_user.trips` relationship.

### C. Editing a trip

`TripsController#set_editable_trip`, lines 111–119, uses a database query that requires both:

- A traveler associated with the current user.
- A membership whose role is `owner` or `planner`.

```
@trip = Trip.joins(trip_members: :traveler)
            .where(travelers: { user_id: current_user.id })
            .where(trip_members: { role: ["owner", "planner"] })
            .find(params[:id])
```

This callback applies to `edit`, `update`, `cover`, `update_cover`, `refresh_cover`, `travelers` and `geocode_missing`.

Failure to find a matching trip leads to a redirect with a permission alert.&#x20;



### D. Deleting a trip or regenerating its inbound address

`TripsController#set_owner_trip`, lines 120–127, is more restrictive. It requires the acting user's traveler membership to have `role: "owner"`.

It protects `destroy` and `regenerate_inbound_email`.

An account owner is therefore not automatically treated as a trip owner by this authorization query; the matching `TripMember` role is what matters.

### E. Managing trip members

`TripMembersController#require_owner_or_planner`, lines 30–35, uses a different implementation:

```
member = current_member_for(@trip)

unless member&.owner? || member&.planner?
  redirect_to @trip, alert: "Only trip owners and planners can manage travelers."
end
```

This checks the actual membership object after loading the trip.

The controller also prevents deletion of a membership whose role is `owner`, regardless of the acting user's own role.

### G. Repeated and inconsistent permission logic

The source contains two different authorization styles.

Role-restricted queries:

`TripsController#set_editable_trip` and `#set_owner_trip` use explicit role conditions in their SQL-backed Active Record queries.

`TripMembersController#require_owner_or_planner` loads the membership and evaluates Rails enum predicates.

Membership-only scoping:

The following controller methods use `current_user.trips.find(params[:trip_id])` without distinguishing owner, planner, contributor and viewer:

- `TripItemsController#set_trip` — lines 118–120.
- `ExpensesController#set_trip` — lines 90–92.
- `InboxItemsController#set_trip` — lines 44–46.
- `ApprovedSendersController#set_trip` — lines 30–32.

Those controllers include actions that modify or delete records.&#x20;



This is a meaningful authorization observation: the role names suggest different levels of permission, but many mutating routes enforce only membership.

There is also a difference between UI visibility and server authorization. `app/views/trips/_trip_panel.html.erb:178–249` displays the trip-editing controls only when the current member is an owner, while the server-side trip-editing methods also permit planners. UI visibility alone does not define authorization.&#x20;

## 7. Design-pattern candidates

Only after tracing all three flows do I find one recognized pattern category worth carrying into formal verification, represented by two potentially distinct system-event responsibilities.

Candidate A — GRASP Controller

UNCONFIRMED

Responsibility-assignment pattern · Mainly application-owned

Possible collaboration: Trip Creation Coordination

The principal event handler is `TripsController#create`, lines 35–49. It receives the creation request, constructs a `Trip`, assigns account information, saves it, creates the initial owner membership and delegates image retrieval to `FetchTripCoverImageJob`.

Why it might fit: A system-event handler coordinates several domain operations without implementing every subordinate operation itself.

Strongest false-positive argument: This may be routine Rails controller code following conventional request handling. More evidence is needed to assess whether its responsibility assignment is a meaningful GRASP Controller instance rather than merely labeling any Rails controller as a pattern.

Origin: Mixed infrastructure, with application-defined orchestration.

Decision: UNCONFIRMED.

Candidate B — GRASP Controller

UNCONFIRMED

Responsibility-assignment pattern · Mainly application-owned

Possible collaboration: Trip Membership Management Coordination

`TripMembersController#create` and `#destroy`, together with `resolve_and_add_by_email` and `add_traveler`, coordinate membership addition and removal.

The controller delegates storage to Active Record models and invitation delivery to `InvitationMailer`.

Why it might fit: The controller handles meaningful membership-management events and coordinates multiple domain objects and operations.

Both candidates use the same pattern name but concern different system events. If either is later confirmed, its instance boundary must be established from its actual responsibility and collaboration—not merely from the number of controller classes or actions.

### Classifications not supported by the evidence

`TripMember` is an association model containing role information, not an independently implemented behavioral hierarchy.

The inspected source does not establish interchangeable role algorithms, role-state objects, a specialized object-creation factory, a recursive object hierarchy or a protective proxy.

Likewise, `@trip.trip_members.create!` is ordinary Active Record association-based creation. It does not independently prove a GRASP Creator assignment to the `Trip` model, because the application explicitly places the orchestration in `TripsController`.

No additional pattern names are warranted in this preliminary investigation.

## 8. Strongest non-pattern explanation

The implementation is best explained as conventional Rails CRUD orchestration over a membership-based domain model with controller-level authorization.

Trip creation uses Active Record persistence followed by owner-membership creation and asynchronous cover-image retrieval.

Membership management uses a join model carrying role data, account-scoped traveler lookups, conditional invitation handling and ordinary creation/deletion operations.

Authorization uses the signed-in user's membership and role through Active Record queries and before-action methods. The rules are repeated across controllers rather than encapsulated in one authorization abstraction.

This explanation accounts for the source without requiring an additional GoF design pattern.
