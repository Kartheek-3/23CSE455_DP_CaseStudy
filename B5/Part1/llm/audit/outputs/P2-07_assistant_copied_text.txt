## 2. Candidate A — Trip Creation Coordination

CONFIRMED

### System event and receiving object

Event: A signed-in user requests creation of a new trip.

Receiving method: `TripsController#create`.

Source: `config/routes.rb:21` and `app/controllers/trips_controller.rb:35–48`.

The trip form in `app/views/trips/new.html.erb:18–65` submits the request to the route generated by `resources :trips`.

### Application decisions

The controller performs a specific multi-object operation:

```

def create
  @trip = Trip.new(trip_params)
  @trip.created_by = current_user
  @trip.account    = current_account

  if @trip.save
    owner_traveler = current_account.owner_traveler
    @trip.trip_members.create!(
      traveler: owner_traveler,
      role: :owner,
      joined_at: Time.current
    )
    FetchTripCoverImageJob.perform_later(@trip.id)
    redirect_to @trip, notice: "Trip created."
  else
    render :new, status: :unprocessable_entity
  end
end

```

The key application decisions are to assign the signed-in user as creator, associate the trip with their account, proceed only if saving succeeds, select the account owner's traveler profile, create an owner membership and request cover-image processing.&#x20;



### Delegated responsibilities

| Participant                                              | Source location                                   | Responsibility                                   |
| -------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| `TripsController#create`                                 | `app/controllers/trips_controller.rb:35–48`       | Receives and coordinates the use case            |
| `ApplicationController#current_user`, `#current_account` | `app/controllers/application_controller.rb:14–20` | Resolve authenticated identity and account       |
| `Trip`                                                   | `app/models/trip.rb:4–19`                         | Relationships, validations and creation callback |
| `Trip#generate_inbound_email`                            | `app/models/trip.rb:31–37`                        | Generate the trip's email address                |
| `Account#owner_traveler`                                 | `app/models/account.rb:9–11`                      | Find the account owner’s traveler profile        |
| `TripMember`                                             | `app/models/trip_member.rb:1–6`                   | Represent the membership and its role            |
| `FetchTripCoverImageJob#perform`                         | `app/jobs/fetch_trip_cover_image_job.rb:4–30`     | Retrieve and persist a cover-image URL           |

The controller does not itself generate the inbound email address or implement Pexels retrieval. It relies on the `Trip` model and a separate job for those operations.

### Why this supports GRASP Controller

The use case is not merely `Trip.create`.

It establishes a trip, an owner membership and a separate follow-up operation. One receiving object coordinates those responsibilities and delegates subordinate operations.

The source therefore demonstrates a meaningful application-defined system-event responsibility.

### Strongest objection

The controller owns the sequencing of trip persistence and membership creation.

It also invokes `create!` directly and does not wrap both writes in an explicit application-level transaction. This creates potential consistency concerns if the second write fails.

Such controller-level orchestration could be moved into a dedicated application operation, but the absence of that abstraction does not invalidate the observed GRASP Controller role.

The controller is relatively short and delegates major supporting work. It is not simply performing all operations internally.

Origin: Mixed. Rails provides routing, request callbacks, persistence and job infrastructure; DaPlanStan owns the use-case decisions.

Final decision: CONFIRMED.

Stable instance name: `Trip Creation Coordination`

## 3. Candidate B — Trip Membership Management Coordination

CONFIRMED

### System events and receiving object

The application handles two related system events:

- Add a traveler to an existing trip: `POST /trips/:trip_id/trip_members`.
- Remove a traveler from an existing trip: `DELETE /trips/:trip_id/trip_members/:id`.

Both are handled by `TripMembersController`, whose routes are declared in `config/routes.rb:40`.

The receiving methods are `TripMembersController#create`, lines 6–15, and `TripMembersController#destroy`, lines 17–22.

### Application decisions

The addition operation is more complex than basic CRUD.

`TripMembersController#create` checks whether the request contains a traveler ID or an email address.

If an ID is supplied, the controller finds the traveler within the trip's account.

If an email is supplied, it invokes `resolve_and_add_by_email`, which searches for an existing account traveler, checks for a registered user, creates a traveler record when needed and optionally requests an invitation email.

Both paths eventually invoke `add_traveler`.

The source shows the controller making these decisions:

```

def add_traveler(traveler)
  if @trip.trip_members.exists?(traveler: traveler)
    redirect_to travelers_trip_path(@trip),
      alert: "#{traveler.name} is already on this trip."
  else
    @trip.trip_members.create!(
      traveler: traveler,
      role: :contributor,
      joined_at: Time.current
    )
    redirect_to travelers_trip_path(@trip),
      notice: "#{traveler.name} added to trip."
  end
end

```

For deletion, the controller checks whether the selected membership belongs to a trip owner and prevents its removal if so.

The controller also applies a shared owner/planner permission check before either membership-management event.&#x20;

### Delegated responsibilities

| Participant                                      | Source location                                            | Responsibility                                           |
| ------------------------------------------------ | ---------------------------------------------------------- | -------------------------------------------------------- |
| `TripMembersController#create`                   | `app/controllers/trip_members_controller.rb:6–15`          | Receive and coordinate member addition                   |
| `TripMembersController#destroy`                  | Same file, lines 17–22                                     | Coordinate member removal                                |
| `TripMembersController#require_owner_or_planner` | Same file, lines 30–35                                     | Enforce membership-management permission                 |
| `TripMembersController#add_traveler`             | Same file, lines 37–44                                     | Check existing membership and add traveler               |
| `TripMembersController#resolve_and_add_by_email` | Same file, lines 46–65                                     | Resolve user/traveler identity and coordinate invitation |
| `ApplicationController#current_member_for`       | `app/controllers/application_controller.rb:22–25`          | Resolve the acting user's membership                     |
| `Account` and `Traveler`                         | `app/models/account.rb:1–11`; `app/models/traveler.rb:1–8` | Supply account and traveler relationships                |
| `User`                                           | `app/models/user.rb:11–17`                                 | Supply registered-user identity and associations         |
| `TripMember`                                     | `app/models/trip_member.rb:1–6`                            | Store membership and role                                |
| `InvitationMailer#invite_to_trip`                | `app/mailers/invitation_mailer.rb:8–13`                    | Construct the invitation email                           |

The controller delegates data operations to Active Record associations and invitation delivery to Action Mailer. It does not implement mail transport or database persistence itself.&#x20;



### Why this supports GRASP Controller

The controller acts as the entry point for a meaningful membership-management use case.

It coordinates account membership, registered-user identity, trip membership, permissions and invitations. These responsibilities span several domain objects.

The event handler determines which collaborators are required and how the operation proceeds.

That is evidence of a system-event coordination responsibility rather than merely the existence of a Rails controller class.

### Strongest objection: controller-heavy design

This candidate has a stronger objection than trip creation.

`TripMembersController` directly implements substantial business rules:

- Email-based traveler resolution.
- Selection between registered users and email-only travelers.
- Creation of traveler profiles.
- Membership duplication checks.
- Assignment of the contributor role.
- Invitation decisions.
- Owner-removal protection.

These decisions are concentrated in the controller rather than delegated to a dedicated domain operation.

Does that invalidate GRASP Controller?

Not necessarily.

GRASP Controller identifies where responsibility for receiving and coordinating system events is assigned. It does not require every internal rule to have been perfectly delegated.

The controller clearly performs that coordination role. Nevertheless, its business-policy concentration is a design limitation and should be documented rather than described as an example of excellent separation of concerns.

Origin: Mixed. Rails provides routing and persistence infrastructure, while DaPlanStan owns the membership-management decisions.

Final decision: CONFIRMED.

Stable instance name: `Trip Membership Management Coordination`

## 4. Are these genuinely independent collaborations?

Yes. They are separate use-case collaborations, not merely separate controller classes.

| Comparison             | Trip Creation Coordination                | Trip Membership Management Coordination             |
| ---------------------- | ----------------------------------------- | --------------------------------------------------- |
| System event           | Create a new trip                         | Add/remove members of an existing trip              |
| Entry point            | `TripsController#create`                  | `TripMembersController#create` / `#destroy`         |
| Main objective         | Establish a trip and initial ownership    | Maintain trip participation                         |
| Authorization          | Authenticated user                        | Existing trip owner or planner                      |
| Main objects           | `Trip`, `Account`, `TripMember`           | `Trip`, `Account`, `Traveler`, `User`, `TripMember` |
| Significant delegation | `Trip` initialization and cover-image job | Identity lookups and invitation delivery            |
| Outcome                | New trip and initial owner membership     | Existing trip's membership changes                  |

### Why two instances rather than one?

The distinction is not controller class identity. It is the independent system event and coordinated domain outcome.

Trip creation establishes a new trip and its initial ownership. Membership management operates on a trip that already exists and handles member participation.

The two flows share `TripMember` and Active Record association machinery, but that shared infrastructure does not make their system events identical.

A particularly important source-level distinction is that the original owner membership is created directly from `TripsController#create` with `role: :owner`, whereas later additions use `TripMembersController#add_traveler` with `role: :contributor`.&#x20;



They have different entry points, authorization conditions, decisions and collaborators.

The controller coordinates trip creation, initialization of the owner membership and delegation of cover-image retrieval. **Candidate 2: Trip Membership Management Coordination**

- Pattern: GRASP Controller
- Status: CONFIRMED (static source assessment)
- Main participant: `TripMembersController`
- Evidence: `app/controllers/trip_members_controller.rb:1–65`

The controller handles membership-management events, including authorization, traveler resolution, membership creation/removal and invitation coordination. The role is supported by actual application decisions spanning multiple objects. However, substantial business rules remain in the controller, indicating controller-heavy procedural orchestration.

**Counting decision**

These are two independent use-case collaborations with different system events, objectives, authorization rules and participant interactions. They represent two GRASP Controller instances under the documented use-case collaboration counting rule, not two instances merely because they reside in different Rails controllers.

**Rejected or uncertain classifications**

No additional pattern classifications were proposed or rejected in this verification. Neither candidate remains structurally uncertain, although the appropriateness of counting conventional Rails event handlers as GRASP instances should receive independent faculty/team review.

**Limitations**

Source-based confirmation does not establish runtime correctness, design quality or completed human verification. Preserve the controller-heavy and transaction-consistency concerns separately from the pattern classification.

Final conclusion: Both candidates meet the GRASP Controller responsibility rule at the source level, with different strengths and design trade-offs. They can be proposed as two distinct baseline instances, subject to human verification and consistent counting across the rest of the repository.
