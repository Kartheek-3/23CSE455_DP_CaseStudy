## 3. Implemented cancellation policies

All policies implement:

```
fee_rate(seconds_until_start:)
```

Their rules match the frozen design.

| Time until booking starts         | Flexible fee | Moderate fee | Strict fee |
| --------------------------------- | ------------ | ------------ | ---------- |
| At least 72 hours                 | 0%           | 0%           | 100%       |
| 24 to less than 72 hours          | 0%           | 50%          | 100%       |
| More than 0 to less than 24 hours | 10%          | 100%         | 100%       |
| At or after start                 | 100%         | 100%         | 100%       |

All three implementations are stateless and perform no database access or network calls.

## 4. Eligibility implementation

`CancellationPolicies::QuoteEvaluator` independently checks that the item:

- Has `status = confirmed`.
- Has an associated InboxItem with confirmed review status.
- Contains its own confirmation reference.
- Has a valid start timestamp and nonnegative amount.
- Uses EUR, GBP or USD.

This means a Scenario 1 generated idea or Scenario 2 demo-provider idea cannot receive a quote merely because a user changes its status to confirmed.

The service also refuses to use another itinerary item's displayed fallback confirmation reference.

## 5. QuoteEvaluator behavior

The evaluator at `quote_evaluator.rb:32–55` selects one of the three explicitly permitted policies and calculates:

\\[ \text{Fee}=\operatorname{round}\_{2}(\text{Amount}\times\text{Rate}) \\]

\\[ \text{Refund}=\text{Amount}-\text{Fee} \\]

It uses `BigDecimal` and `ROUND_HALF_UP` rather than floating-point money calculations.

The output includes the policy code and name, original amount, fee, refund, currency, refundable flag and explanation.

Unknown policies, negative amounts, missing required fields, unsupported currencies and invalid evaluation times produce controlled errors.

## 6. Final user workflow

Owner opens a confirmed email-linked TripItem

Selects Estimate cancellation (demo)

Controller verifies trip ownership and booking eligibility

Owner selects Flexible, Moderate or Strict

QuoteEvaluator calculates hypothetical fee and refund

Application displays result and disclaimer

TripItem, InboxItem and Expense remain unchanged

Both `new` and `create` enforce owner authorization in the controller. The POST action reads booking details from the server-loaded record, not browser-supplied amounts or booking fields.

The UI states explicitly that the result is hypothetical and that no reservation has been cancelled.

## 7. Read-only and persistence verification

Source inspection confirms that the new controller and evaluator contain no calls to save, update, destroy or create booking records.

They also do not invoke cancellation APIs, payment operations, email delivery or background jobs.

No migration or cancellation-status enum was added.

Important distinction: This is confirmed by source inspection and isolated calculation tests. Full database read-only behavior still requires the blocked Rails integration tests.

## 11. Remaining limitations

The implementation intentionally cannot cancel an actual booking or guarantee a real refund. It does not retrieve provider-specific contractual terms.

Bookings without required start, amount, currency or confirmation data cannot receive estimates. No historical quote is persisted, and the controller uses the actual current time when generating a quote.

A compatible Rails environment is still required to verify rendering, authorization, database interactions and the complete application regression suite.
