## 2. Scope and architecture comparison

| Approach                           | Fit and complexity                                                      | Database impact     | Testability and pattern assessment                          |
| ---------------------------------- | ----------------------------------------------------------------------- | ------------------- | ----------------------------------------------------------- |
| A. Hard-coded conditionals         | Small but mixes refund rules with controller/model responsibilities     | None                | Easy initially; no separate Strategy collaboration          |
| B. Separate policy objects         | Good separation of distinct refund behaviors                            | None for quote-only | Highly testable; possible Strategy                          |
| C. JSON-only policy definitions    | Compact data-driven calculation                                         | None                | Deterministic but may simply be table-driven logic          |
| D. Real provider cancellation APIs | Poor fit with current demo and email-only integrations; high complexity | Likely substantial  | Credentials and API access required; pattern not guaranteed |
| E. Small local policy abstraction  | Best fit for distinct deterministic policy behavior                     | None                | Independent tests; plausible Strategy collaboration         |

Selected: E — a small local policy abstraction.

Use three concrete policies, one evaluator and one Rails controller. No payment gateway, booking-client API, policy database table or persistent cancellation workflow is necessary.

This is not a claim that a provider will honor the calculated refund. The application must prominently label all results as hypothetical demonstration estimates.

## 3. Eligible TripItem rule

A TripItem may receive a cancellation-policy quote only when all the following conditions hold:

1. `item.confirmed?` is true.
2. `item.inbox_item_id` is present.
3. Its associated InboxItem has `review_status == confirmed`.
4. The item's own `confirmation_ref` is nonblank.
5. `starts_at` is present and interpretable.
6. `amount` is present and nonnegative.
7. `currency` is supported.

The evaluator must check these conditions independently of the UI.

This excludes manually created ideas, generated ideas and Scenario 2 provider-demo ideas, even if an ordinary user later toggles their status to `confirmed`.

The requirement for the item's own reference is intentional: `TripItemsController#show` can display a reference inherited from a sibling item (`:16–28`). That display fallback should not establish cancellation-quote eligibility for an item lacking its own booking reference.

Known limitation: Genuine email bookings without a confirmation reference, amount or start time will not be eligible for a quote in V1. They remain visible and otherwise functional.

## 4. Cancellation outcome: quote-only

Selected: Calculate and display only

V1 will not create a `cancelled` status, change booking data, alter an Expense or send a cancellation request.

The existing `TripItem` record stays unchanged after an estimate.

This is appropriate because DaPlanStan does not know the real provider's contractual policy and has no external cancellation integration.

A persistent cancellation state could falsely imply that a reservation was cancelled. It would also require additional model semantics, UI changes, lifecycle rules and testing. Those are unnecessary for this coursework feature.

### Proposed AFTER workflow

Trip owner opens eligible confirmed TripItem

Selects Estimate cancellation (demo)

CancellationQuotesController checks access and eligibility

User chooses Flexible, Moderate or Strict

CancellationPolicies::QuoteEvaluator selects the policy

Concrete policy determines applicable fee percentage

Evaluator calculates fee and hypothetical refund

UI displays amounts, currency and explanation

No booking or database record is changed

## 5. Exact cancellation-policy rules

Define the time difference as:

\\[ \Delta = \text{item.starts\\\_at} - \text{evaluated\\\_at} \\]

Use elapsed seconds to determine each boundary. The calculation should receive an explicit evaluation timestamp, allowing reproducible unit tests without relying on wall-clock time.

All three policies are fictional application policies.

| Time until start                   | Flexible | Moderate | Strict   |
| ---------------------------------- | -------- | -------- | -------- |
| At least 72 hours                  | 0% fee   | 0% fee   | 100% fee |
| At least 24 but less than 72 hours | 0% fee   | 50% fee  | 100% fee |
| More than 0 but less than 24 hours | 10% fee  | 100% fee | 100% fee |
| At or after start                  | 100% fee | 100% fee | 100% fee |

The table deliberately specifies inclusive boundaries:

- At exactly 72 hours, Moderate has no fee.
- At exactly 24 hours, Flexible has no fee and Moderate charges 50%.
- One second before start, Flexible charges 10%.
- At exactly the start timestamp and afterward, every policy charges 100%.

### Required monetary rules

Use `BigDecimal` for amounts and rates.

\\[ \text{fee}=\operatorname{round}\_{2}(\text{amount}\times\text{fee rate}) \\]

\\[ \text{refund}=\text{amount}-\text{fee} \\]

Round the fee to two decimal places with a documented rounding mode such as `BigDecimal::ROUND_HALF_UP`. Derive the refund by subtracting the rounded fee so that:

\\[ \text{fee}+\text{refund}=\text{original amount} \\]

For the first version, support EUR, GBP and USD, which fit the application's two-decimal amount representation. Other currencies, including JPY, should receive a clear unsupported-currency message rather than an inaccurately rounded quote.

### Edge-case policy

| Input                                              | Required handling                                |
| -------------------------------------------------- | ------------------------------------------------ |
| Missing amount                                     | Do not calculate; explain missing booking amount |
| Zero amount                                        | Valid; zero fee and zero refund                  |
| Negative amount                                    | Reject                                           |
| Missing start time                                 | Reject; do not guess from Trip dates             |
| Missing currency                                   | Reject                                           |
| Unsupported currency                               | Reject clearly                                   |
| Unknown policy                                     | Reject before calculation                        |
| Item is an idea                                    | Ineligible                                       |
| Item has no genuine confirmed email link/reference | Ineligible                                       |
| Cancellation at/after start                        | Apply after-start tier                           |
| Exactly at a deadline                              | Apply explicitly inclusive boundary              |
| Evaluation time missing from direct service call   | Reject; controller supplies `Time.current`       |
| Malformed timestamp                                | Reject                                           |
| Valid currency                                     | Preserve it unchanged in the result              |

`refundable` in the result should mean `refund_amount > 0`. A zero-cost item can have a zero fee without a positive refundable amount.

## 6. Proposed classes and interfaces

The implementation does not need a large class hierarchy.

| New class                              | Responsibility                                                   | Public method                                   |
| -------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------- |
| `CancellationPolicies::Flexible`       | Determine Flexible policy fee rate                               | `fee_rate(seconds_until_start:)`                |
| `CancellationPolicies::Moderate`       | Determine Moderate policy fee rate                               | `fee_rate(seconds_until_start:)`                |
| `CancellationPolicies::Strict`         | Determine Strict policy fee rate                                 | `fee_rate(seconds_until_start:)`                |
| `CancellationPolicies::QuoteEvaluator` | Validate the booking, select a policy, calculate monetary result | `call(trip_item:, policy_code:, evaluated_at:)` |
| `CancellationQuotesController`         | Authorize and coordinate quote requests                          | `new`, `create`                                 |

The three policies return decimal fee rates between zero and one. They must be stateless and must not know about controllers, the database or external providers.

`QuoteEvaluator` acts as the common context. It uses a fixed policy-code-to-class map, performs eligibility and monetary validation, invokes the selected policy, and returns a consistent result.

A separate registry class or abstract superclass is unnecessary in V1.

### Proposed output structure

```
{
  policy_code: "moderate",
  policy_name: "Moderate",
  original_amount: BigDecimal("200.00"),
  fee_amount: BigDecimal("100.00"),
  refund_amount: BigDecimal("100.00"),
  currency: "EUR",
  refundable: true,
  explanation: "The selected demo policy applies a 50% fee."
}
```

This is a proposed result contract, not an output currently produced by the application.

The evaluator should raise controlled, distinguishable errors for ineligible bookings, unknown policies, missing data and unsupported amounts/currencies. The controller will display a friendly message without exposing internal exceptions.

## 7. Database migration decision

No migration required

The current `db/structure.sql:91–104` shows:

| Field              | Existing type |
| ------------------ | ------------- |
| `status`           | String        |
| `starts_at`        | Datetime      |
| `amount`           | Decimal(10,2) |
| `currency`         | String        |
| `confirmation_ref` | String        |
| `inbox_item_id`    | Foreign key   |
| `notes`            | Text          |

Those fields are sufficient to calculate a hypothetical cancellation quote.

The `expenses` table (`db/structure.sql:105–125`) should remain unchanged.

No `cancellation_policy`, `cancelled_at`, `cancellation_fee` or `refund_amount` columns are necessary because no cancellation or quote is persisted.

The user selects the demonstration policy each time. The selection must not be treated as the real contractual policy for that booking.

### Authorization

Use the source's existing mechanisms:

```
@trip = current_user.trips.find(params[:trip_id])
@item = @trip.trip_items.find(params[:trip_item_id])

head :forbidden unless current_member_for(@trip)&.owner?
```

For V1:

- Trip owners may request quotes.
- Planners, contributors and viewers cannot request them.
- Users who do not belong to the trip cannot access its items.
- Every GET/POST must enforce authorization server-side.
- The frontend link's visibility is not an authorization control.

The `new` action displays eligible booking details and a policy selector; `create` evaluates the selected policy and renders the result without writing to the database.

## 11. Test plan

Policy unit tests

Verify all three algorithms using fixed timestamps, especially exactly 72 hours, exactly 24 hours, one second before each deadline, at start and after start. Verify zero/negative amounts, decimal rounding, currency preservation and unknown policies.

Evaluator and controller tests

Verify policy selection, normalized quote fields, missing booking data, eligible inbox-linked bookings, owner authorization, rejection of unrelated users, and no persistence on GET or POST.

Regression tests

Retain Scenario 1 generation, preview, JSON import and manual creation coverage. Retain Scenario 2 provider-normalization, demo idea and duplicate-protection coverage. Check email-confirmation linking, expense creation and the existing geocoding/Turbo workflows.

Manual/runtime checks

With a compatible Rails environment, open an eligible confirmed item, select all three policies, inspect the quotes, and confirm that database records remain unchanged. Verify that demo ideas do not offer the quote action.

All calculation tests must pass `evaluated_at` explicitly. Do not introduce external API requests into policy tests.

The previously identified Rails environment blocker still needs resolution before full integration testing. No Scenario 3 tests have been executed during this design step.

## 12. Regression risks

| Risk                                            | Safeguard                                                                       |
| ----------------------------------------------- | ------------------------------------------------------------------------------- |
| Confirmed itinerary idea mistaken for a booking | Require confirmed InboxItem, item confirmation reference and `confirmed` status |
| Real policy implied without evidence            | Label every policy and quote as hypothetical                                    |
| Client manipulates booking amount               | Evaluator reads amount from the server-loaded TripItem                          |
| Incorrect deadline handling                     | Compare timestamps in seconds; test exact boundaries                            |
| Money calculation inaccuracies                  | BigDecimal and explicit two-decimal rounding                                    |
| Existing expense accidentally adjusted          | Never write to Expense                                                          |
| Real booking marked cancelled                   | Quote-only; no cancelled status                                                 |
| Scenario 2 demo offer considered cancellable    | Require confirmed email linkage, which demo offers lack                         |
| Scenario 1 changes accidentally                 | Do not edit generation/import source                                            |
| Turbo/geocoding behavior disturbed              | No changes to those participants                                                |

## 13. Tentative pattern candidates

These are candidates only. Confirmation requires inspecting the actual future implementation.

### Candidate A — Strategy (GoF): Cancellation Policy Evaluation

| Role               | Proposed concrete participant          |
| ------------------ | -------------------------------------- |
| Context            | `CancellationPolicies::QuoteEvaluator` |
| Strategy contract  | `fee_rate(seconds_until_start:)`       |
| ConcreteStrategy 1 | `CancellationPolicies::Flexible`       |
| ConcreteStrategy 2 | `CancellationPolicies::Moderate`       |
| ConcreteStrategy 3 | `CancellationPolicies::Strict`         |
| Client             | `CancellationQuotesController#create`  |

Why it may qualify: Different algorithms for computing the fee are interchangeable under a stable contract. The evaluator selects one and delegates the variable behavior.

Why it might be rejected later: If implementation reduces to a single method with hard-coded conditionals or policy configuration values rather than actual interchangeable behavior objects, a separate Strategy classification may not be justified.

If eventually confirmed, all three concrete policies would form one Strategy instance, not three.

### Candidate B — Controller (GRASP): Cancellation Quote Coordination

The potential coordinator is `CancellationQuotesController`, handling the distinct user event of requesting a hypothetical cancellation quote.

Its collaborators would be Trip, TripItem, TripMember, InboxItem and QuoteEvaluator.

This differs from P05 import, S1-N01 personalized generation and S2-N02 provider option coordination.

However, merely introducing a Rails controller does not confirm a new Controller pattern. The implemented responsibility, participants and delegation must be verified afterward.

### Factory assessment

A fixed map from `"flexible"`, `"moderate"` and `"strict"` to classes is ordinary selection logic. Do not plan to count Factory Method or Abstract Factory without separate structural evidence.

## Final Scenario 3 design decision

Implement a quote-only cancellation-policy demonstration using Flexible, Moderate and Strict calculation objects, with one evaluator and one controller.

The design deliberately avoids persistence and actual cancellation because the existing application does not have provider cancellation contracts or booking APIs. It uses real fields already present on email-linked TripItems, protects Scenario 1 and Scenario 2, and permits deterministic testing.

The source version for the next implementation step will be `scenario3_cancellation_policies`.
