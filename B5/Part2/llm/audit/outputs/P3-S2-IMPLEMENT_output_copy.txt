## 5. Atlas and Beacon normalization

Both providers have different source representations but return the same nine-field offer contract.

| Information   | Atlas source            | Beacon source |
| ------------- | ----------------------- | ------------- |
| Collection    | `destinations → offers` | `results`     |
| Offer ID      | `id`                    | `code`        |
| Name          | `title`                 | `label`       |
| Category      | `category`              | `type`        |
| Location      | `location`              | `address`     |
| Description   | `details`               | `summary`     |
| Sample amount | `price.value`           | `amount`      |
| Currency      | `price.currency`        | `currency`    |

The normalized structure contains `provider_code`, `provider_name`, `offer_id`, `name`, `kind`, `address`, `description`, `sample_amount` and `currency`.

Both fixtures support Rome and Paris, with five fictional offers per provider.

Invalid kinds, amounts, currencies, offer IDs and malformed fixture structures result in controlled errors.

## 6. Authorization, tampering and persistence

The controller requires an authenticated user with an owner role for the selected trip.

On POST, it accepts only the three identifying parameters: `provider_code`, `destination_code` and `offer_id`.

It retrieves the selected offer again from the server-owned fixture. Browser-supplied prices, names, kinds, status values and confirmation references are ignored.

The saved item has:

| Field                   | Value                                                        |
| ----------------------- | ------------------------------------------------------------ |
| `status`                | `idea`                                                       |
| `added_by`              | Current authenticated user                                   |
| `name`                  | Provider-prefixed offer name                                 |
| `notes`                 | Provider identity, offer ID, description and demo disclaimer |
| `amount` / `currency`   | Validated fictional estimate                                 |
| `starts_at` / `ends_at` | `nil`                                                        |
| `confirmation_ref`      | `nil`                                                        |
| `inbox_item_id`         | `nil`                                                        |

A controlled marker, such as `[demo_provider_offer:atlas_demo:atlas-rome-walk-01]`, is placed in the notes. It is used to identify an already-added idea from the same provider and offer ID.

No Expense or InboxItem is created.

## 7. Geocoding reuse

The new controller sets `defer_geocoding = true` on the specific new TripItem before saving it.

After saving, it calls the existing `GeocodeTripItemsJob.perform_later`.

The existing job then loads a fresh record and performs geocoding normally, followed by the existing Turbo refresh.

No global callback manipulation was introduced, and the existing `TripItem`, `Geocodable` and geocoding job source files remain unchanged.

## 10. Implementation differences and remaining limitations

The feature follows the approved design. The principal implementation detail added is a controlled provider-and-offer marker in `TripItem.notes` to support deduplication without a migration.

Remaining limitations include sequential rather than concurrency-safe duplicate prevention, provider metadata being stored as text rather than relational fields, fixed demo destinations and invented costs, and the unavailable Rails integration environment.

The Source ZIP contains the complete change record and logs needed to continue verification in a compatible Rails environment.
