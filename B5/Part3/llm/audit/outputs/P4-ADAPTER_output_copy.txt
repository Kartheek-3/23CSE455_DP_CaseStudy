## 4. Atlas and Beacon normalization

The two provider formats are structurally different.

| Property    | Atlas Demo                 | Beacon Demo                      |
| ----------- | -------------------------- | -------------------------------- |
| Structure   | Destination-scoped records | Flat offer records               |
| ID          | `id`                       | `code`                           |
| Name        | `title`                    | `label`                          |
| Category    | `category`                 | `type`                           |
| Location    | `location`                 | `address`                        |
| Description | `details`                  | `summary`                        |
| Price       | Compound, e.g. `EUR:24.00` | Separate `amount` and `currency` |
| Destination | First column               | Final column                     |

Atlas maps `activity → do`, `shopping → shop` and `dining → eat`.

Beacon independently maps `experience → do`, `retail → shop` and `dining → eat`.

Both adapters produce the same normalized fields:

`provider_code`, `provider_name`, `offer_id`, `name`, `kind`, `address`, `description`, `sample_amount_cents`, `currency`.

Amounts are stored as integer cents. Neither adapter creates a booking or confirmation reference.

## 5. Adapter collaboration and role mapping

BookingOfferClient

Uses the common provider contract

OfferProvider Target Interface

offersFor(destination)

AtlasAdapter

Interprets Atlas raw TSV and compound price

BeaconAdapter

Interprets Beacon raw TSV and separate price fields

NormalizedOffer

One common, validated output representation

| Adapter role      | Participant in all four implementations |
| ----------------- | --------------------------------------- |
| Client            | `BookingOfferClient`                    |
| Target            | `OfferProvider`                         |
| ConcreteAdapter 1 | `AtlasAdapter`                          |
| ConcreteAdapter 2 | `BeaconAdapter`                         |
| Adaptees          | Atlas and Beacon raw TSV formats        |
| Selection         | `ProviderRegistry`                      |
| Target output     | `NormalizedOffer`                       |

Python uses the method name `offers_for`; Java, JavaScript and C++ use `offersFor`.

Why this is Adapter rather than Strategy: The key responsibility is translating incompatible source structures into a common client-facing contract. The two implementations do not represent competing cancellation or booking algorithms.

`ProviderRegistry` is a fixed whitelist and is not counted as a Factory.

## 7. Provider isolation verification

Additional assertions beyond A01–A10 checked:

- Atlas cannot retrieve Beacon offer IDs.
- Beacon cannot retrieve Atlas offer IDs.
- Rome and Paris filtering works.
- Malformed Atlas data does not prevent valid Beacon lookup.
- Malformed Beacon data does not prevent valid Atlas lookup.
- Invalid Beacon kinds produce `INVALID_OFFER`.
- Missing Beacon schema fields produce `INVALID_FIXTURE`.
- Provider selection does not depend on mutable global state.

These additional isolation checks passed in all four languages. They are not included as additional numbered A01–A10 cases.

## 12. Remaining limitations

This is a dependency-free demonstration of the verified Adapter collaboration. It does not reproduce Rails, Active Record, actual provider APIs or a real booking transaction.

The example is restricted to two fictional providers, two destinations, three normalized kinds and the fixed test inputs. It handles malformed local fixtures deterministically but does not test live network failures, concurrency or production provider changes.

The execution times are machine-specific and heavily influenced by process startup and fixture handling.
