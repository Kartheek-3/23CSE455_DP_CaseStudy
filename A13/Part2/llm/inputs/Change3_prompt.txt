## 5. URL analysis and canonicalisation

Create a reusable URL-analysis service with explicit, testable responsibilities.

It should extract and evaluate relevant URLs from post content using Misskey's existing parsing conventions where appropriate.

Analyse at least the following characteristics.

### 5.1 URL syntax and normalisation

Handle:

- HTTP and HTTPS URLs.
- Hostname normalisation.
- Hostnames with trailing dots.
- Internationalised domain names and Punycode representations.
- Explicit ports.
- Encoded characters where they affect parsing.
- URLs containing user-information components before the hostname.
- IP-address-based destinations.
- Malformed and unsupported URL schemes.
- Hostnames that become ambiguous after normalisation.

Use standard URL parsing and domain-normalisation facilities where appropriate. Do not implement URL interpretation through fragile regular expressions alone.

Treat a URL's canonical form as an analysis aid, not proof that it is safe.

### 5.2 Misleading domains

Identify suspicious representations where feasible, including:

- Unicode/Punycode hostnames that may resemble trusted domains.
- Misleading subdomains.
- Hostname/user-information combinations that visually imitate a trusted site.
- Known deceptive or abusive domains from configured reputation sources.

Any heuristic for homograph or confusable-domain detection must be described as a risk signal, not a guarantee of malicious intent.

Do not block a legitimate internationalised domain solely because it contains non-ASCII characters.

### 5.3 Suspicious redirects

Investigate how to identify risky redirection patterns, such as:

- Known malicious redirector domains.
- Known URL-shortening services when relevant to the configured policy.
- Open-redirect patterns supported by reliable reputation evidence.
- Redirect destinations already identified as malicious by a configured source.
- URLs that obscure their actual hostname or destination.

Do not claim that an arbitrary redirect chain has been verified unless it was actually inspected.

Prefer reputation-based analysis or a narrowly scoped, controlled mechanism when redirect-chain verification is needed. Treat unknown redirect behaviour as uncertain rather than automatically malicious.

## 6. Threat-intelligence and reputation integration

Implement a configurable reputation layer that can determine whether a URL or domain is:

- Known malicious or associated with phishing.
- Suspicious according to available evidence.
- Known benign according to a configured source.
- Unknown or not yet evaluated.

The precise result representation can follow Misskey's conventions, but it must distinguish a positive risk finding from the absence of evidence.

### 6.1 Provider abstraction

Decouple URL analysis from any specific external reputation provider.

Use the existing dependency-injection and configuration mechanisms to register the provider and configure its behaviour.

Where appropriate, support:

- A configurable, administrator-maintained domain list.
- An optional external reputation provider.
- A deterministic local provider or fixture for automated tests.
- A cache for recently obtained reputation results.

Do not require a paid external service for basic local operation or automated testing.

If no reputation source is configured, the application must behave predictably and explain that it cannot perform that particular check. Do not interpret an unavailable provider as evidence that a URL is malicious—or that it is safe.

Provider timeouts, rate limits, malformed responses and network failures must be handled explicitly.

### 6.2 Caching

Use the repository's existing caching infrastructure where appropriate.

Implement reasonable expiration rules so that stale results do not remain authoritative indefinitely.

Different result categories may require different cache policies. A temporary provider failure should not permanently cache an unknown result as a known-benign verdict.

Deduplicate concurrent lookups for the same canonical URL or domain where practical.

Avoid retaining entire post bodies in a reputation cache when storing a canonical URL or domain result is sufficient.

### 6.3 Reputation provenance

Preserve enough information to explain why a warning was generated.

Depending on the provider, this may include:

- The canonical hostname or relevant URL identifier.
- The risk category.
- The provider or local rule responsible.
- The observation time.
- A concise explanation that can be displayed to users or moderators.

Do not expose API credentials, internal configuration secrets or private report information in a public warning.

## 7. Redirect fetching and SSRF safety

**Security requirement: do not introduce an unrestricted server-side URL-fetching mechanism.**

Analysing a user's URL can expose the server to Server-Side Request Forgery (SSRF), DNS rebinding, unsafe redirects and resource-exhaustion attacks.

If your implementation needs to fetch a redirect chain or consult a remote provider, follow these restrictions.

1. Prefer a provider API that analyses a submitted URL without causing Misskey to fetch arbitrary destination content.
2. Use existing secure HTTP request infrastructure where appropriate.
3. Restrict permitted schemes to those genuinely required by the implementation.
4. Reject loopback, private, link-local, multicast, reserved and otherwise prohibited network destinations.
5. Apply equivalent protections to IPv4 and IPv6 representations.
6. Resolve and validate DNS results and protect against redirects to prohibited destinations.
7. Revalidate every redirect hop; do not treat validation of the first URL as sufficient.
8. Avoid DNS-rebinding vulnerabilities and verify that the actual connection cannot silently reach a forbidden destination.
9. Apply redirect-count limits, connection and response timeouts, and strict resource limits.
10. Do not download or process arbitrary response bodies when a destination check is sufficient.
11. Prevent accidental access to cloud metadata endpoints or internal administrative services.
12. Fail safely if destination validation cannot be performed reliably.

If a robust implementation cannot be achieved within the feature's scope, do not add redirect fetching. Implement reputation-based and canonicalisation-based checks instead, and document precisely which redirect risks are not directly verified.

Add deterministic security tests for prohibited destinations, invalid URL forms, unsafe schemes and redirect-validation behaviour where applicable.

## 8. Spam and repeated promotional-pattern analysis

Implement a small, explainable spam-analysis mechanism that complements Misskey's existing moderation and reporting facilities.

Investigate the current codebase before deciding which behavioural signals are already available.

Potential signals include:

- Repeated posting of the same or substantially similar URLs.
- Repeatedly posting links to the same domain within a bounded interval.
- Repetitive promotional content patterns.
- Previously flagged domains.
- Multiple independent reports associated with a URL or domain.

Use only signals that can be implemented from real, available data.

### 8.1 Scoring and explainability

Use a deterministic, configurable rule-based scoring approach for the first implementation. A trained machine-learning model is not required.

Each risk decision should be explainable through its contributing signals.

Keep these concerns distinct:

- URL reputation.
- Suspicious URL structure.
- Posting-frequency or repetition signals.
- User-reported concerns.
- The final advisory risk assessment.

Avoid treating a high score or a large number of reports as conclusive proof of malicious intent.

### 8.2 Abuse resistance

Repeated reports can be useful evidence, but they can also be manipulated.

Before using report information, inspect Misskey's current report storage and moderation workflows.

Use suitable safeguards, such as deduplicating reports, limiting their influence and distinguishing independent reports from repeated reports by the same reporter.

Do not allow a coordinated reporting attack to silently suppress a legitimate domain.

Do not invent report counts or infer reports that do not exist.

### 8.3 Policy behaviour

A suspicious-pattern result must not automatically delete normal posts or impose irreversible sanctions solely because a heuristic produced a high score.

The default outcome should be an advisory warning or reviewable flag, unless an existing explicitly configured and authorised moderation policy governs a stronger action.

Any automatic restriction must respect the existing moderation model and must be clearly configurable.

## 9. Composer warnings

Integrate the safety checks into the actual post-composition workflow.

Before publication, users should be able to see a relevant advisory when a URL is identified as malicious or suspicious.

An illustrative warning is:

"This destination has been reported for phishing."

The actual message should accurately reflect the evidence. Do not present an unknown URL as confirmed phishing.

The composer should support:

- Detecting relevant links in the current draft.
- Showing a concise warning and reason.
- Distinguishing confirmed risk findings from uncertainty.
- Allowing the user to inspect the explanation.
- Dismissing or acknowledging an advisory where policy permits.
- Updating the result when the draft changes.
- Avoiding unnecessary repeated checks for unchanged URLs.
- Handling an unavailable reputation provider without breaking ordinary post creation.

Existing post-creation, validation, visibility and submission logic must remain intact.

Client-side analysis is not a substitute for backend enforcement or security checks. Where relevant, the final publication path should use the backend's authoritative analysis or policy result.

Do not automatically cancel publication or delete an otherwise valid post merely because an advisory heuristic scores it as risky.

## 10. Reader-facing link warnings

Where applicable, show:

- The destination hostname.
- The risk category.
- A concise reason.
- The source or type of evidence, without revealing confidential provider details.
- An appropriate action to inspect or dismiss the advisory.

Unknown results should not be labelled malicious.

Do not render arbitrary HTML received from an external reputation provider.

Do not introduce a new post renderer if the existing URL or MFM rendering system provides a suitable integration point.

Ensure that the frontend does not break existing links, link previews, note rendering or accessibility features.
