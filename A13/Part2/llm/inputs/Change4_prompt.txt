## 3. Core feature specification

Introduce a separate, opt-in **For You** feed that ranks eligible public posts according to a user's interests and interactions.

Misskey already has chronological timelines, Antennas, hashtag-related discovery and other ways of finding posts. Do not simply rename an existing timeline and claim to have implemented personalised recommendations.

The new feed must provide:

- A separate recommendation API.
- A transparent, deterministic ranking algorithm.
- Ranking signals based on explicit interests and relevant user interactions.
- Recency-aware relevance.
- Content and author diversity.
- An understandable explanation for each recommendation.
- User controls to mute topics and reduce recommendations from selected authors.
- A way to reset the recommendation profile.
- A clear way to switch between the personalized feed and chronological ordering.
- Enforcement of existing privacy, visibility, block, mute and safety restrictions.
- Automated tests covering ranking, explanation, user controls and restricted-content exclusion.

Start with a small weighted-scoring algorithm. Do not train a large machine-learning model or introduce an external AI dependency.

Recommendations must be user-controlled and explainable. Do not implement opaque ranking that cannot identify why a post was recommended.

## 5. Opt-in behaviour and timeline integration

The For You feed must be an additional timeline, not a replacement for existing chronological timelines.

Implement a clear way for a user to enable or open the personalized feed. The user must be able to return to the ordinary chronological feed without losing their existing timeline configuration.

Respect the opt-in choice. Do not silently replace the user's home timeline or change the ordering of existing timelines.

A reasonable initial design is a distinct For You timeline option or route, integrated with the current timeline navigation conventions.

The frontend must:

- Clearly distinguish the recommendation feed from chronological feeds.
- Show a useful empty or onboarding state if the user has insufficient recommendation data.
- Provide access to recommendation controls.
- Preserve ordinary timeline navigation and pagination behaviour.
- Handle API errors without breaking the rest of the application.
- Avoid inserting duplicated posts when loading another page or refreshing the feed.

Use the existing Vue component, API client and timeline conventions rather than building a separate social application.

## 6. Candidate selection and eligibility

The recommendation system should not attempt to score every note in the entire database for every request.

Design a bounded and efficient candidate-selection process using existing Misskey queries and data-access patterns.

Select candidate notes from applicable sources, such as:

- Recent eligible public posts.
- Posts from followed accounts that are accessible to the user.
- Posts associated with topics of demonstrated interest.
- Other sources justified by the existing architecture and the actual available data.

The exact candidate sources must be documented.

Use reasonable candidate and time-window limits so the service does not perform unbounded scans.

Before returning recommendations, enforce the applicable eligibility rules.

Exclude notes that the requesting user cannot access, including private or restricted notes that are not intended for them.

Apply existing rules for:

- Note visibility.
- Blocks and mutes.
- Muted or restricted content.
- Deleted notes and unavailable authors.
- Existing moderation and content-safety restrictions.
- Any other applicable timeline-eligibility constraints in the current implementation.

Treat eligibility as a hard constraint, not merely another ranking score.

A high recommendation score must never make an inaccessible post eligible.

For CH04, prioritise the eligible public-content feed specified by this requirement. Do not broaden access to private, specified-recipient, followers-only or otherwise restricted posts in order to improve recommendation quality.

Avoid duplicating the existing eligibility logic if a suitable query or service already enforces it. Inspect and test the actual behaviour.

## 7. Transparent weighted recommendation algorithm

Implement a deterministic, explainable weighted scorer.

The implementation should be small enough to understand, test and document.

A conceptual model is:

`score(user, note) = interest relevance + interaction relevance + recency contribution + diversity adjustment`

This is a design outline, not a mandatory equation. Choose the actual feature definitions, normalisation and weights based on the available Misskey data.

Document the implemented formula and ensure its components can be independently tested.

### 7.1 Interest relevance

Use appropriate interest signals, such as:

- User-controlled topic or hashtag preferences.
- Explicitly followed topics, if supported by the actual source.
- Relevant interests inferred from recent interactions, where the available data makes this practical.

Explicit user preferences should provide a clear and predictable signal.

Do not assume that every post interaction means the user wants more of the same content. Consider context and avoid treating negative or dismissive interactions as positive preference signals.

### 7.2 Interaction relevance

Investigate the existing interaction models and select signals that are meaningful and practically available.

Possible signals include:

- Bookmarked posts.
- Reactions.
- Replies or other meaningful engagement.
- Followed authors.

Use a modest, documented weighting scheme.

Avoid unnecessarily expensive per-post aggregation or N+1 database queries.

Where user-specific data influences recommendations, ensure it is only accessed for the authorised user and is not exposed to other users.

### 7.3 Recency

Recent content should generally remain competitive with older content when relevance is otherwise comparable.

Implement a deterministic recency contribution based on post creation time or another justified signal.

Use an explicit, documented decay function or time-window rule.

Test the expected ordering of comparable recent and older notes.

Avoid allowing recency to overwhelm every other signal or giving old, highly popular content an unlimited advantage.

### 7.4 Content diversity

Prevent the feed from repeatedly showing the same author or a narrow set of topics.

Use a simple, explainable approach, such as an author repetition penalty or a bounded diversity adjustment for previously selected topics.

Do not introduce a complicated learning-to-rank framework for this initial implementation.

Explain how diversity affects ordering and ensure it does not violate eligibility or privacy rules.

### 7.5 Determinism

Given the same candidate notes, user preferences, interaction data and current time reference, the scorer should produce the same ranking.

Provide stable tie-breaking so pagination and tests do not produce arbitrary ordering.

Avoid relying on uncontrolled randomisation.

If diversity adjustments use the already-selected posts, document the ordering process and ensure it remains deterministic.

## 8. Explain every recommendation

Every recommended post must have an understandable explanation.

Examples include:

- "Recommended because you follow #opensource."
- "Recommended because you frequently interact with posts about Linux."
- "Recommended because you saved a similar post."
- "Recommended because this topic matches your selected interests."

Use only the explanation supported by the actual scoring signals.

Do not display an explanation that is inconsistent with the score, inferred from a signal the system did not use, or based on data the current user is not authorised to access.

If a post receives a diversity adjustment or recency-based contribution, the user-facing explanation does not need to expose the numerical score. Explain the principal relevance reason in a concise, comprehensible way.

When no meaningful relevance explanation exists, either omit the post from the personalized candidates or provide a truthful, clearly defined fallback explanation. Do not falsely claim that a user follows a topic.

Store or compute explanations using a design that remains consistent with the actual ranking. Do not maintain duplicate explanation state that can become inconsistent with the computed score.

## 9. Topic muting and author recommendation controls

Implement user controls that make personalization genuinely controllable.

### 9.1 Mute a topic

Users must be able to prevent recommendations for a selected topic or hashtag.

Apply the preference to eligible recommendation candidates so that matching content is excluded or appropriately suppressed according to the defined behaviour.

Explicitly muted topics must not be recommended merely because another relevance signal gives the post a high score.

Define normalisation rules for topic identifiers so that the same topic cannot evade a mute because of trivial differences in representation.

Use existing hashtag conventions where possible.

### 9.2 Reduce recommendations from an author

Provide a user control to reduce recommendations from a selected author.

Define clearly whether the control excludes that author's posts from For You or assigns them a strong penalty. The initial implementation should prefer a predictable, easy-to-test policy.

Keep this control distinct from an actual block or mute if those existing mechanisms have different platform-wide effects.

A user selecting reduced recommendations should not unexpectedly block, unfollow or mute the author across the entire Misskey application.

### 9.3 Reset recommendation profile

Give users a way to reset the recommendation-specific profile and preferences as appropriate to the design.

This should clear the relevant persisted personalisation data, such as inferred interest weights or recommendation interactions, without accidentally deleting unrelated Misskey data such as the user's bookmarks, posts, follows or reactions.

Document precisely what the reset operation removes and preserve unrelated account settings.

After reset, ensure that recommendations no longer depend on cleared personalised state. The feed may use an explicitly documented fallback based on recency or newly gathered preferences.

### 9.4 User preference persistence

Inspect Misskey's existing user-setting and preference mechanisms before adding new storage.

Use a suitable existing abstraction if possible. Introduce a database model or settings structure only when necessary.

Validate all topic and author identifiers.

Ensure users can only modify their own recommendation preferences unless a specifically authorised administrative operation is being implemented.

The feature must preserve the existing behaviour of Misskey's ordinary timelines.

If a UI control or setting is used to switch feeds, ensure that the corresponding request actually selects the correct backend behaviour.

## 11. Recommendation service and API design

Introduce a dedicated recommendation service and API endpoint following the existing backend conventions.

Inspect existing timeline services, query builders, entities and API schemas to determine the appropriate integration point.

The endpoint should:

1. Authenticate and identify the requesting user.
2. Obtain eligible recommendation candidates.
3. Apply the authoritative eligibility and safety rules.
4. Load or compute the user's available recommendation signals.
5. Apply explicit topic mutes and author controls.
6. Calculate scores.
7. Apply deterministic ordering and content diversity.
8. Produce supported recommendation explanations.
9. Pack and return the appropriate note objects.
10. Return pagination information using the established API conventions.

Keep the service focused on ranking rather than copying the entire timeline implementation.

Use bounded query parameters and reasonable result limits.

Avoid returning internal ranking state, another user's preference data or private interaction history in API responses.

Follow Misskey's established authentication, permission, validation, error and entity-packing conventions.

Register the new endpoint and generate/update SDK metadata according to the repository's actual build workflow.

Do not manually alter generated files when the repository expects them to be regenerated.

## 12. Caching and invalidation

Implement a reasonable cache where it improves performance.

Inspect the existing caching conventions before choosing a cache key, storage location or expiry policy.

A cached result must be appropriately scoped to the requesting user and relevant preference state. Never allow one user's recommendation profile or ranked result to be served to another user.

Document which inputs affect the result, such as:

- User preference version.
- Explicit topic mutes.
- Reduced-recommendation authors.
- Relevant interaction signals.
- Candidate-note changes.
- The current ranking time reference, where recency influences ordering.

Invalidate or refresh cached results when a meaningful preference change occurs.

At minimum, a topic mute, author-reduction change and profile reset must affect the next applicable recommendation request. Do not let a stale cache continue recommending content the user has explicitly suppressed.

Avoid building an unnecessary caching system if Misskey's existing infrastructure or inexpensive recomputation is more appropriate for the bounded candidate set.

Measure or explain the chosen approach rather than adding caching solely to satisfy the feature description.

## 13. Security, privacy and content safety

The recommendation system must preserve Misskey's existing access-control guarantees.

Enforce applicable visibility, block, mute and moderation restrictions before a candidate can be returned.

Never trust the frontend to perform eligibility filtering by itself.

Ensure:

- A user cannot read another user's personalised profile.
- Preferences are written only for the authorised account.
- Private interaction data is not exposed through recommendations or explanations.
- Draft, deleted or inaccessible notes are excluded.
- Explicitly muted topics remain excluded.
- Reduced-recommendation author controls are applied consistently.
- Existing block and mute semantics remain effective.
- CH03 link-safety warnings or restrictions remain respected where they apply.
- Resetting the profile cannot delete unrelated user content.
- Cache keys and entries do not leak personalised data across accounts.

Use existing permission and note-visibility mechanisms rather than reproducing an incomplete copy of them.

If the exact restrictions cannot be determined from the supplied context, inspect the actual implementation and tests before deciding what may be returned.
