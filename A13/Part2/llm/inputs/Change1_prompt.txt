## 3. Feature specification

Implement a structured event-management experience integrated into Misskey's existing social networking application.

The result should allow users to create events, share them through the appropriate Misskey interface, express their attendance intentions, receive relevant notifications, and manage events they own.

Misskey already supports ordinary posts, media, notifications and other social interactions. Do not merely add event details to an ordinary text post and claim the feature is complete. Implement an actual structured event workflow.

### 3.1 Event information

An event must support:

- A required title.
- A description.
- A start date and time.
- An end date and time.
- A valid IANA timezone identifier.
- An optional physical location.
- An optional online meeting URL.

Use appropriate database types, API schemas and frontend controls for these fields.

Establish sensible validation constraints for title and description length, valid time ranges, timezone identifiers and optional URL fields. Reuse Misskey's existing validation and error-handling conventions.

The start and end instants must be stored and compared consistently regardless of the creator's local timezone. The selected timezone should be preserved or otherwise represented according to the chosen data model so that the event can be displayed correctly.

Reject invalid time ranges, malformed inputs and unsupported URL schemes. Do not trust frontend validation as the sole enforcement mechanism.

### 3.2 Creating and sharing events

An authenticated local user must be able to create an event.

Integrate the feature with the existing Misskey application and content experience. Inspect the note model, frontend composer, timeline rendering and existing media or structured-content patterns before deciding how best to represent an event.

Choose the smallest maintainable architecture that supports a real user-facing event workflow.

The implementation must provide a suitable way to access event details and RSVP controls from the application. A backend-only endpoint with no practical way for a user to use the feature is insufficient.

Do not introduce unnecessary duplicate post models or bypass Misskey's existing access-control and validation mechanisms.

For this change, events created locally are in scope. Full ActivityPub federation of event objects is explicitly out of scope unless a minimal existing mechanism makes it unavoidable. Do not claim remote-instance interoperability.

### 3.3 RSVP functionality

Support these three RSVP states:

- `going`
- `interested`
- `not_going`

An authenticated user must be able to select or change their response to an event.

Implement the appropriate persistence and API behaviour so that:

- An RSVP is associated with an event and a user.
- Each user has at most one current RSVP per event.
- Changing an RSVP updates the existing response rather than creating duplicate attendance records.
- Attendance counts or equivalent event-attendance summaries reflect the current responses.
- The event creator can inspect attendance information in accordance with the application's privacy rules.
- Users cannot modify another user's RSVP.
- Invalid, missing, cancelled or inaccessible events produce appropriate errors.

Define and enforce the rules for events that have already started or ended. These rules should be consistent across the API and service layers.

Protect against duplicate records and concurrent RSVP updates through appropriate constraints and data-access behaviour.

### 3.4 Editing and cancellation

Event creators must be able to edit event details and cancel their own events.

Implement the following behaviour:

- Editing an event updates its stored information and the information shown to users.
- Changing the start time updates the reminder schedule.
- Changing the relevant event details can generate an event-update notification for affected attendees.
- Cancelling an event marks it as cancelled using the chosen domain model and prevents its outstanding reminder from being delivered.
- Cancellation generates an appropriate notification for affected participants.
- Unauthorised users cannot edit or cancel an event they do not own.

Avoid deleting records when doing so would destroy necessary RSVP or notification history.

Use transactions or other appropriate consistency mechanisms where multiple related records must change together.

## 4. Reminder and notification requirements

Integrate the feature with Misskey's existing notification, job-queue and background-processing architecture. Inspect the relevant queue declarations, processors, event services and notification types before adding new infrastructure.

Do not introduce a separate standalone notification system if the existing one can be extended safely.

### 4.1 Event reminders

Implement an automatic reminder for eligible event participants before the event starts.

Use a documented initial default reminder lead time of **15 minutes**.

The scheduling logic must account for the event's actual start instant rather than the wall-clock representation of a particular timezone.

The behaviour must satisfy these conditions:

- A reminder is not scheduled for an event that has already passed.
- Editing an event's start time updates its reminder schedule.
- Cancelling an event prevents its pending reminder from being sent.
- A participant who changes their RSVP to `not_going` must not receive the event reminder.
- Eligible participants receive no more than one reminder for the same event occurrence.
- A job that is retried or processed more than once must not generate duplicate reminder notifications.
- The reminder identifies the event clearly and provides a way to view its details.
- Scheduling and delivery use the existing queue or job mechanisms where appropriate.

Choose a scheduling design that fits the current Misskey implementation. Avoid introducing an unreliable in-memory timer that loses scheduled work on process restart.

Use the repository's existing notification conventions and persistence patterns.

### 4.2 RSVP notifications

Implement appropriate notifications for relevant RSVP activity, using the existing notification system if feasible.

At minimum, define the intended behaviour for the event creator when an attendee responds or changes their response. Avoid sending duplicate notifications for idempotent requests.

Ensure that notification recipients and payloads comply with existing user and event visibility rules.

### 4.3 Event update and cancellation notifications

When an event changes in a way that affects attendees, notify the relevant participants according to the chosen notification policy.

A cancellation notification must make clear that the event has been cancelled. It must not be confused with a reminder or a normal RSVP update.

Use distinct notification semantics and types where the existing architecture requires them. Do not create redundant types merely to increase the number of apparent features.

### 4.4 Failure handling

Handle the following situations:

- The queue submission fails.
- A scheduled job executes after an event has been cancelled.
- A scheduled job is retried.
- An attendee changes their RSVP shortly before the reminder.
- An event is rescheduled multiple times.
- The event or attendee becomes inaccessible under the applicable rules.

The system must not send stale notifications simply because an old job remains in the queue. Jobs should verify the current event and RSVP state when appropriate.

Document any external-service or infrastructure limitation that prevents complete verification.
