## 3. Core requirement

Misskey already supports audio files and other media attachments. Simply enabling audio uploads or adding a generic HTML audio element is not a sufficient implementation.

Create a dedicated audio-post experience that integrates with Misskey's existing media, post composition, note rendering and content-access mechanisms.

The feature must support:

- Recording or uploading audio clips.
- Audio playback with a waveform and duration.
- Optional speech-to-text transcription.
- Author review, correction and approval of generated transcripts.
- Expandable and collapsible transcript presentation.
- Searchability of published transcripts.
- Accessibility-conscious audio and transcript controls.
- Configurable transcription providers without mandatory dependence on a paid external API.

Inspect the existing source first. Reuse Misskey's media upload, DriveFile, note, API, notification, queue and search architecture where appropriate.

Do not introduce a parallel media-storage mechanism without a demonstrated technical reason.

## 5. Audio recording and upload

### 5.1 Recording

Provide a recording option in the appropriate post-composition workflow using browser audio-recording capabilities supported by the existing frontend environment.

Where supported, use the browser's MediaRecorder API or an appropriate existing abstraction.

The recording workflow must handle:

- Microphone permission requests.
- Recording start and stop.
- Previewing the captured audio.
- Discarding an unwanted recording.
- Uploading the accepted recording through Misskey's existing media-upload mechanism.
- Unsupported browser capabilities and denied permissions.
- Recording or upload failures without losing unrelated composer state.

Do not require microphone permission merely to view or play an existing audio post.

### 5.2 Uploading existing audio files

Allow users to select supported audio files using the existing file-selection and upload conventions.

Reuse Misskey's existing validation and storage infrastructure. Do not trust the filename or client-provided MIME type alone.

Apply the existing or appropriately configured file-size limits and validate the format on the backend.

Handle unsupported, malformed and empty audio files with meaningful errors.

Do not weaken existing media validation to make the feature easier to implement.

### 5.3 Audio metadata

Extract or calculate the metadata necessary to display and handle the clip, including its duration where available.

Use the existing media metadata when it is reliable. Avoid storing redundant copies of metadata that already exists unless there is a clear requirement.

Handle audio files whose metadata cannot be decoded. The original audio should remain manageable even when waveform or duration extraction fails.

## 6. Waveform and player UI

Implement a dedicated, accessible audio-post presentation integrated with the existing post display.

It should provide:

- Play and pause controls.
- Current playback position and total duration where available.
- A waveform or waveform-like representation that reflects the actual audio data.
- A usable playback-position control when supported.
- A clear loading and failure state.
- A fallback when waveform decoding is unavailable.
- Keyboard-accessible controls and meaningful accessible labels.

Prefer existing media-player patterns and frontend components when suitable.

Do not introduce a large charting or waveform dependency without justification.

If waveform generation requires decoding audio in the browser, account for large files and decoding failures. Do not load excessively large audio files fully into memory without appropriate safeguards.

Existing audio attachments must continue working after the change. Do not regress ordinary images, video, files or existing note presentation.

## 7. Speech-to-text transcription

### 7.1 Transcription workflow

Implement an optional transcription workflow that can be initiated for an eligible audio post.

The workflow should:

1. Identify the audio asset and its access permissions.
2. Submit an appropriate transcription job when transcription is requested and available.
3. Obtain transcription output from the configured provider.
4. Store the result as a draft transcript.
5. Allow the author to inspect and edit it.
6. Publish it only after explicit author approval.
7. Display the published transcript to users who are permitted to access the associated content.

The workflow must represent job states accurately, for example:

- Not requested.
- Queued.
- Processing.
- Draft available for review.
- Approved and published.
- Failed.

Use states appropriate to the final design. Avoid unnecessary states that do not represent meaningful behaviour.

### 7.2 Provider abstraction

Do not hard-code the feature to a paid speech-recognition service.

Introduce a small provider interface or use an existing suitable abstraction in Misskey. It must separate the application's transcription workflow from the provider implementation.

Provide configuration that permits an administrator to enable or disable transcription and select or configure a supported provider according to the repository's configuration conventions.

The implementation must have a meaningful, non-paid deployment path, such as a configurable local or self-hosted transcription service, where feasible.

If a concrete transcription provider cannot run in the current development environment, separate provider integration from the domain workflow and use a deterministic provider double for automated tests. Clearly document what has and has not been verified.

Do not claim that transcription works with a real speech-recognition engine when only a mocked provider was tested.

Do not introduce a mandatory external API key, paid-service dependency or network requirement for the ordinary audio playback workflow.

### 7.3 Failure handling

Handle:

- A transcription provider that is not configured.
- Provider unavailability.
- Unsupported audio formats.
- Invalid or empty provider output.
- Processing timeouts.
- Job retries.
- Duplicate job execution.
- A user requesting transcription more than once.
- An audio file becoming unavailable before processing completes.
- An author editing or discarding a draft transcript.

Failures must be reported accurately. A transcription provider being unavailable must not make the underlying audio post unusable.

Use the existing background-processing architecture if it is suitable for this work. Do not implement unreliable in-memory scheduling for long-running transcription jobs.

## 8. Transcript review, correction and publication

The author must be able to inspect the draft generated by the provider.

Implement a suitable interface or workflow that allows the author to:

- View the draft.
- Edit its text.
- Save the corrected transcript.
- Approve and publish the transcript.
- Reject or discard a draft if appropriate.
- See a meaningful processing or error state.

Enforce authorisation in the backend. Frontend controls are not sufficient to protect transcript modification.

A transcript must not become publicly searchable merely because a transcription job completed successfully.

Use an explicit approval state or equivalent clear publication mechanism. Keep draft content inaccessible to unauthorised readers.

Once approved, the transcript should be displayed in the audio-post experience and inherit the relevant visibility and access restrictions of its associated content.

Editing and republishing should update the stored transcript and its search representation consistently.

Do not publish a generated transcript automatically without the required author approval.

## 9. Transcript persistence and data modelling

Determine the appropriate data model after inspecting Misskey's existing note, DriveFile and media attachment structures.

Use a dedicated table or existing entity extension only when justified by the current architecture.

The model must represent the relationship between the audio asset or post and its transcript, along with the necessary publication and processing state.

Consider:

- Ownership and access control.
- Draft versus published state.
- Transcript updates.
- Approval metadata, if required by the design.
- Failed transcription attempts.
- Creation and update timestamps.
- Search-index updates.
- Removal or replacement of associated audio.
- Consistency during asynchronous processing.

Add migrations following repository conventions when required. Do not rewrite historical migrations.

Verify that the chosen model does not create duplicate transcript records for the same intended resource or expose draft content through a public API.

## 10. Transcript search

Making published transcripts searchable is part of this requirement, not an optional future enhancement.

Inspect Misskey's existing search architecture and identify the smallest appropriate integration.

Where appropriate, integrate transcript content with an existing supported search mechanism. If the current search infrastructure cannot safely or reasonably support this, implement a focused search path that fits the existing API and data-access conventions.

Search must return only transcripts that are approved and published.

It must respect:

- The access permissions of the associated note or audio content.
- Note visibility restrictions.
- Existing block, mute and access-control rules where applicable.
- Draft and deleted content exclusions.
- Appropriate pagination and query-size limits.
- Updates to corrected or unpublished transcripts.

Do not leak a transcript from a private or otherwise inaccessible post through search results.

Do not treat an arbitrary full-text SQL scan over all transcripts as an adequate long-term design without evaluating the existing indexing and query conventions.

Implement the smallest practical search integration and test it using deterministic data.

## 11. Security and privacy

The implementation must:

- Require appropriate authorisation for recording uploads, transcript creation and transcript modification.
- Respect ownership of audio files.
- Prevent access to draft transcripts by unrelated users.
- Avoid exposing audio content or transcripts through unrestricted endpoints.
- Use existing upload limits and file-validation mechanisms.
- Treat transcription output as untrusted text.
- Render transcript content safely using the existing text-rendering rules.
- Avoid executing commands using unsanitised user-supplied filenames or text.
- Protect any configured provider credentials.
- Avoid transmitting audio to a third-party provider unless the instance administrator has configured that provider and the workflow explicitly uses it.
- Handle changes to content visibility consistently across playback, transcript display and search.

If an implementation detail creates a privacy risk, fix the design instead of documenting the risk as an acceptable limitation.

## 13. Automated testing: focused CLI verification

Automated tests are mandatory. Do not run the entire Misskey test suite.

Inspect the existing tests and package scripts first. Use the currently installed test-runner version and the repository's established conventions.

Add tests for the actual implementation rather than constructing a separate mock application.

### 13.1 Required behaviour to test

Create a focused collection of meaningful tests covering the following applicable cases.

**Audio handling**
- A valid audio asset can use the new audio-post workflow.
- Invalid or unsupported uploads are rejected appropriately.
- Existing audio attachments remain compatible.
- Metadata or waveform extraction failures do not break ordinary playback.

**Transcription**
- A configured provider can return a valid draft transcript.
- Missing provider configuration is handled correctly.
- Provider failure or invalid output produces the appropriate job status.
- Repeated job execution does not create duplicate effective results.
- The transcription result is stored as a draft rather than immediately published.
- The author can correct and approve a transcript.
- Unauthorised users cannot edit or approve another author's draft.

**Publication and search**
- Approved transcripts are visible to authorised readers.
- Unapproved transcripts are not publicly displayed or searchable.
- Corrected transcripts update the published content and search representation.
- Search respects content visibility and does not expose inaccessible transcripts.
- Removing or unpublishing a transcript updates the relevant search results.

**Frontend behaviour**
- The relevant player or transcript component can be tested using the repository's existing frontend unit-testing tools where practical.
- Recording permission denial and unsupported recording capabilities are handled appropriately when a browser API mock is suitable.
- Audio playback remains usable when transcription is disabled.

These are coverage objectives, not instructions to create an unnecessarily large number of redundant tests. Design the smallest reasonable test suite that establishes the required behaviour.

### 13.2 Test scope

Run focused tests for:

- The new or modified backend service.
- Transcript persistence and state transitions.
- The transcription job workflow.
- The relevant search and access-control logic.
- Relevant frontend components or utilities where practical.

Run a focused type-check or lint command if appropriate.

Do not automatically run:

- The full backend test suite.
- The full frontend test suite.
- All end-to-end tests.
- Full browser automation.
- Federation tests against remote servers.
- Large load tests.
- Unrelated package test suites.

Use deterministic mocks for unrelated external dependencies. If real PostgreSQL, Redis or a local transcription engine is essential to a particular integration check, test it when available and record limitations when it is not.

A provider mock verifies the provider contract and job workflow; it does not establish speech-recognition accuracy.

### 13.3 Test failure policy

If a test fails:

1. Inspect the actual failure.
2. Distinguish an implementation defect from an environment issue.
3. Fix real defects.
4. Rerun the relevant failed test.
5. Save the actual final result.

Do not remove valid assertions simply to get a passing result. Do not fabricate output or mark a failed test as successful.

Record skipped or unexecuted checks with their actual reason and `not_run` status where appropriate.
