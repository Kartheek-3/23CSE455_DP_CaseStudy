## 5. Implementation rules for Misskey

Follow the architecture and conventions of the existing repository.

Before modifying code:

1. Identify the relevant existing frontend component, API endpoint, core service, repository, model, notification mechanism or queue processor.
2. Inspect the actual methods and their callers.
3. Identify the current behaviour and any direct dependencies affected by the feature.
4. Determine whether database changes or migrations are required.
5. Identify the API contract, response representation and frontend integration points affected by the change.

Make the smallest maintainable change that satisfies the requirement.

Reuse existing Misskey services, repositories, dependency injection, validation, notification infrastructure, visibility checks and queues wherever appropriate.

Do not create a parallel architecture merely to isolate the new feature from the existing application.

If the implementation requires a migration, follow the repository's migration conventions. Do not rewrite historical migrations.

Respect existing permissions, privacy and visibility rules. Do not weaken authentication, access control or federation safeguards.

Avoid modifying unrelated files, unrelated features or large parts of the application that do not need to change.

Do not add federation support for new functionality unless it is explicitly required by my feature specification.

Do not introduce unnecessary dependencies, external services or complicated abstractions simply to demonstrate a design pattern.

## 6. Testing policy: focused CLI tests only

Testing is mandatory, but the scope must remain focused.

I do not require you to run the entire Misskey test suite, a comprehensive browser automation suite or a large end-to-end environment merely to verify a small feature.

Your objective is to establish that the requested feature works correctly through the smallest appropriate set of meaningful tests.

### 6.1 Before writing tests

Inspect the existing test conventions and package scripts. Use the existing test framework and utilities where appropriate.

Choose the relevant test level:

- Unit test for isolated business rules or algorithms.
- Service test for interactions among the feature's backend collaborators.
- API/endpoint test if the API contract, validation or permissions changed.
- Focused integration test only when it is necessary to verify persistence, job scheduling or another direct dependency.

Do not write redundant tests that verify the same behaviour without additional value.

### 6.2 What the tests must cover

For every feature, test:

1. The primary successful use case.
2. The essential validation or failure case relevant to the requirement.
3. Any directly affected permission, privacy, visibility or state-transition rule.
4. Any critical regression behaviour that the modification could reasonably break.

Choose only the cases relevant to that particular feature. Do not apply every category mechanically if it does not make sense for the requirement.

For example:

- An event change should verify event creation and the relevant RSVP/reminder behaviour.
- A link-safety change should verify the configured safe and risky URL cases.
- A personalized-feed change should verify ranking and the visibility restrictions directly relevant to the implementation.

These are examples, not substitutes for the requirements I will provide.

### 6.3 What not to run

Do not automatically run:

- The complete repository test suite.
- Unrelated package test suites.
- Full browser-based test automation.
- GUI tests that are not needed to verify the new backend functionality.
- Large deployments or external services that can be safely replaced with deterministic test doubles.
- Expensive performance or load tests for ordinary feature acceptance.

Run a focused type-check or lint command only where practical and relevant to the changed code.

Use the repository's native CLI commands. Do not create a separate toy implementation that passes tests but bypasses the actual Misskey code.

### 6.4 Test correctness and failures

Tests must exercise the actual implementation.

Use deterministic fixtures and mocks for unrelated external dependencies when appropriate. Make test data explicit and reproducible.

If a test fails:

1. Inspect the failure.
2. Determine whether it is caused by the new implementation, an existing issue or an unavailable environment dependency.
3. Fix implementation defects where possible.
4. Rerun the relevant tests.
5. Record the actual final result.

Do not change an assertion just to force a pass. Do not disable an existing test merely because it detects a regression.

Do not mark a test as passed because the code compiles.

If a required test cannot run, record the exact command, the reason and the status `not_run`. If a test still fails, disclose the failure clearly. Do not claim the feature is fully verified.

### 6.5 Test result log

The corresponding `test_result.log` must preserve:

- The working directory.
- The exact CLI command.
- Relevant environment information.
- Actual output.
- Exit code.
- Passed/total test count where available.
- Failed, skipped or unexecuted checks and their reasons.

The log must be based on real command execution. Never manually manufacture successful output.
