PROMPT 1 — BLIND DESIGN-PATTERN IDENTIFICATION
You are evaluating design-pattern identification from Java source code for an academic case study.

Inspect every Java source file in the supplied source_files folder. Use only evidence visible in the source code. Do not infer a pattern from a class name alone or from framework conventions. If evidence is insufficient, state that explicitly.

Allowed labels (use zero or more per file):
Repository, Strategy, Observer, Service Layer, Pessimistic Locking, Exception Mapper, Filter/Interceptor, Chain of Responsibility.

For each file, return:
1. File path
2. Assigned label(s), or None/Insufficient Evidence
3. Exact source evidence (class/method/annotation and line range if available)
4. A concise explanation linking the evidence to the label
5. Confidence: High, Medium, or Low
6. Any plausible alternative label and why it was not selected

Do not invent line numbers. Separate direct evidence from interpretation. Return machine-readable CSV or JSON only if requested; otherwise use a clear table. Do not force a label when the source does not support it.

PROMPT 2 — SUMMARIZE PATTERN INVENTORY
Using the supplied patterns.csv and pattern_counts.csv, summarize the detected pattern categories and counts. Preserve the dataset's terminology and values. Distinguish the number of pattern categories from the number of instances. Do not silently change classifications or claim that all listed items are classic Gang of Four patterns. Explain each category briefly using only evidence available in the project. Flag inconsistencies or classifications that may need human review.

PROMPT 4 — REVIEW PART 2 FEATURE EVOLUTION
Review the three feature changes to the Quarkus fund-transfer application:
- Change 1: multi-currency support using a fixed/demo exchange-rate provider
- Change 2: transaction limits
- Change 3: fraud detection using a strategy abstraction

For each change:
1. Identify the actual files changed.
2. Explain the design impact and any patterns introduced, reused, or affected.
3. List the tests that exercise the change.
4. Report only test results shown in actual logs.
5. Identify edge cases and limitations.
6. Do not describe fixed demo exchange rates as live rates.
7. Do not claim a feature is production-ready without evidence.

Compare the baseline, each change stage, and the final integrated version. Preserve independent test coverage and disclose any test changes made to get a suite passing. Do not hide test modifications or failures.

- Pattern

PROMPT 6 — REVIEW LLM CLASSIFICATION RESULTS

5. Do not invent the model name, model tier, date, prompt, or output. If metadata is absent, mark it as missing and ask for it to be filled from the actual session.
