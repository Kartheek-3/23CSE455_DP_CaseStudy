CORE RULES
1. Never invent a source file, participant, class, line number, commit, test, timing, model name, date, student detail, or repository fact.
2. Separate findings into: CONFIRMED FROM SOURCE/LOG, REPORTED BUT NOT INDEPENDENTLY VERIFIED, PARTIALLY SUPPORTED, and MISSING/CONTRADICTED.
3. A class name or framework annotation alone is not sufficient proof of a design pattern. Map the collaborating roles and explain the observed interactions.
4. Preserve the project’s terminology unless the source demonstrates that it is inaccurate. If a classification is questionable, explain why instead of silently changing it.
5. Do not represent fixed demonstration exchange rates as live rates, an in-memory teaching application as a production banking platform, or a successful test run as proof that every submission requirement is complete.
6. If required files are not supplied, continue with the available evidence and clearly list what could not be checked.
7. Do not claim that you personally ran commands unless actual execution evidence is supplied.
8. Write in clear technical language appropriate for a university design-pattern case study. Be detailed, but avoid repeating the same facts in multiple sections.

PHASE C — PART 2: THREE EVOLUTION CHANGES AND REFACTORING
Treat each change as a separate snapshot and also assess the cumulative final version. For every change, identify its requirement, changed files, implementation behavior, acceptance tests, actual results, pattern effects, refactoring and limitations.

CH01 — Multi-currency support
The report describes CurrencyConversionStrategy, SameCurrencyConversion, FixedRateConversion, CurrencyStrategyFactory and VendorFxAdapter. Inspect whether the strategy separates conversion algorithms, the factory selects by currency pair, and the adapter translates vendor quote formats. Check the example of USD 10.00 at a fixed 0.92 rate producing EUR 9.20 and same-currency EUR 10.00 remaining unchanged. Check unsupported pairs, precision/rounding and errors. Verify the report’s claim that Transaction.Builder was replaced by an immutable record constructor. Identify Builder status based on the actual changed code.

CH02 — Transaction limits
The report describes TransactionLimitPolicy, PerTransferLimit and DailyLimitDecorator. Check the individual transfer cap and daily aggregate behavior, including the documented EUR 1,000 limit examples. Trace where daily usage is calculated and stored; do not assume a policy argument proves persistent or rolling daily tracking. Check boundary values and whether rejection occurs before any balance or transaction mutation.

CH03 — Fraud detection
The report describes FraudCheckChain, DenyListCheck and VelocityCheck. Trace handler order and first-rejection behavior. Verify that screening occurs before wallet debit/credit and inspect the documented suspicious-amount and deny-listed-beneficiary cases. Do not describe demo rules as a production-grade fraud system.

- Identify a genuine code smell before describing a refactoring. Do not invent a refactoring merely to fill the report.
