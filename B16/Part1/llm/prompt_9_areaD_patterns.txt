Using the Area D files (JUnit 6.1.3, commit f59f60d), check which design patterns are
actually used in Jupiter extensions and resource management.

Focus on Extension and the callback interfaces (BeforeEachCallback, AfterEachCallback, ...),
MutableExtensionRegistry, CallbackSupport, ParameterResolver and ParameterResolutionUtils,
ExecutionCondition and ConditionEvaluator, TestWatcher, InvocationInterceptor and
InvocationInterceptorChain, TimeoutExtension with SameThreadTimeoutInvocation /
SeparateThreadTimeoutInvocation, ExtensionContext and its Store, NamespaceAwareStore,
NamespacedHierarchicalStore, AbstractExtensionContext, TempDirectory / TempDirFactory /
CleanupMode, AutoCloseExtension, and BeforeEachMethodAdapter / AfterEachMethodAdapter.

Check Composite, Strategy, Template Method, Observer and Adapter (others such as Decorator
or Chain of Responsibility only with strong evidence). For each pattern: explain how it is
used, map the roles to the actual classes or methods, give the file path, line numbers and
a small code snippet, and a verdict (confirmed, uncertain or rejected) with a reason. Also
list classes that look like a pattern by name but are not, and why.

These were already counted in Areas A to C, so do not count them again unless the same
classes play a new role: the JupiterTestDescriptor skeleton methods, the
DefaultClassDescriptor / DefaultMethodDescriptor wrappers, DefaultTestReporter, the
no-op listeners (NOOP), and all listener classes.
