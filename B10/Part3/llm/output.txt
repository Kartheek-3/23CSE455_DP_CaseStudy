2. PATTERN 1 - TEMPLATE METHOD - "Date/Daily Setpoint Interpolation"
==================================================================================================
A. Selection and mapping
Why this instance: DateMethod.calculate_setpoint is a fixed interpolation algorithm that calls a single
hook, ignore_date(). DailyMethod changes the behaviour (daily repetition) only by overriding that hook,
which is the textbook Template Method shape (Gamma et al., 1994). It is pure computation over time
strings and numbers, so it can be reproduced exactly without a database.

| Pattern role                                   | Name in snippet                        | Source symbol (Mycodo/ file:lines) |
|------------------------------------------------|----------------------------------------|------------------------------------|
| AbstractClass (defines template + default hook)| DateMethod                             | mycodo/utils/method.py:75-162 (class DateMethod) |
| TemplateMethod                                 | calculate_setpoint / calculateSetpoint | mycodo/utils/method.py:87-135 |
| Hook (primitive operation with default)        | ignore_date / ignoreDate               | mycodo/utils/method.py:81-85 |
| ConcreteClass                                  | DailyMethod                            | mycodo/utils/method.py:165-196 (ignore_date override 172-176) |
| Data (method rows)                             | MethodRow                              | method_data rows loaded in AbstractMethod.__init__, mycodo/utils/method.py:30-48 |

Simplified away:
- MethodData database rows become a list of MethodRow objects. `now` is passed as text
  "YYYY-MM-DD HH:MM:SS" instead of a datetime object.
- The debug logging (method.py:118-131) is dropped.
- get_plot (method.py:137-162, 178-196) is not reproduced, because it is plotting, not part of the template
  collaboration.
- The AbstractMethod base class is omitted, because it belongs to the Strategy instance below.
- Strict input formats (2-digit fields) are specified because strptime is not available in Java, JS and C++;
  Python keeps strptime (see J).

C. Test cases (setpoint_interpolation_cases.csv)
TM01 Daily, now inside the first row → linear interpolation (25).
TM02 Same row, a different date → the Daily hook ignores the date (25).
TM03 now equal to the row start → strict "<" boundary gives None.
TM04 Decreasing setpoint (30→10) → subtract branch (25).
TM05 Empty setpoint_end → constant setpoint_start (22).
TM06 Second row matches → the loop reaches later rows (28.5).
TM07 Date method across two days → full-timestamp interpolation (17.5).
TM08 Date method with now outside the span (different month) → None.
TM09 Date method across leap day 2024-02-29 → day arithmetic with a leap year (30).

TM11 ERROR: Daily row with hour 25 → time format error.
TM12 ERROR: Date method given a time-only row → format mismatch error.

F. Language notes
- Java: DateMethod is a concrete base class; the template calculateSetpoint is declared final and the hook
  ignoreDate is protected and overridden with @Override. Overrides are checked at compile time; objects are
  garbage-collected.
- Python: DateMethod is a plain base class whose ignore_date is overridden in DailyMethod. Nothing prevents
  overriding the template itself, and mistakes surface only at run time; objects are reference-counted/GC.
- JavaScript: ES class with extends; ignoreDate is found by prototype lookup at run time; there is no
  final/protected, and objects are garbage-collected.
- C++: calculate_setpoint is non-virtual (the template cannot be overridden) and calls a protected virtual
  ignore_date marked override in DailyMethod, all checked at compile time. Rows are held by value; the
  runner owns the method through std::unique_ptr<DateMethod> (virtual destructor).

5. PATTERN 4 - PROXY - "Daemon RPC Client"
==================================================================================================
A. Selection and mapping
Why this instance: DaemonControl is a local stand-in for the remote daemon.
- It creates a Pyro5 proxy per call with a timeout and forwards calls under the same names.
- check_daemon adds timeout control and error translation.
- output_on_off is answered locally for an invalid state.
These are the remote-proxy responsibilities described by Gamma et al. (1994). It is the only Proxy
instance in Part 1.

|--------------------------|-----------------------------------|------------------------------------|
| Proxy                    | DaemonControl                     | mycodo/mycodo_client.py:50-292 |

| Proxy: added behaviour   | check_daemon / checkDaemon        | mycodo/mycodo_client.py:80-107 |
| Proxy: forwarded calls   | output_on, output_off, output_state | mycodo/mycodo_client.py:203-212, 199-201, 231-232 |
| Proxy: local dispatch    | output_on_off / outputOnOff       | mycodo/mycodo_client.py:214-222 |
| Remote proxy (dependency)| RemoteProxy (stand-in)            | Pyro5.api.Proxy, imported at mycodo/mycodo_client.py:32 |
| RealSubject              | Daemon (stand-in)                 | daemon object at PYRO_URI, outside the Part 1 scope |
| Subject                  | DaemonApi (Java and C++ only)     | not separately declared in the source (Pyro forwards dynamically) |

Simplified away:
- The Pyro5 network becomes an in-memory URI → Daemon map. A timeout is simulated by comparing the
  daemon's latency with the proxy timeout (no sleeping).
- The NamingError branch is dropped (there is no name server). The default timeout comes from a constant
  (30) instead of the Misc table.
- output_on keeps only (id, amount, channel); output_type, min_off and trigger_conditionals are dropped.
- Returned (code, message) tuples are flattened to text ("0 ...", "1 ..."), and states are compared as
  text ("on"/"1"/"true").
- Only 5 of the ~40 forwarded DaemonControl methods are reproduced.

F. Language notes
- Java: an explicit Subject interface DaemonApi is implemented by Daemon, RemoteProxy and DaemonControl, so
  the forwarding is checked at compile time; GC.
- Python: no Subject interface (as in the source); RemoteProxy forwards any attribute through __getattr__,
  so a wrong method name fails only at run time; GC.
- JavaScript: RemoteProxy's constructor returns an ES Proxy whose get trap forwards any property, so
  forwarding is dynamic and resolved at run time; GC.
- C++: an abstract DaemonApi class with pure virtual methods. proxy() returns std::unique_ptr<RemoteProxy>,
  which is destroyed after each call (the "finally" restore is a plain statement after the try/catch). The
  network map holds non-owning Daemon pointers.

is the only Plugin instance in Part 1.

- C++: there is no reflection, so the catalogue uses std::function factories plus a template make_input<T>.
  The loader returns std::unique_ptr<PluginModule> and the host returns std::unique_ptr<AbstractInput>;
  checked at compile time.

A. Selection and mapping
Why this instance: User and Role are domain objects that carry their own persistence (save/delete through
CRUDMixin) next to domain logic (password hashing). That is the Active Record pattern (Fowler, 2002). It
is the only instance in Part 1.

| Pattern role             | Name in snippet                     | Source symbol (Mycodo/ file:lines) |
|--------------------------|-------------------------------------|------------------------------------|
| Active Record base       | CRUDMixin.save / delete             | mycodo/databases/__init__.py:10-32 (save 16-24, delete 26-32) |
| Active Record (domain)   | User (set_password, check_password) | mycodo/databases/models/user.py:11-52 (35-39, 41-52) |
| Active Record (domain)   | Role                                | mycodo/databases/models/role.py:7-27 |

Simplified away:
- Flask-SQLAlchemy and SQLite become an in-memory Session with add/delete/commit/rollback. Columns are
  reduced, and the constraints are declared as UNIQUE/REQUIRED lists (instead of db.Column(unique=True,
  nullable=False)).
- bcrypt becomes an FNV-1a salted stand-in that is NOT secure (std-lib only; no bcrypt in four standard
  libraries).
- UserMixin, UserSchema, __repr__, id/unique_id defaults and current_app.logger (replaced by Session.log)
  are dropped.

C. Test cases (user_role_cases.csv)
AR01 Save one user → saved; count 1.
AR02 Save two users → count 2.
AR03 Duplicate name → save returns None (rolled back); count stays 1.
AR04 Duplicate email followed by another user → rollback clears the failed add, so the next save works.

AR12 ERROR: hash with an empty salt → "Invalid salt".

F. Language notes
- Java: an abstract CRUDMixin with abstract column-metadata methods implemented by User/Role, and a
  Session that keeps object references; identity comparison through the default equals; checked at
  compile time; GC.
- Python: a mixin base class whose models declare UNIQUE/REQUIRED class attributes read with getattr
  (dynamic attribute access, as SQLAlchemy does); run time; GC.
- JavaScript: base class with static UNIQUE/REQUIRED fields, and obj[column] for dynamic column access; run
  time; GC.
- C++: an abstract CRUDMixin with pure virtual column metadata. The Session stores non-owning raw pointers
  while the runner owns the records (std::unique_ptr). delete() is renamed del() because delete is a

12. I. TECHNOLOGY DISCUSSION DRAFT (247 words, excluding the reference list)
==================================================================================================
The same eight collaborations could be written in all four languages without changing the pattern roles.
What changes is where the contract lives:
- Java and C++ make the roles explicit types. Java uses abstract classes, interfaces, final and @Override
  (Java Language Specification, Java SE 21, chapters 8-9). C++ uses pure virtual functions, override and
  std::unique_ptr ownership (cppreference.com, "virtual function specifier" and "std::unique_ptr").
  A missing or misnamed role method is therefore rejected by the compiler.
- Python and JavaScript express the same roles by convention. The Python abc module could enforce abstract
  methods at instantiation (Python documentation, "abc — Abstract Base Classes"); the snippets follow the
  source and use plain base classes. ECMAScript classes (MDN, "Classes") have no abstract or final
  keywords.
- Dynamic features make some patterns shorter. Python's __getattr__ (Python Language Reference, "Data
  model") and the JavaScript Proxy object (MDN, "Proxy") implement a forwarding proxy without listing the
  methods. First-class classes make the Plugin catalogue trivial.
- The measured cost of static typing is size, not complexity. Java and C++ files are consistently larger,
  while the maximum function complexity is usually within a few points across languages. The largest
  complexity differences come from missing library support: hand-written date parsing in JavaScript and
  C++.
- The patterns themselves are as described by Gamma et al. (1994, Template Method, Strategy, Adapter,
  Proxy, Command) and Fowler (2002, Plugin, Layer Supertype, Active Record). Their intent survives the
  translation; only the enforcement point moves between compile time and run time.

References: E. Gamma, R. Helm, R. Johnson, J. Vlissides, "Design Patterns: Elements of Reusable
Object-Oriented Software", Addison-Wesley, 1994. M. Fowler, "Patterns of Enterprise Application
Architecture", Addison-Wesley, 2002. The Java Language Specification, Java SE 21 Edition (Oracle). Python
3.12 documentation: "abc" module and the Language Reference "Data model". MDN Web Docs: "Classes" and
"Proxy". cppreference.com: "virtual function specifier", "std::unique_ptr".

13. J. PITFALLS FOUND (and how they were resolved)
==================================================================================================
J1  CSV splitting differs. Java "a,b,".split(",") drops trailing empty fields, so every runner uses
    split(",", -1). C++ std::getline also loses a trailing empty field, so the runners' split appends ""
    explicitly. An empty field split on "|" gives [""] in every language, so empty lists are filtered
    (Plugin PL07: empty file list).
J2  C++ number formatting: the default ostream precision (6 digits) would print the dew point as 9.25517,
    which fails the 1e-9 tolerance. The C++ runners use std::setprecision(17).
J3  M_PI is not declared by MinGW g++ 6.3 under -std=c++14 (strict mode), which was a compile error in a
    probe. pi is computed as std::acos(-1.0) in setpoint_schedule.hpp. std::stod and std::to_string did
    compile on this MinGW (probe in the scratchpad), so no istringstream workaround was needed.
J4  Date parsing.
    - Python strptime accepts single-digit fields; Java needs ResolverStyle.STRICT with "uuuu" to reject
      invalid dates; JavaScript's Date.UTC silently rolls over out-of-range values (hour 25), so JS and
      C++ validate the ranges by hand.
    - The spec therefore requires 2-digit fields, and no test uses single digits.
J5  Integer vs float division.
    - C++ computes the percentage from long long seconds, so both operands are static_cast<double>.
    - Java's Duration.getSeconds() returns long and is assigned to double before dividing.
    - Python and JavaScript always use true division.
J6  Missing keys / bad numbers.
    - In JavaScript, `undefined + "text"` does not throw, so an explicit appendMessage check reproduces
      Python's KeyError (Command CM11/CM12).
    - Number('') is 0 in JavaScript, while float('') raises in Python, so the JS adapter and module-base
      code validate numeric text explicitly.
    - Java Map.get returns null (NullPointerException later), and C++ map::at throws out_of_range. Both
      reach the guarded "return None" path in the weather adapter.
J7  Exception types differ (Python ValueError/KeyError/OSError, Java IllegalArgumentException,
    NoSuchElementException, DateTimeParseException, UncheckedIOException, JS Error subclasses, C++
    std::invalid_argument/out_of_range/runtime_error). The shared CSV only says ERROR, and every runner
    accepts any exception. The Python ERROR reasons were printed and checked once (all come from
    production code, none from runner parsing).
J8  32-bit FNV-1a hash. Java int multiplication wraps and String.format("%08x") prints the unsigned value;
    JavaScript needs Math.imul and >>> 0; Python masks with & 0xffffffff; C++ uses std::uint32_t. All four
    reproduce the independently computed value d3b8b801 (AR09/AR10) and the published FNV-1a("a") =
    e40c292c.
J9  Mixed-type state in the source. DaemonControl.output_on_off compares state with ['on', 1, True]. The
    snippets compare text ("on", "1", "true") in all languages, because the CSV only carries text.
J10 Semantics of empty text. Python's ''.split(',') gives [''] but a std::getline loop gives no element;
    Java needed isEmpty() to treat an empty value.message like Python's falsy check. Both were fixed in
    production code before the first run of the Command tests (not covered by a CSV case).
J11 C++ keyword: CRUDMixin.delete() is named del() in C++ (delete is reserved). Session::commit is
    declared inline in the class and defined after CRUDMixin, because it calls CRUDMixin's virtual methods.
J12 Measurement tooling.
    - The first lizard pass silently skipped the four .hpp files. The command list was written by Python on
      Windows with "\r\n", so the last path ended in "\r" and lizard skipped a file it could not find.
      Fixed with tools/run_lizard.py, which checks every path.
    - lizard's JavaScript parser stopped after a nested template literal (`...${x ? `...` : ''}`) in
      daemon_rpc.js and reported only 3 functions. The expression was split into a separate variable
      (same output; the Proxy tests still pass 12/12), and the file was re-measured: 13 functions.
J13 Shell quoting. A bash heredoc with backslash-heavy text was mangled, so the CSV files and the README
    generator were written with the file tool instead.
J14 Untested divergence kept on purpose: DurationMethod with an empty cycle and repeat = 0 would compute
    s mod 0. Python raises ZeroDivisionError, while Java, JavaScript and C++ give NaN. The SPEC
    precondition (rows present, now ≥ start) excludes it, and no case covers it.
