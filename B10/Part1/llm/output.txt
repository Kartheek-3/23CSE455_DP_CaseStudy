## 1. Architecture summary

**Main components / layers**

- **Daemon-module layer supertype** – `AbstractBaseController` (`data/code/mycodo/abstract_base_controller.py`) gives every daemon-side module a logger, custom-option parsing (CSV/JSON), device-measurement/conversion loading, DB-persisted custom options and measurement look-ups.
- **Sensor management (Inputs)** – `AbstractInput` (`data/code/mycodo/inputs/base_input.py`) with concrete input modules `adafruit_i2c_soil.py` (capacitive soil moisture + temperature over I²C) and `weather_openweathermap_weather.py` (city weather over HTTP); registry, rescaling and conversion helpers in `data/code/mycodo/utils/inputs.py`.
- **Controller threads** – `AbstractController` (`data/code/mycodo/controllers/base_controller.py`) defines the thread loop; `InputController` (`controllers/controller_input.py`) schedules readings, pre-output activation and storage; `ConditionalController` (`controllers/controller_conditional.py`) periodically runs user conditional code.
- **Irrigation / outputs** – `AbstractOutput` (`data/code/mycodo/outputs/base_output.py`) implements on/off/duration/volume switching, on-duration logging and output triggers; concrete `pump_gpio.py` (peristaltic pump that dispenses volumes) and `on_off_gpio.py` (GPIO relay); output registry and `output_types()` in `data/code/mycodo/utils/outputs.py`.
- **Functions (closed-loop control)** – `AbstractFunction` (`functions/base_function.py`) and `bang_bang.CustomModule` (`functions/bang_bang.py`), a hysteresis controller that reads the last measurement and switches an output through the daemon.
- **Setpoint schedules** – `data/code/mycodo/utils/method.py`: `AbstractMethod` family (`DateMethod`, `DailyMethod`, `DailySineMethod`, `DailyBezierMethod`, `DurationMethod`, `CascadeMethod`) plus `create_method_handler` / `load_method_handler`.
- **Module loading** – `load_module_from_file` (`data/code/mycodo/utils/modules.py`) – importlib-based loader used by `utils/inputs.py`, `utils/outputs.py` and `InputController`.
- **Alerts / actions** – `AbstractConditional` (`controllers/base_conditional.py`) is the API offered to user conditional code; `AbstractFunctionAction` (`actions/base_action.py`) with `email.ActionModule` and `output_on_off.ActionModule`.
- **UI/CLI-to-daemon communication** – `DaemonControl` (`data/code/mycodo/mycodo_client.py`) wraps a Pyro5 `Proxy`; the daemon server side is defined outside scope.
- **Persistence / user management** – `CRUDMixin` (`data/code/mycodo/databases/__init__.py`), `User` and `Role` models (`databases/models/user.py`, `databases/models/role.py`) on `db.Model` (`db` defined outside scope in `mycodo.mycodo_flask.extensions`).

**Event flow – one soil-moisture reading, from thread start to storage**

1. The daemon (defined outside scope) starts an `InputController` thread; `AbstractController.run` (`controllers/base_controller.py:69-99`) calls `InputController.initialize_variables` (`controllers/controller_input.py:246-343`).
2. `initialize_variables` calls `parse_input_information()` (`utils/inputs.py:163-308`), which scans the input directories and loads every file through `load_module_from_file` (`utils/modules.py:10-21`). It then loads the module for `self.device` and instantiates `input_loaded.InputModule(self.input_dev)` (`controller_input.py:309-313`). The soil module's constructor calls `try_initialize()` → `initialize()`, which builds the `Seesaw` I²C driver (`adafruit_i2c_soil.py:58, 60-69`).
3. `AbstractController.run` repeatedly calls `InputController.loop` (`controller_input.py:129-238`). When the period has elapsed (141-147) it optionally switches a pre-output on via `DaemonControl.output_on` (166-171), then calls `update_measure` (345-393) → `self.measure_input.next()` (361) → `AbstractInput.next` (`base_input.py:88-92`) → `AbstractInput.read` (115-146) → `adafruit_i2c_soil.InputModule.get_measurement` (71-84) → `self.sensor.moisture_read()` / `get_temp()` → `value_set` (`base_input.py:195-220`).
4. On success, `create_measurements_dict` (`controller_input.py:395-425`) calls `parse_measurement` (`utils/inputs.py:34-73`), which applies `rescale_measurements` and `convert_units` (defined outside scope).
5. `run_input_actions` (defined outside scope, called at `controller_input.py:224`) runs the Input's actions, then `add_measurements_influxdb` (defined outside scope, called at 232-235) writes the measurements to the time-series store.

## 3. One record per CONFIRMED instance

### 3.1 Sensor Measurement Acquisition

- **Pattern:** Template Method — GoF Behavioral
- **Origin:** application (all participants). The Python iterator protocol (`__next__`) is only the entry point the application exposes.
- **Purpose:** every sensor (soil moisture, weather) follows the same reading procedure. The procedure clears the cached measurements, calls the device-specific acquisition step, classifies `TimeoutError` / `IOError` / other exceptions, logs at a level that depends on the debug setting, and returns an error flag. Only the acquisition step varies between devices.

### 3.3 Controller Thread Lifecycle

- **Pattern:** Template Method — GoF Behavioral
- **Origin:** application (`AbstractController`, `InputController`, `ConditionalController`) taking part in a standard-library hook. `threading.Thread` is on the framework side: its `start()` calls `run()`. The application overrides that `run()` hook in `AbstractController`, which comes first in the MRO of `InputController(AbstractController, threading.Thread)`.
- **Purpose:** every daemon controller thread has the same lifecycle. It initializes, logs activation time, loops until stopped (isolating each iteration's errors and sleeping `sample_rate`), and always runs final clean-up. Concrete controllers (sensor input, conditional alerts) supply only the per-iteration behaviour.

### 3.4 Output Actuation (irrigation switching)

- **Pattern:** Template Method — GoF Behavioral
- **Origin:** application.
- **Purpose:** irrigation pumps and relays share one switching policy. That policy normalizes the requested state, validates the channel and set-up, enforces a minimum off-time, keeps on-duration bookkeeping, writes the on-duration to the time-series DB and fires output triggers. Only the hardware-specific switch and status read vary between output types.

### 3.13 User and Role Persistence

- **Pattern:** Active Record — Architectural (Fowler, PoEAA)
- **Origin:** application (`CRUDMixin`, `User`, `Role`) and framework (`db.Model` / `db.session` / `db.Column` from `db` in `mycodo.mycodo_flask.extensions`, defined outside scope). `User` also inherits `flask_login.UserMixin` (framework) without overriding it.
- **Purpose:** web-UI accounts and permission roles are persisted by the domain objects themselves. Each object maps to one row, carries domain behaviour (password hashing) and saves or deletes itself.

## 8. Limitations

- **Source location:** `data/code/` does not exist in this workspace. The analysis used `Mycodo/` (git HEAD = ee70a111c622e2a81026fd5c1553a948acf8161e, clean tree), and paths were rewritten to the requested `data/code/` prefix. Line numbers are from that tree.

  - `db_retrieve_table_daemon` and `session_scope` (DB access);
  - `add_measurements_influxdb`, `write_influxdb_value`, `get_last_measurement` / `get_past_measurements` (`mycodo.utils.influx`);
  - `run_input_actions`, `check_allowed_to_email`, `send_email` (`mycodo.utils.send_data`), `convert_units`, `calculate_dewpoint`, `get_sec`, `save_conditional_code`;
  - the generated `ConditionalRun` class;
  - `mycodo.config` constants (`PATH_INPUTS`, `PATH_OUTPUTS`, `PYRO_URI`, …) and `mycodo.databases.models` (`Input`, `Output`, `OutputChannel`, `Trigger`, `Method`, `MethodData`, `Actions`, `SMTP`, `Misc`, …);
  - `db` / `ma` (`mycodo.mycodo_flask.extensions`), `LockFile`, the `constraints_pass_*` functions, `TRANSLATIONS`;
  - third-party libraries (Pyro5, adafruit_seesaw, RPi.GPIO, requests, bcrypt, Flask-Login, marshmallow).
- **Callers not visible:** who calls `AbstractOutput.output_on_off` / `initialize` / `stop_output`; who calls `bang_bang.CustomModule.loop` and `stop_function`; who consumes `create_method_handler` / `load_method_handler` (setpoint-tracking controllers); who calls `ActionModule.run_action`; the loaders for function and action modules; the Flask views (so MVC and any role-based authorization use of `Role` flags cannot be assessed).
