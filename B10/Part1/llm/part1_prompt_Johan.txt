TASK
Find the design pattern instances in the SCOPE files: GoF (creational, structural,
behavioral) and architectural (e.g. Repository, Active Record, Plugin, Proxy, Layer

GRASP: report a GRASP pattern ONLY if it is not already covered by a GoF or architectural

STRICT RULES
1. A pattern instance is one COLLABORATION of participants, not one class. Two concrete
   strategies in the same collaboration = ONE Strategy instance. Never count the same
   collaboration under two pattern names.
2. Map EVERY role of the pattern to an actual class, interface, method or function, with
   "path:startline-endline", where path starts with "data/code/" and the line numbers are the
   real line numbers in that file.
3. Before writing any line range, confirm it with the Read tool or `grep -n`. For a class,
   the range runs from the "class" line to its last line; for a method, the "def" line to
   its last line. If you cannot confirm a range, write "line range uncertain".
4. If a role does not exist in the code, write "not separately declared". If one class
   plays two roles, say so (e.g. "ConcreteSubject=Library (also performs Subject role)").
   NEVER invent classes, methods or line numbers.
5. A class name, docstring, annotation or comment alone is NOT evidence. Evidence must be
   the interaction: who holds whom, who calls whom, what can be swapped/extended, which line.
6. Classify each candidate as CONFIRMED, UNCERTAIN or REJECTED and give the reason.
   Actively check and report rejections for these common false positives: Singleton,
   Factory (vs. a plain function that returns an object), Facade, Decorator (Python
   @decorators are not automatically the GoF Decorator), Template Method on plain overrides
   that call super(), Command, Composite, Observer, Repository on simple ORM queries.
7. Where the same mechanism repeats across many subclasses (e.g. many input modules),
   treat it as one instance and list only the concrete classes present in SCOPE.
