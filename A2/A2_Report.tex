\section{Application and Architecture}

The application studied is the MBTA API, an Elixir/Phoenix
application available at \url{https://github.com/mbta/api}.
The source was inspected from a downloaded archive. Its exact
baseline Git commit could not be independently verified.

The repository specifies Elixir 1.19.5-otp-28 and Erlang/OTP
28.5.0.3 in its \texttt{.tool-versions} file.

The analysis focuses on two candidate Strategy pattern
collaborations:
\begin{enumerate}
    \item Rate Limiter Backend Selection.
    \item State Data Parsing.
\end{enumerate}

\section{Part 1: Pattern Discovery}

The candidates were identified by examining common behaviours,
implementations, configuration, and delegation calls in the
source code.

\subsection{Rate Limiter Backend Selection}

The common behaviour is
\texttt{ApiWeb.RateLimiter.Limiter}. The concrete backends are
\texttt{ApiWeb.RateLimiter.ETS} and
\texttt{ApiWeb.RateLimiter.Memcache}. The
\texttt{ApiWeb.RateLimiter} module acts as the context by
selecting a configured backend and delegating operations.

This is a Strategy pattern candidate because the application
can use interchangeable implementations through a shared
contract.

\subsection{State Data Parsing}

The parsing contract is \texttt{Parse.parse/1}. The parser
implementations include \texttt{Parse.Alerts},
\texttt{Parse.Line}, and \texttt{Parse.Routes}. The
\texttt{State.Server} module obtains a configured parser and
delegates parsing to it.

This is a Strategy pattern candidate because parsing behavior
is delegated to a selected parser implementation.

\section{Part 2: Evolution and Refactoring}

Three changes were prepared in the evolved source copy.

\subsection{Change 1: Rate Limiter Test Coverage}

Tests were added for clearing rate-limiter state and keeping
different users' counters independent.

Observed result:
\begin{itemize}
    \item Command:
    \texttt{mix test apps/api\_web/test/api\_web/rate\_limiter\_test.exs}
    \item 8 tests, 0 failures.
    \item Memcache and integration tests were excluded.
\end{itemize}

The Strategy pattern participants remained unchanged.

\subsection{Change 2: ETS Rate Limiter Tests}

Targeted tests covered requests within and over the limit,
independent keys, clearing, and concurrent requests.

Observed result:
\begin{itemize}
    \item Command:
    \texttt{mix test apps/api\_web/test/api\_web/rate\_limiter/ets\_test.exs}
    \item 5 tests, 0 failures.
    \item Memcache and integration tests were excluded.
\end{itemize}

The Strategy pattern remained unchanged. The recorded diff
is descriptive because the original source archive did not
contain the added test file.

\subsection{Change 3: Parser Exception Handling}

The \texttt{parse\_new\_state/3} function was updated to handle
parser exceptions separately and avoid publishing a successful
update event when parsing fails.

The targeted test command was:

\begin{verbatim}
mix test --no-compile apps/state/test/state/server_test.exs
--name-pattern "invalid parsed state does not emit a successful update event"
\end{verbatim}

Observed result: 1 test passed and 18 were excluded. Because
the command used \texttt{--no-compile}, it does not prove that
the latest source compiles cleanly. A separate compile/test
attempt encountered a warning treated as an error in
\texttt{apps/state/lib/state/shape.ex}.

The State Data Parsing pattern remained in place; the change
improved exception handling.

\section{Findings}

Two candidate Strategy collaborations were identified in the
inspected MBTA source. The rate limiter delegates operations
to configurable backends through a common behaviour. State
parsing delegates to configured parser modules.

Two changes expanded rate-limiter test coverage, and one
change improved parser exception handling. The cross-language
examples illustrate the pattern structure but do not reproduce
the full production behavior.
