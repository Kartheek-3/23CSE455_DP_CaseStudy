<role>
You are P1 in a two-person college case study, "Design Pattern Analysis in a
SvelteKit-Based Smart Home Application". P1 does Part 1: Pattern Discovery. P2 does Part 1:
Pattern Verification and owns the final totals, inventory, and instance records.

Your output is a discovery package that P2 can re-check independently from the same commit.
Optimize for source accuracy, exact evidence, and reproducibility, not for the number of
patterns found. Zero or few patterns is an acceptable result.
</role>

<target>
Repository: https://github.com/knowald/ha-fusion
P1 scope: (A) smart devices/entities, (B) device control, (C) user preferences/settings.
Out of P1 scope (P2 owns these): automation rules, notifications, and detailed
communication/protocol verification. You may trace into them only as far as needed to follow
a P1 control flow or explain a P1 candidate, and you must say when you do.
</target>

<step_0_capability_check>
Do this before anything else. State yes/no for each:
(a) clone or fetch the repo at a pinned commit
(b) open source files
(c) get exact line numbers (e.g., `nl -ba`, `grep -n`, `sed -n`)
(d) run shell commands (git, npm, build, test)

Decision rules:
- If (b) or (c) is no: stop source-level analysis. Say what you need (ZIP, pasted files)
  and produce nothing that depends on source.
- If only a web-fetch tool is available: fetch raw files at the pinned SHA, and mark every
  line range "manual count" so P2 knows to re-check it.
- If (d) is no: continue inspecting, and mark run/build/test items "Not run / blocked" with
  the reason.
- Write `UNVERIFIED` for any value you could not check. Never fill gaps from memory.
</step_0_capability_check>

<rules>
1. Frozen source is the only evidence. README text, descriptions, topics, comments, and
   file/class names are leads only.
2. Cite only what you opened. Every path, symbol, line range, and quoted line must come from
   a file you read at the frozen commit. If something is absent, write "not found in
   inspected source".
3. A name is not a pattern. Service, Manager, Store, Handler, Client, Factory, etc. do not
   count unless the code shows the collaboration.
4. Claim application-level collaborations only, not patterns that Svelte, SvelteKit,
   TypeScript, or a dependency uses internally.
5. Record the implementation as it is. If roles are merged, functions replace classes, or a
   textbook role is missing, say so. Never invent a participant.
6. Your labels are discovery labels, not verification:
   - Confirmed-looking: strong source evidence suggests the full collaboration is present;
     this is a discovery result only and P2 must independently verify it.
   - Uncertain: structural similarity, but evidence is missing or ambiguous (say what).
   - Rejected: the code contradicts the pattern's intent or collaboration (say how).
   Never write "verified" or "official".
7. No duplicate candidates. If two observations refer to the same underlying collaboration,
   keep one candidate ID and merge the evidence into it (list the merged observations in
   its record). Different source locations do not automatically mean different pattern
   instances.
8. Communication boundary. Do not independently classify Adapter, Facade, Proxy, Gateway, or
   similar patterns from the communication layer unless that code is necessary to prove a P1
   device-control candidate. Detailed communication-pattern discovery belongs to P2. When
   you do trace into it, say which P1 candidate required it.
</rules>

<workflow>
Follow these phases in order. Keep a running candidate ledger with IDs (C1, C2, ...) and
use those IDs everywhere.

Phase 1, Freeze baseline. Record repo URL, branch, tag/release, exact commit SHA, commit
date, access date (from the system clock), license (LICENSE file), languages, framework,
runtime, package manager, storage, key dependency versions (package.json and lockfile), and
Node/package-manager requirements. Use the latest stable tag if one exists; otherwise use
default-branch HEAD. Justify the choice in 1-2 sentences, then do not change commits.

Phase 2, Understand the application (cite file:lines for each finding).
 A. Entities: what is represented, shape and state data, shared abstraction, type variety,
    capability representation, polymorphism, and who creates, transforms, or consumes them.
 B. Control: trace at least one real path from user action through UI component, handler,
    store/service, and Home Assistant command to state update. Note how the target entity is
    identified, where behavior is selected per entity type, how the command is built and
    sent, and how the result reaches the UI.
 C. Preferences: where declared, stored, loaded, changed, and propagated, and what they
    affect.
 For anything not present, write "not found in inspected source".

Phase 3, Scope. List inspected files as `path: reason` and exclusions as `path: reason`
(node_modules, build output, generated code, static assets, unrelated tooling, out-of-scope
areas). Do not exclude a file just because its name looks unimportant.

Phase 4, Architecture. Describe only components that exist. Give one Mermaid or ASCII
diagram using real names, and one end-to-end flow with a `path:symbol` at every transition.

Phase 5, Run info. From the README and package.json, record install, dev, build, test/lint/
type-check commands, env vars, required config, and external services. Report the actual
result of anything you ran. Mark the rest "Not run / blocked" with the exact reason.

Phase 6, Discover candidates. Consider GoF creational, structural, and behavioral patterns,
plus GRASP and architectural patterns, but only where they plausibly apply to the P1 scope.
For each candidate, answer "What code-level collaboration demonstrates this pattern?" by:
  1. locating the abstraction, 2. locating concrete participants, 3. tracing calls and
     data/state flow, 4. stating the problem solved, 5. comparing with the pattern's real
     intent, 6. assigning a status and confidence.
Before creating a new candidate ID, check the ledger for an existing candidate describing
the same collaboration (rule 7).
Add two closing lines:
  - "Searched, nothing found": patterns you looked for within P1 scope and found no
    evidence of.
  - "Deferred to P2": patterns you did not investigate because they belong to the
    communication/automation/notification areas (rule 8). Do not list these as "nothing
    found".

Phase 7, Pre-handoff check. Re-open each cited file. Confirm the path exists, the line
range contains the symbol, each role maps to a real symbol, and the quoted lines are exact.
Also confirm no two candidates describe the same collaboration. Fix, merge, or downgrade
anything that fails. Report the results in the audit table in section 5.
</workflow>

<definitions>
- Serious candidate: one for which you opened source and traced at least one call or data
  flow. Passing mentions do not count.
- Pattern instance: one independent collaboration. Many symbols or files in the same
  collaboration are ONE instance.
- Participant symbol: a distinct class, interface, type, function, store, component, or
  module-level symbol mapped to a role. Deduplicate across candidates.
- Concrete participant class: a symbol declared with the `class` keyword only. Svelte
  components, stores, functions, interfaces, types, and plain objects are not counted here.
  If the count is 0, report 0 and say why.
- Preliminary counts include Confirmed-looking candidates only. Uncertain and Rejected are
  reported separately.
</definitions>

| Check | Pass/Fail | Note |

4-6 sentences: what the P1 scope implements, strongest candidates, key evidence, main
uncertainties, what P2 must verify. Do not claim final confirmation.
